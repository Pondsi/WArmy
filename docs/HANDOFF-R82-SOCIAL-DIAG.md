# 交接：#113/#115 社交接入向导与连通性诊断

## 是什么

新增 `packages/app-shell/src/she-jiao-lian-tong.ts`：

- 四平台配置校验：飞书、钉钉、企业微信、Telegram；
- 端点推导（飞书 tenant_access_token、钉钉 accessToken、企微 gettoken、Telegram getMe）；
- 分步诊断：`config` → `dns` → `http`；
- 错误分类：401/403 归“凭据被拒”，超时/DNS 失败分开；
- 所有错误/步骤都脱敏，不回显 secret/token 全文。

设置→功能→社交接入（既有配置行）新增「连通性诊断」按钮，结果显示每步 `✓/✗` 与建议。

## 有什么用

- 用户填完凭据后能先判断“网络通不通、凭据对不对”，不用等发消息失败；
- 不会把 401 误报成网络问题，也不会把超时误报成凭据错误；
- 诊断结果不包含密钥，可安全截图/发日志。

## 入口

设置 → 功能 → 社交接入 → 每个平台行 →「连通性诊断」。

## 数据与权限

- 配置只从当前输入框读取，诊断时在内存构造请求；
- 不落盘、不写设置、不打印 secret；
- 默认超时 8 秒；非回环 baseUrl 强制 https。

## 方案与取舍

- 方案 A：只做静态说明。  
  - 优点：零风险；缺点：用户不知道错在哪。
- 方案 B（已采用）：配置校验 + DNS + HTTP 诊断。  
  - 优点：能区分网络/凭据/超时；缺点：不验证平台业务码，也不收发消息。
- 方案 C：完整接入各平台消息协议。  
  - 优点：真正可用；缺点：需要真实企业应用凭据、回调/长连接公网地址与服务端联调。

## 例子

- 飞书 appId/appSecret 填错：`config` 通过，`http` 返回 401，提示“凭据被拒”，不是“网络不通”；
- 域名写错：`dns` 失败，提示检查域名/网络；
- 服务器不回包：8 秒后 `http` 超时，提示检查网络/代理。

## 最坏情况

- 2xx 只代表端点可达，不代表机器人已开通/有权限；
- 真实消息协议未实现，诊断通过不等于能收发；
- baseUrl 指向恶意地址时可能泄露凭据到该地址（用户自己填的地址，代码只做格式校验）。
