# 账号与互通安全：把"钱包式安全"落到一个**没有服务器**的产品上

> 起因：用户给了一份《登录账号安全方案》（比特币钱包式：根身份密钥 + 设备密钥 + 挑战签名 + 端到端加密 + 中继只存密文）。
> 那份方案默认**有一个中继/服务端**。我们的产品没有服务器，所以不能照抄；能照抄的是它的**安全哲学**，
> 需要替换的是"服务端验证"和"中继转发"两处。本文说清哪些能直接照搬、哪些必须换、换成什么。

## 1. 能直接照搬的六条
1. **账号 = 密钥对**（不是用户名 + 密码）。我们已有：凭证 = 256 bit 种子 ⇒ Ed25519 身份密钥，确定性派生、跨设备一致。
2. **根密钥不用于日常登录**：日常用"设备密钥 + 伪 PIN 解封"，根密钥只在换设备/导出/恢复时用。
3. **助记词只做离线备份**，不做日常凭证（用户已确认：助记词是唯一取回方式）。
4. **私钥不落明文**：本机只存"被封装后的密钥材料"（PIN 包 / 系统可信存储）。
5. **不自己造密码学**：Argon2id、HKDF、XChaCha20-Poly1305 / AES-256-GCM、Ed25519 / X25519，全用成熟实现。
6. **端到端加密 + 只搬密文**：任何同步介质（网盘、U 盘、聊天文件）都只看到密文。

## 2. 必须替换的两处（因为没有服务器）
| 原方案 | 为什么不能照抄 | 我们怎么做 |
|---|---|---|
| **挑战-签名登录**（服务端发 nonce） | 没有服务端发挑战，也没有"登录会话" | **本机解锁**用伪 PIN（`P0-5-ZITUOGUAN.md` §9）；**互通**时由**对端**发 nonce（见 §3） |
| **中继暂存离线消息** | 没有中继 | 消息走用户已有的渠道（微信/飞书/邮件/U 盘…）；我们只保证**内容本身是签名+加密的**，渠道拿到的只是密文 |

## 3. 互通信封 v2（牛马 ↔ 牛马 / 人 ↔ 牛马）
```
envelope = {
  v: 2, from: 身份公钥指纹, to: 收件人指纹（可多个）,
  dev: 设备证书（根密钥签发的设备公钥 + 有效期 + 序号）,
  nonce, ts, ttl,
  payload: AEAD( 会话密钥, 正文 ),
  wrap: 每个收件人一份 X25519(临时密钥, 收件人公钥) → 会话密钥,
  sig: Ed25519( 发件设备私钥, 以上全部字段的规范化串 )
}
```
验证顺序（任一不过就拒收，并如实说明是哪一步）：
1. 设备证书是否由**发件人根身份公钥**签发、是否在有效期内、是否在**撤销名单**里；
2. 信封 `sig` 是否由证书里的设备公钥签发、`nonce+ts` 是否未过期/未重放（按 `from+nonce` 记一个短期窗口）；
3. 自己是否是收件人之一；`wrap` 解出的会话密钥能否通过 AEAD 校验；
4. **正文里的"我做过/我要做"不作为事实**，除非带上可核对的产物或签名引用（与知识库的证据闸同一口径）。

## 4. 联系人 / 项目 / 群聊怎么存
- **社交图谱是私密数据**：联系人、项目成员、群成员一律加密存本地（不进可公开的会话库），导出时也只出密文。
- **群聊密钥**：每个群一把对称"群密钥"，发给成员时逐个用对方公钥封装（成员变更 ⇒ 轮换群密钥并重发；离开的成员拿不到新密钥）。
- **多设备同步**：以"设备证书 + 每设备一份 DEK 包"实现；同步内容本身是密文，冲突用最后写入者胜 + 保留两版（CRDT 只用于清单类数据）。
- **不做明文上链/上云**：谁认识谁、谁是甲方乙方，都属于内部或私密层，不能因为"方便同步"就公开。

## 5. 恢复：为什么我们不默认做社交恢复
方案书推荐"3–5 个受托人 + 门限签名"。它确实比助记词好用，但会**引入一个新的信任面**（受托人串通、受托人设备被攻破、受托人失联）。
用户已明确选择"助记词是唯一取回方式"；所以：
- **默认**：助记词（24 词）+ 可选 age 导出包；
- **可选（不做进主流程）**：SLIP-39 分片交给可信的人 —— 要做得对，需要额外的联系人安全通道与撤销机制，等用户点名再做。
- **不做**："忘记一切也能找回" —— 那只可能来自服务端托管或受托人集合，与"没有服务器"冲突。

## 6. 与 P0-5 的分工
| 层 | 解决什么 | 文档 |
|---|---|---|
| 本机解锁 | 谁能打开这台机器上的数据（伪 PIN + 设备/账号/硬件绑定 + 60 天期限） | `P0-5-ZITUOGUAN.md` §9 |
| 互通身份 | 收到的东西是不是"那个人用那台设备"发的（设备证书 + 签名 + nonce） | 本文 §3 |
| 内容保密 | 渠道/同步介质拿到的是不是密文 | 本文 §3–4 |
| 数据分层 | 哪些内容根本不该离开本机（私密库/社交图谱） | `P0-6-TUMIN.md` |

## 7. 建议的落地顺序（与 P0-5 共用底座）
1. 设备证书的签发/校验纯函数（Ed25519 + 规范化串）与真值表门禁。
2. 互通信封 v2 的**解析与验签**（先只验不签，便于用测试向量跑）。
3. 群密钥与成员变更轮换。
4. 联系人/项目/群成员加密存储（先新写入，旧数据迁移留 `.bak`）。
5. 与 P0-5 的解锁界面合并：一次 PIN 解锁同时解出"本机数据密钥 + 互通身份密钥"。
