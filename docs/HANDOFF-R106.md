# R106：数据安全、选择性 .nm 迁移与项目改进方案

## 0. 交付状态与约束

- 本文是结论、实施规格与验收条件，不是操作过程记录。
- **现有产品仍不满足“全部运行数据始终安全加密”**。下述存储层与选择性 `.nm` 为待实施方案，不能用已有门禁全绿代替安全验收。
- 已修：助记词恢复保留原数据主密钥/KDF，仅替换 PIN/自动登录包裹；避免旧 `vault.bin` 失钥。临时账号与真实 DataVault 集成用例通过，旧 PIN 仍失效。
- 中间回复：改为无标题、不可折叠浮雕；执行过程仍可折叠。界面验收结果见末节。
- 已定产品要求：默认凭证加密、不额外输入导出口令；可选明文；逐类逐会话选择；导入二次确认，冲突导入覆盖；同凭证直接解包，异凭证输入源助记词；这些不再重复请求拍板。
- 不修改真实账户/数据，不代用户导入覆盖，不上传凭证，不调用 DeepSeek API。

## 0.1 复核结论（2026-10-28，覆盖本文旧方案）

**方向正确**：磁盘始终密文、按需在内存解密，优于“退出时整包加密”。但旧方案不能按原文直接开工，存在 5 个阻塞问题：

1. **驱动说错了**：仓库实际依赖 `better-sqlite3@13.0.3`（`packages/memory-os/package.json`），没有 SQLCipher。`better-sqlite3-multiple-ciphers@13.0.3` 是同版本、同同步 API、MIT、Node≥22，包内带 win32-x64/arm64、darwin、linux 的 prebuild；在临时目录实测默认 cipher：库文件和 WAL 都不含明文哨兵，错误 key 被拒绝，正确 key 可读。`PRAGMA cipher='sqleet'` 在该包会报 unknown，不要照旧方案写死 sqleet；用默认 cipher 或显式 `chacha20`/`sqlcipher`，并在启动门禁验证 `cipher_version` 非空。
2. **“SQLCipher”只保护 `memory.db`，不等于保护全部数据**：当前权威数据是明文 `fast-memory.jsonl`（`memory-os/src/index.ts:416`）、`knowledge-*.json`（`knowledge-base/src/index.ts:130`）、`settings.json`、groups/identity/audit/checkpoint/attachments 等；全项目有 **181 处**直接写盘调用。只换 DB 驱动，私库与聊天仍会明文落盘。必须建统一 `storage-core`（单加密库 + 加密对象存）并逐步删除旧直写出口，不能只包一层 fs。
3. **跨设备凭证没有真正闭环**：当前 `sessionMasterKey` 来自“助记词 + 每账号随机 salt”，同词恢复会重新生成 master；本文件 §1.1 说的稳定 `Kroot` 尚未实现，且没有旧数据迁移包。必须增加版本化 `keyEnvelope`：随机数据 DEK 由旧 master 和 `Kroot` 双包裹；登录后先解旧 DEK，再包到 `Kroot`，验证成功后才切换。否则新设备/同词 `.nm` 仍可能打不开；旧 `.nm v1` 不能假装能迁移。
4. **整仓切代导入不符合实际**：181 个写点、多个子进程/Chromium 写入，无法可靠地“暂停全部写入后复制整仓”。选择性导入应走 SQLite 单事务 + 临时加密对象 + 提交清单；只对受影响 owner 做写屏障，失败清理临时对象。整仓快照只用于全量备份，不作为选择性导入主路径。
5. **“所有数据”有物理边界**：应用无法把任意外部编辑器、工具、Chromium 原生缓存、OS 页面文件/崩溃转储都改成密文；旧明文也无法保证 SSD 法证擦除。应用管理数据可以做到全程密文；外部项目目录需要 OS 加密卷/容器或接受“用户明确导出边界”。这不是可以靠多写几行 `fs` 包装解决的。

**修订后的推荐架构**：

| 层 | 做法 |
|---|---|
| 存储核心 | `@warmy/storage-core`（或 memory-os 子进程内的唯一存储服务）：一个加密 SQLite 主库（设置/牛马/项目/联系人/群/聊天索引/KB/提示词/审计/队列/快照元数据），随机 DEK；不再让主进程各 store 直接写 userData |
| 大对象 | 加密对象目录：附件、录音、产物、快照内容、归档；随机对象 ID + 分块 AES-256-GCM，manifest/owner 在加密主库；不生成明文 tar/解压目录 |
| 聊天事实 | `fast-memory.jsonl` 改为逐记录 AEAD 追加（或迁移入主库后只留加密导出日志）；`retrieve` 仍按 seq 读原文，不降级为预览 |
| 驱动 | `better-sqlite3-multiple-ciphers@13.0.3` 在 Node 子进程加载，不碰 Electron ABI；启动自检 cipher、错误 key、WAL/temp、`cipher_integrity_check` |
| 密钥 | `Kroot = HKDF(seed, "warmy-root-v2")`；随机 data DEK；`keyEnvelope` 双包裹（legacy master + Kroot）；PIN/自动登录只解锁包裹；新设备无账号→助记词恢复→建立本机登录 |
| 导入 | 先认证 manifest/deps→主进程预览令牌→二确认→单事务 upsert + 临时对象→CURRENT 指针提交；不复制整仓 |
| 导出 | 逻辑适配器按类别/owner 查询，不按文件路径；默认 `Kroot` 包裹包 DEK，无需用户再输口令；明文显式选择 |
| 外部工具 | 明确边界：应用管理的项目/产物走密文对象库；外部路径由用户显式授权，若要求连外部工具写盘也密文，则必须使用 OS 加密卷/容器，不能虚假承诺 |

**修订后的实施顺序**：A 先修现有 P0（封存假成功、明文临时归档、导入非事务、IPC/路径/入站/更新校验）；B 引入驱动与 storage-core，先迁 memory DB + 聊天事实 + KB；C 迁 settings/groups/profile/audit/attachments/checkpoint，并加写盘路径注册/未登记即失败；D 做 `keyEnvelope` 与旧数据迁移、新设备恢复；E `.nm` 后端/选择树/同异凭证/二确认；F 性能基线与三平台包。每阶段独立回滚，未迁移完的类别在设置中明确显示“尚未全程密文”，不把半成品标成安全完成。

**已选（2026-10-28）**：采用 **A 单一加密存储核心**；外部工具/项目目录按“应用管理数据全程密文、外部路径显式导出边界”处理。后续不再重复询问这两项。

**上一版作为对照的范围**：

| 方案 | 优点 | 代价/风险 |
|---|---|---|
| A 单一加密存储核心（推荐） | 一处密钥/事务/审计；选择性导出和原子导入最容易做对；未来新数据不会漏写明文 | 需要把现有 181 个写点逐步迁入，周期最长；迁移期要双写/校验 |
| B 逐文件加密包装（过渡） | 改动小、可以先堵住当前明文文件；性能接近现状 | 181 个写点仍要靠人工登记，新增功能容易漏；跨文件导入无法真正原子；以后仍要迁到 A |
| C 只修 P0，暂不迁移 | 最快降低当前封存/导入风险 | **不满足你第 1、2 条**（运行期仍有明文），不能作为最终交付 |

我建议按 **A 分阶段做**，先做 A 的存储核心和 P0，再逐类迁移；不建议把 B 当最终方案。外部工具/Chromium/OS 页面文件的边界另需你选择：接受“应用管理数据全程密文、外部路径显式导出边界”，或要求“连外部工具写盘也必须密文”，后者必须引入 OS 加密卷/容器。

## 1. 推荐：磁盘始终密文，按需在内存解密

不是“登录解密全部文件→用完重新加密”，而是“登录解锁数据服务的密钥→按页/按块解密→磁盘从不出现新明文副本”。普通数据也采用同一路径，私密知识库/单聊额外限制访问范围和内存驻留。

| 方案 | 安全与性能 | 结论 |
|---|---|---|
| 退出时整包加密（现状） | 崩溃/强杀前明文可复制；临时归档残留；启动退出与总数据量成正比 | 不满足要求，停止扩建此模型 |
| 每次读取前解密整个文件，之后再加密 | 读取窗口仍可复制；大库反复全量I/O；搜索索引/缓存易旁路泄漏 | 不采用 |
| 加密 SQLite（`better-sqlite3-multiple-ciphers`）+ 加密对象/日志 + 专用存储进程 | 数据页/WAL内容密文，流式附件只解需要的块；维持索引、事务与连接复用 | 推荐；Node 子进程加载，需迁移与三平台验证 |
| 只用 BitLocker/FileVault | 防关机后离线拆盘，不防已登录用户复制文件 | 仅作为系统层补强，不能代替应用加密 |

**威胁边界**：保护运行中/退出后被拷走的数据文件；不能承诺阻止同OS用户恶意进程、管理员调试、内存转储、截图/拍照或已获授权的人从界面导出。Windows safeStorage/DPAPI不是“只本程序能解”的保险箱；自动登录也不是抵御同用户攻击的第二因子。明文导出是用户明确选择的保护例外；外部程序/供应商已收到的数据不能由本程序撤回。旧明文在SSD、历史备份、交换区中也不能靠删除保证法证级擦除。

### 1.1 密钥和身份

1. 保留现有助记词校验及标准化：词组/成语/拼音输入统一为规范助记词，再恢复32字节高熵seed；不得使用助记词文本哈希、公钥指纹或短PIN直接当数据密钥。
2. 推荐稳定恢复根 `Kroot = HKDF-SHA256(seed, salt="warmy-root-v2", info="recovery", 32)`。本地/导出/身份/凭据用不同info继续派生包裹密钥；根seed不进入渲染层、环境变量、命令行或日志。
3. 本地各存储域使用随机256位DEK：账户元数据、单聊/私库、协作数据、日志、对象。DEK清单由本地包裹密钥加密；新增域、轮换、销毁独立操作，不每次重加密全部数据。
4. PIN/自动登录仅解锁本机的根/DEK包裹记录；改PIN与同词恢复只重新包裹，不悄悄轮换数据DEK。短PIN离线可枚举，界面锁定计数不能阻止复制认证文件后的离线尝试；本机PIN包裹加OS保护，跨设备恢复必须用助记词。Linux无安全keyring/basic_text时拒绝自动登录，不静默base64降级。
5. 干净新设备的助记词入口必须支持“本地无账号→恢复同seed身份→建立本机登录方式”；不能仍返回 `no-account`。有本地账号时，导入解锁助记词只用于该导入事务，不能悄悄切换当前身份。
6. 当前 `AuthService.sessionMasterKey` 带每账号随机salt，不是跨设备稳定根。R106保留KDF的修复只解决旧仓恢复，不等于实现稳定根或新设备恢复。已因旧版本换salt而失钥的仓须用保留的旧认证元数据/备份恢复，不能声称本次修复能自动找回。
7. 显式换身份/轮换身份密钥须保留并验证轮换链；迁移提交前旧身份和密钥不能被删除。真实安全轮换与更改PIN是不同操作。根seed/Kroot泄漏时必须更换恢复根并轮换可能泄露的DEK、重加密数据；只改PIN/重包无效，已流出的旧 `.nm` 无法远程撤销。

### 1.2 存储覆盖清单

建立一个数据类别注册表，各写入方声明 `category, ownerType, ownerId, schemaVersion, sensitivity, exportAdapter`；未登记的新落盘路径在集成测试中失败，禁止靠宽泛的 `logs/Cache` 排除表认定安全。

| 数据 | 落地方式与修改入口 |
|---|---|
| 聊天全文、分段、工具事件、消息元信息 | `memory-os/src/index.ts` 的事实日志改为认证加密分段日志；seq/id/块偏移索引也加密；`memory-client.ts`按会话分页IPC。原文完整保留，不用截断投影替代原文 |
| SQLite记录、两路FTS、向量、meta | 实际链接SQLCipher的驱动，数据库页/WAL/回滚日志一起保护；临时表/排序文件用内存，构建时验证temp-store设置；不允许明文SQLite投影或影子索引 |
| 三层知识库 | `knowledge-base/src/index.ts`由整层JSON改为加密DB内实体/事件/关联表；保留会话/内部/私密边界；私密域按请求校验，私库索引不得混入公开缓存 |
| 牛马、项目、联系人、群、提示词、设置、档案、网络状态 | 对应store改走同一存储服务事务；启动前仅允许最小认证信封，不能实例化业务仓后写默认值覆盖真实数据 |
| API key/IM token等 | 当前设备内存解密后以DEK存储；便携导出再包入导出DEK，导入按目标设备重新包裹；不能原样复制DPAPI密文冒充跨机恢复 |
| 附件、录音、截图、产物、快照、归档、回收站 | 随机对象ID、分块AEAD密文；原文件名/路径/归属/哈希放加密索引。受控协议/流式读取，不为预览制造明文临时副本 |
| 审计、启动诊断、工具输出、崩溃信息 | 启动前日志只留非敏感错误码，业务日志进加密分段日志；不打印请求体、助记词、token、用户路径；崩溃转储默认不收正文 |
| Chromium缓存、Local/Session Storage、缩略图、下载暂存 | 检查每个实际写入点；敏感正文/凭据不存Web Storage，远程页面用非持久partition，缓存/暂存必须内存或已验证加密域；JS的fs包装无法保护Chromium原生写盘 |
| 公开模型/运行时/插件代码 | 非用户生成的公开可重下载资源按程序资源管理，不需要反复加密；自定义模型、语音、用户脚本与配置仍属用户数据 |

**外部项目目录**：仅加密userData不够。应用管理的项目数据进入密文对象库；工具需要普通目录时使用受限的内存工作区/可验证加密挂载，并纳入回收与崩溃验收。用户在外部编辑器打开、另存的普通文件是明确导出边界；不能在后台擅自加密或删除用户原有目录。强制所有外部工具写盘均密文需要OS级隔离/加密文件系统，纯Electron API不能给出该保证。

### 1.3 数据服务、锁和性能

- 独立存储进程持有密钥、DB连接及明文页缓存，主进程做授权和任务调度，渲染层只拿当前会话当前页；模型/插件进程不得继承根密钥。
- 加密SQLite真实驱动启动自检：`cipher_version`非空、错误key读库失败、有效key读成功；不能把普通SQLite接受未知PRAGMA当成启用加密。内置 `node:sqlite` 和普通better-sqlite3不能只加一句 `PRAGMA key`就变安全。驱动用 `better-sqlite3-multiple-ciphers@13.0.3`，在 Node 子进程加载；不要设置实测会报 unknown 的 `cipher='sqleet'`，用默认 cipher 或 `chacha20`。
- 复用连接/预编译语句，以随机高熵DEK的raw-key方式避免每次打开都做口令KDF；用户登录KDF放Worker且限制并发和输入参数。同步PBKDF2不能挡住主界面。
- 私库/单聊使用有上限、按会话隔离的页/正文缓存；请求后释放短期Buffer，取消/注销/系统锁屏后停止所有请求、清DOM及缓存、关闭连接并退出持钥进程。加载内容还在显示时必然存在内存明文，不虚称“加载后内存也已锁”。JS字符串/复制与GC无法保证全部立即清零。
- 日志按块追加、KB增量事务更新、快照按差量对象清单；消除当前全量重写，才有机会抵消加密CPU开销。不能承诺零开销或未实测就声称提速。
- API语义可保持 `read/query/write`；禁止全局劫持 `fs` 伪装透明加密，这会漏掉原生SQLite、Chromium、子进程和外部工具。
- 本地随机访问对象采用AES-256-GCM：每个对象版本重新生成DEK与nonce前缀，nonce为8字节前缀+4字节块序号，单版本最多2^32−1块；块≤1MiB，AAD绑定格式、对象ID、owner、版本、块号、长度和终结标记。重写/失败重试生成新版本，禁止用旧key/nonce重加密变化后的正文；未提交版本不可读，崩溃后不续用不确定计数器。

## 2. `.nm` v2 选择性导入导出规格（待实施）

### 2.1 选择树

统一设置页/我的页/项目/聊天导入导出入口；`.nm`专用格式，不使用 `.wvault` 作为新导出格式。项目/聊天快捷入口只是预选本节点。

```
我的牛马 → 牛马/会话列表 → 设置、聊天及执行过程、会话知识、提示词、附件/产物、计划/队列、快照/归档、日志
项目     → 项目/会话列表 → 同上（另含成员、值班者、权限和工作区配置）
联系人   → 联系人/会话列表 → 同上（另含名片、IM绑定）
群聊     → 群/会话列表 → 同上（另含成员、加入记录）
知识库   → 会话层 / 内部层 / 私密层 → 所属会话或全局条目
其他提示词 → 道、术、认知、短记忆、要求、印象、自定义模板
全局数据 → 我的资料、应用设置、供应商/模型、技能/插件配置、网络配置、凭据、日志、回收站、其它已登记数据
```

- 父节点全选/半选、搜索、条数/字节数、敏感标记；展开会话懒加载，不能一次把全部正文送进渲染层。
- 全局KB与某会话不是同义词，按真实owner筛选。勾选会话不能隐式导出整层私库或全部settings.json；共享依赖去重，界面列明自动包含的最小关联记录。
- 日志/快照/工具结果可能嵌入未选私库或他会话正文，不能只按owner筛选。可拆则按记录来源拆出选择副本，不修改原始日志；不可拆则阻止该项并提示显式扩选依赖或取消该项，不允许静默带出。
- 任何带程序执行能力的导入配置/技能/计划作为数据导入，不能在导入时自动运行；需原有授权机制放行后才能恢复执行。
- 默认加密且无需额外密码；关闭加密明确提示“可被任何拿到文件的人读取”，含API密钥等敏感项时额外显著确认。只导出选中数据，不携带根seed/助记词或本机PIN/自动登录解锁器；身份由用户保管的助记词恢复，不与密文捆绑泄露。

### 2.2 格式和密钥

建议新二进制头 `WARMYNM2`，版本/模式/长度/随机archiveId/随机salt/算法ID；不把会话标题、原文、用户名放公开头。旧 `.nm` JSON v1 与 `.wvault`只能经独立受限迁移解析，不能仅改扩展名宣称升级。

- 每包随机DEK；`Kexport = HKDF(Kroot, archiveSalt, "warmy/nm/v2/wrap")`包裹该DEK。包裹使用AES-256-GCM和随机nonce，完整公开头绑定为AAD，防修改模式/版本/长度。
- 大包优先成熟的 `libsodium secretstream` 顺序认证流：首个认证消息为加密manifest，后续流式条目块，必须验证 `TAG_FINAL` 与结束清单；不能忽略截断/重排/拼包。流帧固定为u32be密文长度+密文（正文块≤1MiB，manifest分帧且总大小限额），在分配内存前验长；AAD绑定完整包头摘要和递增帧号，FINAL之后强制EOF，拒绝尾随数据/拼包。库构建与供应链审核通过后接入，不自创“无MAC流加密”。
- manifest记录 `schemaVersion, archiveId, sourceIdentity, selectedScopes, entries[{id,category,ownerType,ownerId,logicalId,recordVersion,bytes,dependencies}]`；终结清单给各条目长度/内容哈希与计数。SHA-256用于完整性比对，不替代AEAD认证。明文模式同schema，但不称其“来源可信”。
- 内容只在小块内存中解密；加密临时对象/加密新数据库代次用于暂存，绝不生成明文tar或解压目录。导出文件先同目录 `.partial`，flush完成并验证写入后rename；取消清理本次暂存。
- 档案使用内部逻辑ID而非OS绝对路径。限制单块/条目数/递归深度/总展开大小，校验磁盘空间，拒绝重复ID、非法枚举、`..`、绝对路径、UNC、盘符、ADS、符号链接/junction、保留设备名及大小写碰撞。正文数据不得当SQL/脚本执行。

### 2.3 导入流程与覆盖语义

1. 主进程选择文件，固定文件身份并解析受限头；若明文，直接进入预检；若加密，尝试当前Kroot解DEK并认证manifest，**不是只比较指纹字符串**。
2. 当前凭证不能解包则显示源助记词界面；校验规范助记词、派生源Kroot，只为本次导入解密。不上传、不记录、不进聊天/模型；取消立即销毁临时密钥。损坏头/不支持版本直接报错，不循环诱导输入助记词。
3. 全包认证/结构与依赖验证后生成主进程预览令牌：绑定文件摘要、选中ID集合、冲突摘要、当前目标版本、窗口ID与有效期。渲染层只得到目录树和统计；确认后若源文件/选择/目标变更，重新预检。
4. 导入选择树展示包中可选项及新建/覆盖数量、关联依赖；第一次确认范围，第二次明确“这些冲突数据将被覆盖，完成后无法在程序内撤销”。任一步取消，对现有数据零修改。
5. 冲突按 `category + 稳定会话/对象ID + logicalId`匹配，不按显示名；冲突项用导入值覆盖，不另给“跳过/副本”改变用户定稿。不同源身份的ID碰撞必须在预览显式展示；只有内部数据库seq/rowid重映射，不能偷偷重命名会话绕开覆盖。
6. 混存JSONL/KB/settings/groups必须逻辑筛选和upsert，不能整文件替换。只覆盖选中的同ID记录，未选中和不冲突的本机记录不动。保留 `entityIds/eventIds/quDaiIds/anchors`关联，重算本机seq/字节锚点，重建FTS/向量等可再生投影。附件带真实二进制内容，不能只带源机器路径。
7. 导入源凭据数据在内存解开后按目标存储密钥重新加密；不要替换当前账户的根seed/认证文件，防止把本地未选中数据变成失钥数据。原身份签名/授权不因成功解包自动成为当前用户权限。
8. 应用期间设置与提交粒度一致的写入屏障：若整仓切代，必须锁整仓全部写入方并复核目标版本，不能只暂停选中会话而丢掉其它会话并发更新；对象预拷贝可在屏障前做。新代次基于完整本机状态，仅应用选中覆盖；DB、对象及DEK清单都落稳并校验后，以单一CURRENT指针原子提交（含文件flush/目录持久化及Windows重命名语义验证）。提交前崩溃回滚旧代次，提交后重启加载新代次；全局设置缓存和搜索投影必须失效重载。
9. “不可恢复”指成功提交后不保留应用内回档/撤销入口；提交前的事务回滚不是违背覆盖规则。独立旧备份/SSD历史块无法保证被抹除。若要求更强删除，需对象/域DEK轮换并销毁旧包裹，且说明外部备份不受控。

### 4.1 必须自动验收的安全矩阵

- 随机哨兵：聊天/三层KB/提示词/日志/文件名与附件正文；运行、注销、正常退出、强杀、断电模拟、失败导入后扫描应用路径、TEMP、缓存、DB/WAL/索引/快照；不把“搜不到字符串”单独当加密证明，同时验证格式认证与错误key拒绝。
- 两个临时OS保护器/两台设备：同seed不同auth salt、不同PIN仍可导入；不同seed须源助记词；错误词/损坏包/取消零写入；当前账号与未选择数据保持可用。
- 篡改头/manifest/任一块/tag/final、截断、重复/重排/拼接、解压炸弹与恶意路径一律拒绝，无区外文件，无未认证数据入库。
- 导入冲突二确认必须主进程校验，预览后修改文件或目标版本必须失效；提交前故障回滚，提交后无应用内旧版本恢复入口。
- 选区矩阵：4类会话×3层KB×聊天/提示词/日志/附件；测试所有禁选哨兵均不出包、依赖不带无关正文，重复导入幂等。
- 锁屏/注销时在途读取/写入/模型/插件/子进程全部停止或拒绝；错误key和keyring不可用不得降级明文；日志不出现助记词/token。

### 4.2 性能目标（目标，不是已达成的测量）

同硬件、同数据、同发行构建，以改造前冷/热各30次为基线：常用聊天打开/查询P95不慢于基线；主线程加密/导出引入的连续阻塞<20ms；50条消息翻页P95<100ms；10万条KB命中10条仅更新命中计数，不全写库；IPC pending≤128且退出100ms内拒绝；大包额外RSS≤128MiB且不随包总大小线性增长；取消1秒内停止新增I/O。优先修全写/扫描/DOM放大，不为追指标关闭认证、fsync或放宽数据完整性。

2026-10-28检索并核对当前官方资料，最新在线文档不等于本项目Electron 40.10.6已经支持所有新API。
