## #18 / #106 完整路由（方案 B）

**目标**：发送前按会话选路（最近成功优先、5 并发竞速、失败两次剔除）；失败重试；全部失败时把会话置为只读并广播“网络不可用”。

**现状**：`HuiHuaLuYou` 纯逻辑与 `touDiDaoSuoYou` 扇出已有门禁；**未接**真实发送主路径。当前人消息走 mesh 广播，服务器列表只用于配置/检测。

**落地必须一次做完的四件事**（少一件就会“界面已发、对端没收到”）：
1. 每条消息生成稳定 `msgId`（发送方 UUIDv7），接收方按 `msgId` 去重（inbox 模式）；
2. 发送前写本机 outbox（JSONL，含 msgId、会话、候选网络、payload 密文），成功回执后标记 done；
3. 选路：缓存最近成功 ≤5 → 失败两次剔除 → 5 并发竞速，首成功取消其余；超时 8s；
4. 全部失败：消息保持待发、会话只读、UI 如实显示“未送达/网络不可用”，**不假装成功**。

**最坏情况**：只做 3 不做 4 ⇒ 用户看到绿勾但对方没收到；只做 1 不做 2 ⇒ 重启丢待发消息。故 B 必须整包上线。

## #19 / #108 完整角色矩阵 + 审批流 + 服务商绑定 QR；稳定会话 ID

**角色**：创建者（creator，唯一，不可移除/不可降级）> 管理员（admin，可改设置/审批/移除普通成员）> 成员（member，只读+发言）。当前 `group-store.ts` 已有 `role` 与 `setAdmin`，但 UI 只实现了“加入者不能改名”；踢人/改设置/审批还未按角色门禁。

**审批流**：加入请求先进入 pending 列表，创建者/管理员批准后发成员证书；拒绝不泄漏群内容；证书带 groupId/member/expiresAt/supersedes，旧邀请在创建者确认后失效。

**服务商绑定 QR**：名片二维码包含 `node`（稳定锚点）、`prov`（可多选）、`tok`（一次性邀请）、`avatar`；创建者换服务商后重新生成，旧邀请失效。

**稳定会话 ID（用户提出的锚点）评价**：方向正确，但建议用**每个会话一对 Ed25519 密钥**而不是“随机 ID”：
- 创建项目/群/联系人关系时生成 `anchorKey`，公钥（指纹）作为会话锚点，私钥只在本机安全存储；不显示、不可改。
- 邀请/名片只带公钥指纹；对方用该公钥验签消息与成员证书。换网络/换服务器只换传输地址，锚点不变。
- 比“随机 ID”好在：服务器无法冒充会话（随机 ID 可被猜/被替换）；且可离线验证历史消息来源。
- 代价：锚点私钥丢失 = 该会话身份丢失（需重新邀请/重建），所以要和设备/身份备份一起备份。
- 最坏情况：只做“随机 ID 不验签” ⇒ 恶意中继可伪造该会话的消息；只做锚点不做备份 ⇒ 换机后老会话无法继续。

最坏：模型改坏专有名词/协议词 ⇒ 必须保留原文 diff、可一键回滚；不接受模型新增/删除键。
