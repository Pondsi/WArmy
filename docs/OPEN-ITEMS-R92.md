## 一、外部条件 / 真实环境（代码已就绪，等条件）

### U1. 企业微信 / 钉钉的**接收**（发送已完成）

- **是什么**：把企微/钉钉里别人发来的消息接进 WArmy，再交给某只牛马处理。
- **现状**：发送已真实实现并通过 mock 门禁；飞书用消息列表轮询、Telegram 用 `getUpdates` 已能收；
  **企微/钉钉没有等价的“可轮询消息列表”接口**，所以接收未做。
- **方案**：
  - **A. 企微回调服务器**：应用内起 HTTP 端点，实现 GET 验证 + POST SHA1 验签 + AES 解密；用户用内网穿透/反代把公网 HTTPS 指到本机。优点：协议可控、不依赖第三方 SDK；缺点：用户要维护公网入口与证书；最坏：入口配错 → 收不到消息，界面必须显示“未连接”而不是假装在线。
  - **B. 钉钉 Stream 长连接 SDK**：装 `dingtalk-stream`，用 clientId/secret 建长连接。优点：不需要公网 URL；缺点：引入第三方依赖、要企业应用权限；最坏：断线重连不稳 → 消息延迟。
  - **C. 暂不做接收，只保留发送 + 如实标注**：当前状态；最诚实、零外部依赖；缺点：单向。
- **例子**：客户在企微群里 @ 你，A/B 能把消息送进 WArmy；C 只能你主动发出去，收不到。
- **最坏**：为了“看起来双向”而做假连接 → 用户以为收到了，实际漏消息。
- **需要你**：选 A/B/C；A 给公网 HTTPS 域名/反代方式 + 企微后台 Token/EncodingAESKey；B 允许装 SDK + 给企业应用凭据。

### U2. 四个 IM 平台的真实凭据与线上联调

- **是什么**：飞书/企微/钉钉/Telegram 真正连上你的企业/机器人，而不是回环 mock。
- **现状**：四种发送形状都有 mock 门禁；没有你的凭据无法线上验证。
- **需要你提供**：飞书 `app_id/app_secret/chat_id`；企微 `corpId/corpSecret/agentId`；钉钉 `clientId/clientSecret/robotCode/userId`；Telegram `botToken/chat_id`。
- **方案**：先用测试企业/测试群联调，再切正式群；凭据只在本机加密存储。
- **最坏**：拿正式群直接试 → 发错消息/触发风控；权限不足 → 一直 401/403（界面必须如实报错）。
- **例子**：先用一个只有你和机器人的测试群跑通“发一条 + 收一条”，再切客户群。

### U3. 双机跨公网 / 多服务器故障转移

- **是什么**：两台真实设备跨公网互发；A 服务器挂了自动切 B；全失败时会话只读、消息留待发。
- **现状**：本机双实例 E2E 已过；地址簿多 peer 扇出已实现；**公网中继隧道、跨机 NAT、故障转移**未真实验收。
- **方案**：
  - **A. 只做局域网 mesh**：改动小；公网不行。
  - **B. 接 FWArmy 中继**：公网可用；要补中继客户端、回执、重试、顺序。
  - **C. 多服务器扇出 + 故障转移**：最完整；要处理部分成功、去重、乱序、只读广播。
- **最坏**：只发不收/无 outbox → 用户以为发出、对端没收到；无序扇出 → 重复/乱序。
- **需要你**：第二台设备（Windows 优先）+ 网络条件；选 B 或 C；用 FWArmy 中继时给监听地址/端口与凭据策略。

### U4. 本机 Windows Device Guard 阻止未签名打包 exe（交付阻断）

- **是什么**：2026-10-25 23:08 起，本机 Code Integrity 策略阻止 `release/win-unpacked/WARMY.exe`（事件 3077）。
- **现状**：开发态 `electron.exe` 仍能跑，所以功能验收不受影响；**打包版在本机打不开**。
- **方案**：
  - **A. 代码签名**：OV/EV 证书 + `electron-builder` 签名；需要证书文件路径（不要发聊天里）。

  - **C. 另一台没有该策略的机器验收**：最快；本机仍不能跑打包版。
  - **D. 继续开发态验收**：当前状态；不是用户实际安装形态。
- **最坏**：不处理 ⇒ 本机永远打不开打包版；发布给同类企业策略机器也会被拦。
- **例子**：签名后双击安装包无“已被组织阻止”；或管理员把该 exe 的哈希加白。

### U7. 签名名片 UI 入口

- **现状**：主进程有 `identityMyCard` / `identityPeerCard`，界面没有“导出/导入签名名片”；离线签名邀请因此缺少入口。
- **方案**：

  - **C. 局域网自动交换**：最顺滑；离线不可用，且要防自动信任。

### U9. 工具执行的 OS 级隔离（完全授权禁止区的“绝对版”）

- **现状（第 93 轮已做）**：文件工具统一路径判定；`run_shell` 静态扫描绝对/相对/环境变量/`cd`/编码命令，命中禁止区直接失败。能挡住常见绕法，但不是 OS 沙箱。
- **残余**：高度混淆（变量拼接、运行时生成路径、下载脚本再执行）仍可能绕过字符串扫描。
- **方案**：
  - **A. 保持现状**：零额外依赖；靠静态检查 + 用户授权；最坏是精心构造的命令能绕过。
  - **B. 容器执行工具**：把 `run_shell`/文件工具放进受限容器，只挂载本会话工作区与明确允许的目录；最安全；缺点是需要容器运行时、启动慢、跨平台差异。
  - **C. 低权限账户/作业对象**：Windows Job Object + 受限令牌、macOS sandbox-exec、Linux seccomp/namespace；比容器轻；实现与兼容成本高。
- **最坏**：A 下恶意/失控模型用混淆命令访问其他会话；B/C 配置错误导致正常命令跑不起来。
- **需要你**：A/B/C；若 B/C，确认是否接受“无容器/无权限时工具直接不可用”的降级。

## 二、记忆 / 上下文工程（代码层仍有缺口）

### M1. 定向模式（只有 @AI 才发言）在项目/群聊里走不通

- **是什么**：群里只有被 @ 时才让 AI 回复，避免刷屏。
- **现状**：渲染层群聊发送不传 `mentionIds`，主进程无法判断“这条是否 @ 了 AI”。
- **方案**：
  - **A. 前端解析 @ 并传 mentionIds**：准确；要改输入框/消息协议/群成员映射。
  - **B. 关键词兜底**：简单；容易误判（昵称、引用、别人叫 AI 同名）。
  - **C. 不做**：保持每条都回。
- **例子**：群里 20 人聊天，只有“@牛马-1 帮我看下”才回；A 能精确，B 可能把“牛马-1 今天没来”也当指令。
- **最坏**：A 漏传 → 该回的不回；B 误判 → 不该回的刷屏。
- **需要你**：选 A/B/C；A 要确认群成员昵称与 @ 的显示格式。

### M2. 并行执行者开工时黑板为空

- **是什么**：任务级共享黑板（已完成/待办/决定）在派生子代理/分身时，子任务拿不到主任务已写的内容。
- **方案**：
  - **A. 派生时快照黑板给子任务**：简单；子任务可能基于过期快照。
  - **B. 子任务开工时从主任务黑板按任务号拉取**：最新；多一次读写与权限校验。
  - **C. 不做**：子任务独立，靠提示词里的任务描述。
- **最坏**：A 子任务重复做已完成的事；C 子任务与主任务结论冲突。
- **需要你**：选 A/B/C。

### M3. 跨轮继续同一任务不会自动带回上一轮黑板

- **现状**：只有 `recall(任务号)` 才取回；模型不知道“上一轮做到哪”时可能重做。
- **方案**：
  - **A. 自动带回最近一个任务黑板**（6 小时内）：省事；可能带回不相关任务。
  - **B. 保持按需 recall**：干净；依赖模型主动查。
  - **C. 任务号写进会话状态并在续派时自动带**：最准；改动大。
- **最坏**：A 带错任务 → 模型跑偏；B 模型不查 → 重复劳动。

### M4. P0-6 脱敏体系仍剩的边界

> 用户已定：能力白名单 + 确定性检查 + k=2 证据；模型可提案白名单但宿主校验；不做差分隐私。

仍开放：
- **历史会话库一次性重扫**：升级前的旧条目没经过当前检查器。方案 A 不扫 / B 先 dry-run 出报告再替换（推荐）/ C 直接全量替换。最坏：不扫 → 旧泄漏一直留着；全量替换 → 历史概要大面积消失。
- **canary 红队进 live 档**：故意植入假值走完整归档，检查是否泄漏。方案 A 不加 / B 加一条（推荐）/ C 发版人工跑。最坏：只在单元层证明能挡，证明不了整条链路。
- **受众分档**（群内可见 / 可导出对外）：更安全，但要改层语义/归档/UI。
- **TTL**（概要多久过期）与**人工复核闸**：是否每条新能力都人工批。

### M5. 额度 / 预算的工程债（下一轮候选）

- 额度里加 **token 维**（现在主要按字符/轮数/次数，与真实 token 脱钩）。
- **会话级总额度**（现在每条用户消息重开一条，10 次续派 × 上限接近无界）。
- **开工前估一次**任务装不装得下（SWE-agent 式执行前准入）。
- **断点续跑不重做副作用**（LangGraph checkpointer 那条路）。
- **可组合终止条件**（token 用完 & 超时等）。
- **授权等待期间不烧额度**（审批卡等待时暂停预算）。
- 这些都不影响日常使用；属于“更省、更稳”的优化，不是功能缺失。

## 四、本轮（第 92 轮）的取舍，供你复核

1. **短记忆不可见、不可改**：这是你定的；代价是**用户无法直接纠正模型归纳错的短记忆**，只能等下一次归档或删会话。若以后想留一个“只读查看”入口，需要你改口径。
2. **短记忆仍按“规则/决定”短句追加**（沿用原规范的 `SHU_GUI_ZE` 过滤），不把整段闲聊/隐私搬进去；每会话 2000 字，超出丢最旧条目（旧条目已进知识库）。
3. **要求上限 2000 字**（与短记忆同数）；超限保存直接拒绝，不替用户改写。
4. **模型不可改要求**：产品硬门禁 E + `write_file/edit_file/copy_file/move_file` 路径拦截 + `run_shell` 路径拦截；**没有**给模型任何写 `yaoqiu/` 的 IPC。残余风险：完全授权下的命令混淆仍可能绕过（宿主无法在 OS 层完全禁止任意命令），但已堵住明显路径。
5. **旧「规范」文件保留**（`userData/guifan/`）：历史内容不丢；界面一律叫短记忆。
