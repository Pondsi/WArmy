# 第 80 轮未完成项决策表

> 这些项本轮**没有**擅自做半套：要么需要你定规则/默认值，要么需要官方凭据或真实设备。每项给出用途、可选方案、优缺点、例子与最坏情况。

## 1. #106 会话网络路由 / 在线检测 / 安全流式

- **是什么/有什么用**：让联系人/群聊/项目按会话选择多个服务器，发送时走最近成功的网络，失败自动换；在线状态与“未送达”如实显示。
- **现状**：纯路由 `hui-hua-lu-you.ts`（5 路缓存、5 并发、失败两次剔除）与 `touDiDaoSuoYou` 扇出逻辑已有门禁，但**没接**真实发送主路径；当前仍走 mesh 广播/单路。
- **方案 A（推荐先做）**：只接“在线检测 + 失败原因 + 未送达提示”，不改发送拓扑。优点：小、可逆、马上让用户知道发没发出去；缺点：多服务器仍不生效；最坏：用户以为多服务器已生效。
- **方案 B**：接完整路由（发送前按会话选路、失败重试、只读广播）。优点：多服务器真正可用；缺点：必须先补 msgId 去重与回执，否则会出现“界面已发、对端没收到”；最坏：消息重复或丢失。
- **例子**：会话绑了 A/B 两台服务器，A 挂了，B 成功——B 方案会切到 B 并置顶；A 方案只提示“A 不可用”。

## 2. #108 邀请名片 / 加入 / 成员权限

- **是什么/有什么用**：换设备/换网络后仍能靠稳定名片找到彼此；创建者/管理员/成员权限分级。
- **现状**：名片链接含 node/port/token/指纹；加入弹窗已有扫码/粘贴/回执；**角色矩阵、管理员、审批流、provider 绑定二维码未做**；本轮已先收紧“加入者不能改名”。
- **方案 A**：先补名片 `did/boxPub` 与邀请回执校验。优点：换网可相遇，改动小；缺点：权限仍只有创建者/非创建者两档；最坏：普通成员仍可能做除改名外的管理动作。
- **方案 B**：完整角色矩阵 + 审批流 + 服务商绑定 QR。优点：多人协作边界完整；缺点：需要先定规则（谁能踢人/改设置/审批），周期长；最坏：规则没定就上线 ⇒ 权限泄漏。
- **例子**：创建者离线时，普通成员只能读；管理员可改设置但不能解散——需要你确认。

## 3. #103 知识库授权 / 第四列用户切换

- **是什么/有什么用**：公共/内部/私密三层知识库在第四列按会话展示，用户可切换查看谁的知识。
- **现状**：三层存储与读矩阵代码已有，第四列三个授权勾选、用户切换/HNS 标识未做。
- **方案 A**：只读展示 + 明确标识层，不允许写。优点：安全、可先验收；缺点：用户不能自助授权。
- **方案 B**：连同写权限与用户切换一起做。优点：完整；缺点：默认值（群聊=会话；项目=会话+内部；联系人=会话；我的牛马=三层）需要你确认；最坏：默认勾错导致私密内容越权可见。
- **例子**：项目会话默认能读“内部”但不能读“私密”；切到其他在线用户时只显示对方公开层。

## 4. #109 多语言默认内容 / 自动校对

- **是什么/有什么用**：10 语言默认文案完整、无中文残留；自动发现翻译错误。
- **现状**：非中文语言包只剩品牌名/语言名/协议占位等有意保留的中文；自动校对未做。
- **方案 A**：离线一致性门禁（键齐全、非中文长句无中文、上限内）。优点：零成本、可 CI；缺点：不能判断语义好坏。
- **方案 B**：接模型逐条校对。优点：能发现语义错误；缺点：有 token 成本、可能改用户内容；最坏：模型把专有名词/协议词改坏。
- **例子**：俄语 `llm.toolRecallDesc` 引用了中文省略标记——这是协议原文，不应算残留。

## 5. #112-36/37 项目/群设置弹窗、右键分类（99 项）

- **是什么/有什么用**：项目/群的头像、名称、邀请二维码/链接、创建者服务商、旧邀请失效；右键菜单 99 项分类/拖动/折叠。
- **现状**：右键只有改名/置顶/通知/删除等少量项；无设置弹窗、无 99 项分类。
- **方案 A**：先做 10 个高频分类（文件、成员、网络、归档、通知、权限、外观、工具、诊断、危险操作）。优点：可用、可维护；缺点：不是 99 项全量。
- **方案 B**：按你给的 99 项清单逐项做。优点：完整；缺点：需要清单与交互定义；最坏：分类错乱、拖动丢配置。
- **例子**：右键项目 → “设置” → 改头像/名称（仅创建者）/邀请二维码/选择服务商；确认后旧邀请失效。

## 6. #113/#115 网络 B/A、飞书/钉钉双向、自动翻译

- **是什么/有什么用**：飞书/钉钉真正收消息；网络稳定名片 + 路由/在线/流式；自动翻译校对。
- **现状**：飞书 `faSong` 只返回 online，钉钉 client 未赋值——是空壳；其余按 #106/#108 依赖。
- **方案**：没有官方应用凭据/公网回调就只能做“接入向导 + 连通性检测”；有凭据才能真接。最坏：假装可用、用户发消息没人收到。
- **例子**：飞书需要 App ID/Secret + 事件订阅回调；钉钉需要机器人 Webhook/Stream 模式凭据。

## 7. A9 拟态运行时

- **是什么/有什么用**：桌宠可看屏幕、按动作模型触发动作、独立拟态记忆、音乐循环。
- **现状**：有桌宠窗口/形象/动作文件扫描；**屏幕观察与动作触发未实现**，但设置文案写了“可看屏幕/持续观察屏幕”。
- **方案 A**：去掉夸大文案，只保留窗口与形象。优点：诚实、零风险；缺点：功能少。
- **方案 B**：受控截屏（仅智能模式、明确开关、可随时关、只在本机处理）+ 动作触发。优点：功能完整；缺点：隐私与性能成本；最坏：未经同意截屏，属隐私事故。
- **例子**：用户说“看看我屏幕上这个报错”，桌宠截一张当前屏幕并回答；必须先在设置里显式开启。

## 8. A16 道同源

- **是什么/有什么用**：`docs/dao.md` 与运行时 `DAO_MOREN` 必须是同一份内容，否则用户改文档但实际注入旧稿。
- **现状**：两份文本不同源（docs 45KB，运行时默认约 7KB）。
- **方案 A**：以 `docs/dao.md` 为唯一源，构建时生成 `DAO_MOREN`。优点：不会再漂移；缺点：需要确认 docs 版本是否就是产品要的定稿。
- **方案 B**：保留两份，加一致性门禁。优点：改动小；缺点：仍要人工同步；最坏：门禁没覆盖的段落继续漂移。
- **例子**：构建时 `dao.md` → `dao-default.ts`，不一致直接红。
