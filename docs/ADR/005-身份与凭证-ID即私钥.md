# ADR 005 — 身份与凭证：ID 就是私钥，公钥才是给别人的东西

> 回答产品主的问题：**"55 位十进制换成'数字+字母、去掉 I/O/Z'是多少位？ID 当私钥、
> 公钥给别人，这样能不能在无中心服务器下做到准确识别、可恢复、唯一、可互相关联？"**
>
> 后续修订（产品主要求"字母全大写、不要小写"）：字母表改为**数字 + 大写字母**，
> 见下方第 1 节 —— 每符号信息量略降，长度相应从 45 增到 **51**，强度不变（仍是 256 bit）。

## 1. 位数换算（问题原样算一遍）

| 项 | 计算 |
| --- | --- |
| 字母表（**现行**） | 数字 10 + **大写**字母 26 = 36；去掉 I / O / Z ⇒ **33 个符号** |
| 每符号信息量 | log₂33 ≈ **5.044 bit** |
| 55 位十进制 | 10⁵⁵ ≈ 2^**182.7** |
| 只求"装下 182.7 bit" | 182.7 ÷ 5.044 ≈ 36.2 ⇒ **37 位** |
| 128 bit（最低可接受） | ⌈128 ÷ 5.044⌉ = **26 位** |
| **256 bit（Ed25519 种子标准）** | ⌈256 ÷ 5.044⌉ = **51 位** ← 本实现 |

**结论**：只求"装下 55 位十进制"是 **37 位**；但密码学上不该按这个量级设计，
256 bit 需要 **51 位**（本实现取 51，分组显示为 17 组 × 3，便于抄写核对）。

为什么不用那些"看起来更短"的方案（如实记录取舍）：
- 32/37 位（≈162–187 bit）够"装下 55 位十进制"，但**不够当密钥种子**：攻击者只要在可接受
  时间内枚举 2^162 就能反推私钥；256 bit 是业界标准（Ed25519 种子长度）。
- 去 I/O/Z 是为了避开"1/l/I、0/O、2/Z"这类**人眼抄错**；代价是每符号少 0.76 bit。
- **只保留大写**（本次修订）：抄写/朗读/电话报号不会因大小写歧义，输入法也不会改掉大小写；
  代价是每符号再少 0.76 bit（45 ⇒ 51 位补回来）。
- 不用 55 位十进制：每符号只带 3.32 bit，同样 256 bit 要写 **78 位**数字，抄写成本更高且无收益。

## 2. 身份模型（无中心服务器）

```
        私密（只在自己机器上）                     可公开（给别人的）
  ┌───────────────────────────┐            ┌──────────────────────────────┐
  │  凭证 / ID（45 位 base56） │  派生 ──▶  │  公钥（32 字节）→ 指纹（短标识）│
  │  = Ed25519 私钥种子        │  确定性     │  用于验签 / 比对 / 关联         │
  └───────────────────────────┘            └──────────────────────────────┘
```

| 产品要的 | 靠什么成立 | 边界（诚实说清） |
| --- | --- | --- |
| **唯一性** | 私钥空间 2²⁵⁶；生日碰撞在 10⁹ 设备量级约 2⁻²¹⁶ | 不保证"名字"唯一 —— 名字只是本地别名 |
| **识别** | 对方用公钥验签：签名只有持私钥者做得出来 | 首次相遇必须**比对指纹**（TOFU），否则中间人可以替换公钥 |
| **恢复** | 凭证 → 确定性派生 → 同一把密钥、同一个指纹 | **凭证本身就是密钥**：丢了没处找回（我们没有服务器替你存）；泄露 = 身份被完全接管 |
| **关联** | 联系人 / 群成员记录里存的是**公钥或指纹**，成员证书由群主密钥签名 | 成员变更要靠签名链；没有服务器就没有"全局目录"可查 |

### 由此定下的三条硬规则

1. **ID 只给本人看**：只在「我的」页显示 + 一键复制（复制即备份）。UI 上永远不显示私钥明文
   的第二份副本，导出备份**一律加密**。
2. **给出去的一律是公钥/指纹**：加好友、入群、二维码扫出来的都是公钥指纹，不是 ID。
3. **无中心服务器 ⇒ 没有"挂失"**：凭证泄露的补救只能是**换身份 + 通知联系人**（联系人侧
   记吊销），不存在"找回原身份"。这一点必须写在界面上，不能让用户以为可以像账号一样找回。

## 3. 与旧 ID 的关系

| 版本 | 形态 | 处理 |
| --- | --- | --- |
| 最早 | 9 位十进制 | **不再兼容**：空间只有 9×10⁸，与"身份不可伪造"直接冲突 |
| 上一版 | 17 位十进制 / UUIDv4 | **不再兼容**：它们**不是密钥种子**，"ID 即私钥"在它们身上不成立 |
| 过渡版 | 45 位 base56（含小写） | 只做**读取兼容**（已发出去的不能被判无效），新生成一律用现行格式 |
| **现行** | **51 位、数字+大写字母（去 I/O/Z）、256 bit** | ID 就是私钥；同一凭证可在任意设备恢复同一身份 |

**升级怎么做（不静默、不丢旧身份）**：
读配置时若发现 ID 是历史形态（9/17 位数字、UUID），本机会生成一把真凭证并记下原值
（`deviceIdUpgradedFrom`）；启动时再**按新凭证重建身份**，重建前**先备份旧身份文件**
（`identity.json.replaced-<时间戳>`），并写审计 `identity.credential.upgraded`。
因此升级后：ID 与身份**是同一把密钥**（产品承诺成立），旧身份文件仍在磁盘上可回滚。

## 4. 实现位置

- `packages/app-shell/src/credential.ts` — 字母表、编码/解码、分组格式、`keyPairFromCredential`（确定性派生）
- `packages/app-shell/src/settings-store.ts` — `generateDeviceId()` 产凭证、`isValidDeviceId()` 校验（45 位凭证 / 兼容 UUID / 17 位）
- `packages/app-shell/src/identity-store.ts` — `ensureIdentity(..., { credential })` 由凭证派生身份；
  `restoreFromCredential()` 换机/误删后按凭证找回（**替换前先备份旧身份文件**）
- IPC：`warmy:credential-info`（本机 ID 与分组展示）、`warmy:credential-restore`（恢复）
- 门禁：`verify-live-ui.mjs` 断言 ID 是 45 位凭证且**不含易混字符 I/O/Z**
