# ADR 001：手机端真实客户端 — 方案与接口设计

> **状态：提议（未实现）。** 本文只定义方案、边界与接口契约，**不含实现代码**。
> 起因：手机端 `packages/app-shell/mobile/` 目前是「外观预览」，其设置项不落盘、不与桌面端通信。
> 关联：ADR 000（多智能体群聊桌面应用定稿方案）的十一条不变量、L5 Shell 层、安全机制需求。

---

## 1. 现状事实（本文的前提，均可复核）

| 事实 | 证据 |
| :--- | :--- |
| 手机端 7 项设置（语言/主题/主题色/供应商/SMTP/通知开关/组网）**只改内存 `state`** | `mobile/app.js` 各 handler 只赋值后重渲染 |
| 手机端**没有任何**与桌面端的通信链路 | 全文搜 `fetch`/`XMLHttpRequest`/`WebSocket`/`ipcRenderer`/`postMessage`/`window.ccarmy` = 0 命中 |
| 桌面端**没有**任何面向手机的 HTTP / 静态资源服务 | `electron-main.ts` 搜 `createServer`/`http` = 0 命中；全仓仅 `sync-protocol` 的裸 TCP（`lan.ts:34`、`mesh.ts:176`） |
| 已有的 TCP 总线**不传输设置且无鉴权** | 协议为 JSON-lines 节点消息；收到一行 JSON 即 ACK 落盘 |
| 配对链路**只有生成端，没有接收端** | 桌面端能生成 `ccarmy://join?node=…&port=7788&tok=…` 与二维码；但主进程只注册了 `dsh-app`（`electron-main.ts:2065`），**无 `open-url` / `second-instance` 处理** |
| 「预览」是设计定位，不是缺陷 | `mobile/app.js` 文案：`'chat.systemNote': '手机端为外观预览；编排在桌面端完成。'`；`build-mobile.mjs` 注释：「直接双击就能在手机/浏览器打开」 |

**结论：要让手机端设置「真实有效」，需要的不是修 bug，而是新增一条真实的通信链路。** 本文即为该链路的接口契约。

---

## 2. 目标与非目标

**目标（本期）**
1. 手机端在**同一局域网**内成为桌面端的真实客户端：设置读写落盘、会话与看板真实数据。
2. 手机端做的每一次写操作都进入 `audit.jsonl`，可追溯。
3. 用令牌鉴权把「能看到/能改什么」限制清楚。

**非目标（明确不做）**
1. 不做真机发布、应用商店、移动端安装包；运行载体仍是浏览器。
2. 不做手机端自带 LLM 调用；模型与工具执行仍发生在桌面端。
3. 不做公网暴露；只面向可信局域网。

---

## 3. 必须继承的既有不变量（来自 ADR 000 §3.1）

- **#4 零原生模块** → 服务端只用 Node 内置 `http`，**不引入 express**。
- **#5/#6 JSONL 是唯一事实来源、写入者唯一** → 手机端改设置**必须**走既有 `SettingsStore`，不得另写一份存储。
- **audit 绝不上传** → 手机侧写操作**必须**落 `audit.jsonl`；且 `audit.jsonl` 本身**不得**通过任何手机端点回传。
- **#9 权限过滤先于相关性检索** → 手机端只能看到本机已授权的数据，过滤发生在服务端，**不在客户端**。

## 4. 架构选型

### 4.1 传输：Node 内置 `http` + SSE（而非 WebSocket）

- 设置读写是**请求-响应**；唯一的推送需求是「会话/看板变化」这类**单向**通知 —— SSE 足够，且比 WS 少一套握手、心跳与重连状态机。
- 不引第三方 Web 框架：符合零原生模块取向，也不增加供应链面。

**为什么不复用现有 TCP 总线**：它是面向**节点间**的自定义 JSON-lines 协议，且**无鉴权**（任何发来一行 JSON 的主机都会落盘）。把它直接暴露给浏览器等于新增一个未鉴权写入面。总线继续只做节点同步；手机链路单独一条。

### 4.2 代码落点：新建 `packages/app-shell/src/mobile-bridge.ts`

`electron-main.ts` 目前由**另一个并行开发者**在反复重写（单次提交改动 1117 行）。为把冲突面压到最小：

- 全部新逻辑放**新文件** `src/mobile-bridge.ts`（导出 `startMobileBridge()` / `stopMobileBridge()`）；
- `electron-main.ts` **只加接线**：应用就绪后 `startMobileBridge(...)`，退出前 `stopMobileBridge()`；注入的依赖为既有对象（`settingsStore`、`auditLogger`、`nodeReg` 等），不改其实现。

### 4.3 绑定策略

| 模式 | 绑定地址 | 令牌 | 用途 |
| :--- | :--- | :--- | :--- |
| 本机调试（默认） | `127.0.0.1` | 仍要求 | 桌面端自测、开发 |
| 局域网联机 | `0.0.0.0` | **强制** | 手机接入 |

**默认必须是 `127.0.0.1`**；绑 `0.0.0.0` 必须由用户在界面显式开启，且开启时给出风险提示。

## 5. 接口设计（核心契约）

### 5.1 鉴权与配对

复用既有实现，**不新造一套**：

- `createInvite(ttlMs, groupId)` / `consumeInvite(tok)`（`packages/sync-protocol/src/index.ts:122` / `:131`）
- 设备注册与撤销：`NodeRegistry`（`index.ts:37`）、IPC `ccarmy:nodes-pair`（`electron-main.ts:962`）、`ccarmy:nodes-revoke`（`:966`）

**流程**

```
桌面端  --ccarmy:invite-create-->  一次性邀请令牌（默认 15 分钟，一次性）
手机    --POST /api/pair {inviteToken}-->  { deviceToken, deviceId, expiresAt }
手机    --Authorization: Bearer <deviceToken>-->  其余所有端点
桌面端  --ccarmy:nodes-revoke-->  该 deviceToken 立即失效
```

**硬性要求**
1. `deviceToken` 由服务端 `crypto.randomBytes` 生成，**存 `safeStorage`**，不落明文。
2. `deviceToken` **只能**放在 `Authorization` 头，**禁止**放在 URL query（URL 会进历史记录、日志、Referer）。
3. 邀请令牌**一次性 + 有时效**，用后即废（沿用现有语义）。
4. 撤销必须**立即生效**（服务端查表，不依赖客户端配合）。

### 5.2 端点表

所有端点以 `/api` 为前缀。`写` 列标注是否需要在 `audit.jsonl` 留痕。

| 方法 | 路径 | 作用 | 复用的既有能力 | 写 | 权限 |
| :--- | :--- | :--- | :--- | :---: | :--- |
| `POST` | `/api/pair` | 邀请令牌换设备令牌 | `consumeInvite` + `NodeRegistry` | ✅ | 邀请令牌 |
| `GET` | `/api/info` | 设备名/版本/能力位 | `app.getVersion()` | ❌ | 设备令牌 |
| `GET` | `/api/sessions` | 会话列表 | 既有会话数据源 | ❌ | 设备令牌 |
| `GET` | `/api/sessions/:id/messages` | 会话消息 | 既有会话数据源 | ❌ | 设备令牌 |
| `GET` | `/api/board` | 看板（只读聚合） | 既有 `BoardStore` | ❌ | 设备令牌 |

| `POST` | `/api/smtp/verify` | 验证邮箱配置 | `ccarmy:smtp-verify`（`:1031`） | ✅ | 设备令牌 |

**设计约束**：手机端点一律是既有 IPC handler 的**薄封装**。业务规则**不得**在 `mobile-bridge.ts` 里重写一遍 —— 否则桌面端与手机端两份逻辑必然漂移。

### 5.3 类型契约（放入 `packages/contracts/src/index.ts`）

`packages/contracts` 是 ADR 000 里 P0 冻结的接口包，手机链路契约应并入其中（草案）：

```ts
/** 设备令牌（存 safeStorage，绝不回传明文给第三方） */
export interface DeviceToken { token: string; deviceId: string; label: string; expiresAt: number; }

/** 配对请求/响应 */
export interface PairRequest  { inviteToken: string; deviceLabel: string; }
export interface PairResponse { deviceToken: string; deviceId: string; expiresAt: number; }

/** 统一响应信封：手机端只需处理一种形状 */
export type ApiResult<T> =
  | { ok: true;  data: T }
  | { ok: false; code: ApiErrorCode; message: string };

export type ApiErrorCode =
  | 'UNAUTHORIZED'      // 令牌缺失/过期/已撤销
  | 'FORBIDDEN'         // 令牌有效但无该权限
  | 'BAD_REQUEST'       // 入参不合法
  | 'NOT_FOUND'
  | 'RATE_LIMITED'
  | 'INTERNAL';         // 细节只进主进程日志，不回传

/** 设置：与 SettingsStore 字段对齐，禁止另立命名 */
export interface SettingsPatch {
  locale?: string;
  themeMode?: 'light' | 'dark' | 'system';
  accent?: string;
  emailNotify?: { complete?: boolean; request?: boolean; error?: boolean };
}

/** SMTP：密码字段只进不出 */
export interface SmtpAccountView {
  id: string; label: string; host: string; port: number; secure: boolean;
  user: string; verified: boolean;      // 注意：没有 pass
}

/** SSE 事件 */
export type PushEvent =
  | { type: 'sessions.changed' }
  | { type: 'board.changed' }
  | { type: 'settings.changed'; settings: SettingsPatch };
```

### 5.4 错误模型

- 所有响应统一 `ApiResult<T>`；HTTP 状态码与 `code` 对应（401/403/400/404/429/500）。
- **`INTERNAL` 绝不回传堆栈、绝对路径、SQL、令牌片段**；细节只写主进程日志。
- 入参在**服务端**做运行时校验（TS 类型在 HTTP 边界不是约束）。

### 5.5 与桌面端 IPC 的映射（禁止重复实现）

| 手机端点 | 桌面端既有实现 | 关系 |
| :--- | :--- | :--- |
| `GET/PUT /api/settings` | `ccarmy:settings-get` / `settings-save` → `SettingsStore`（`settings-store.ts:183`） | 同一 store，同一写入者 |
| `PUT /api/providers` | `ccarmy:set-provider` | 薄封装 |
| `POST /api/smtp/verify` | `ccarmy:smtp-verify` | 薄封装 |
| `POST /api/mesh/toggle` | `ccarmy:mesh-start` / `mesh-stop` | 薄封装 |

## 6. 安全设计

**威胁模型（四类）**

1. **局域网同网段攻击者** —— 扫描端口后直接调用。
   → 除 `POST /api/pair` 外**全部**要求设备令牌；配对端点按 IP 限流；无有效邀请令牌一律 401。
2. **恶意网页（CSRF / DNS rebinding）** —— 用户浏览器里其它站点向本机端口发请求。
   → 强制校验 `Origin`/`Host` 白名单；令牌只走 `Authorization` 头（自定义头天然规避简单表单 CSRF）；**保守设置：默认拒绝无 `Origin` 的跨站写请求**。
3. **令牌泄漏** —— 令牌进了 URL/日志/截图。
   → 令牌不入 URL；界面上只显示设备名与后 4 位；随时可撤销。
4. **越权** —— 手机改到不该改的。
   → 端点按「只读/可写」分级；写端点一律进 `audit.jsonl`；**手机端不得直接触发工具/脚本执行审批**（那属于 L5 的 ApprovalDialog，只在桌面端）。

**额外硬性要求**
- SMTP 密码、模型供应商密钥**永不**通过任何端点回传（只回 `verified` 之类的派生状态）。
- 端口默认只绑 `127.0.0.1`；绑 `0.0.0.0` 需用户显式开启。
- `audit.jsonl` **不提供**任何读取端点。

## 7. 分期与验收标准

| 期 | 内容 | 验收标准（必须可量化） |
| :--- | :--- | :--- |
| **期 1（小）** | 只读端点（info/sessions/messages/board/settings/providers/smtp/mesh-status）+ 设置读写 | 手机改主题色 → **重启桌面端后值仍在**（持久化证明）；撤销令牌后所有请求 401 |
| **期 2（中）** | 配对流程 + SSE 推送 + 撤销 UI | 邀请令牌**用两次第二次必失败**；桌面端改设置后手机 2 秒内看到更新 |
| **期 3（大）** | 消息下发、与值班者对话 | **单独立项**：需先定权限、成本与「手机端能否触发工具」的边界，并复用 ADR 000 §2.3 的三级安全模式 |

## 8. 验证方案（怎么证明「真实有效」而不是又一次演示）

手机端此前的问题不是「功能弱」，而是「看似能改其实没存」。所以验收必须能证伪：

1. **端到端**：桌面端起服务，**第二个浏览器上下文**充当手机，走真实 HTTP；
2. **持久化证明**：手机改设置 → **杀掉并重启桌面端** → 重新读取，值仍在（这是"内存演示"与"真实生效"的分水岭）；
3. **越权证明**：不带令牌 / 令牌过期 / 已被撤销 → 均 401；只读端点收到写方法 → 405/403；
4. **审计证明**：手机侧每次写操作在 `audit.jsonl` 有对应记录，且记录里**不含**令牌与密码；
5. **不变量证明**：手机端改设置后，桌面端界面同步变化（证明是同一份 `SettingsStore`，没有第二份存储）。

## 9. 风险与未决问题

| 风险/未决 | 说明 | 倾向 |
| :--- | :--- | :--- |
| 与并行开发者冲突 | `electron-main.ts` 正被另一个 AI 反复重写 | 新文件承载逻辑，仅两行接线；实施前先确认对方已停 |

| 端点粒度 | 供应商密钥是「可写」但不可读，语义略绕 | 拆成 `PUT /api/providers/:id/secret` 写专用端点更清晰 |

## 10. 落地顺序（最小改动量排序）

1. `packages/contracts/src/index.ts` 增补 §5.3 类型（纯类型，零风险）；
2. 新建 `src/mobile-bridge.ts`：令牌表 + 鉴权中间件 + `/api/info`（只读，最小可验证闭环）；
3. 接 `settings-get/save` 两个端点，打通「持久化证明」；
4. 手机端 `mobile/app.js` 加统一 `api` 层，把 handler 从写 `state` 改为调 `api`；
5. 构建注入真实服务地址；配对 + SSE。
