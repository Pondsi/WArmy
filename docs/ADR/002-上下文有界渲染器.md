# ADR 002：上下文有界渲染器（不变量 #2）

> **状态：设计已定，实现待完成。**
> 关联：ADR 000 §3.1 不变量 #1（日志只追加）、#2（视图有界）、#3（写入侧压缩）、#5（JSONL 是唯一事实来源）；
> §3.2 L3 编排层；`packages/ccr-compressor`、`packages/memory-os`。

---

## 1. 为什么需要它（现状是"只有口号"）

ADR 000 的核心承诺是：**注入上下文有固定上限，但不丢失任何历史细节。**

但实现层面这条不变量目前**完全不成立**。唯一的"有界"痕迹是 `orchestrator.ts` 里 `buildStatusCard()` 在 1800 字处截断——那只作用于状态卡片，不作用于对话上下文。

真正的上下文组装点在 `packages/app-shell/src/electron-main.ts` 的 `warmy:chat-send`：

```ts
const hist = chatHistories.get(sessionId) || [];   // ← 全量历史，无上限
hist.push(userMsg);
const resp = await provider.chat({ model, messages: hist, maxTokens: 1024 });  // ← 日志直接当视图
```

**`messages: hist` 把"只追加日志"整段原样喂给模型**：日志越长，prompt 越长，成本与延迟线性上涨，最终撞上下文窗口。不变量 #2 要求的"上下文是日志的有界渲染视图，大小与日志总长解耦"没有任何实现。

## 2. 目标与非目标

**目标**
1. 注入给模型的上下文大小**恒 ≤ 预算**，与日志总长**解耦**（日志千万字，视图仍是同一量级）。
2. **不丢细节**：被挤出视图的部分以**可机器执行的指针**留在视图里，模型可据此取回逐字节原文。
3. 头尾稳定：系统提示冻结、近期对话逐字保留 —— 兼顾连贯性与 KV Cache 前缀稳定（不变量 #1 的意图）。

**非目标**
- 不改日志的只追加语义（日志永不重写）。
- 不用 LLM 做摘要（预算内零 LLM，沿用 ADR 对写入侧压缩的要求）。
- 不替换写入侧 CCR：CCR 管"单条内容太长"，本渲染器管"整体条数太多"，两者正交、串联使用。

## 3. 接口

新增 `packages/app-shell/src/context-renderer.ts`（纯函数、无副作用、可单测）：

```ts
export interface LogEntry {
  /** 日志内的单调序号（决定裁剪顺序） */
  seq: number;
  role: 'system' | 'user' | 'assistant';
  content: string;
  /** 记忆服务里的记录 id，供 retrieve 解引用；没有则用 seq */
  recordId?: string;
  ts?: number;
}

export interface RenderOptions {
  /** 视图总预算（字符）。与日志总长无关，这是"有界"的落点 */
  budgetChars: number;
  /** 头部逐字保留条数（系统提示等） */
  keepHead?: number;
  /** 尾部逐字保留条数（近期对话） */
  keepTail?: number;
  /** 被裁条目的压缩器，默认接 CcrGateway；纯函数，零 LLM */
  compress?: (entries: LogEntry[]) => string;
  /** 用于生成 recall 提示的查询串（一般取最近一条用户输入） */
  recallHint?: string;
}

export interface ElidedRange {
  fromSeq: number;
  toSeq: number;
  count: number;
  recordIds: string[];
}

export interface BoundedView {
  messages: Array<{ role: string; content: string }>;
  elided: ElidedRange[];
  stats: {
    logEntries: number;
    logBytes: number;
    viewBytes: number;
    budgetChars: number;
    pointers: number;
  };
}

export function renderBoundedView(entries: LogEntry[], opts: RenderOptions): BoundedView;
```

## 4. 算法

1. 头尾先占位：取前 `keepHead` 条与后 `keepTail` 条（默认 1 / 8），逐字保留。
2. 中间段（`head.length` … `len-tail.length`）为候选裁剪区。
3. 若"头 + 尾 + 指针模板"已超预算：优先缩 `keepTail`（下限 2），再缩 `keepHead`（下限 1）——**保证任何预算下都产出可用视图，而不是抛错**。
4. 中间段交 `compress()`（复用 `CcrGateway.beforeLog`）得到一段压缩文本。
5. 生成**指针消息**（role=`system`，不与真实对话混淆）：

   ```
   [已省略 37 条历史，seq 12..48，共 8,412 字]
   如需原文，可调用 recall("值班者状态机") 或 retrieve(recordId="m-1699999999") 取回逐字节内容。
   以下是被压缩的要点：
   <compress 的输出>
   ```
6. 在压缩文本仍超预算时，**截断压缩文本而不截断指针**——指针必须完整可执行。
7. 返回 `messages = [头...] + [指针] + [尾...]`，并统计 `viewBytes`。

**关键约束**：`viewBytes ≤ budgetChars` 必须在函数内**断言**，不是"大致如此"。这是本 ADR 唯一的硬指标。

## 5. 指针格式（为什么模型能用它取回原文）

指针必须同时给出三种冗余线索，任一可用即可解引用：
- **范围**：`seq from..to`（配合 `retrieve({seq})`，走 `sqlite:seq` 精确命中）
- **记录 id**：`recordId="m-…"`（配合 `retrieve({recordId})`）
- **语义线索**：`recallHint`（配合 `recall(query)`，走向量+fts 融合）

刻意**不把完整原文塞进指针**——否则视图又变成无界。

⚠️ 落地修订（§9.4 待办 3）：`recordId` 是**有界采样**（每段至多 8 个，段首 4 + 段尾 4），
完整覆盖不靠它，靠 `seq` 范围（`retrieve({seq})` 精确命中任意一条）与 `recall(语义线索)`。
指针文本里因此不再声称"还有 +N 个 id"，只列实际给出的那几个（"已省略 N 条"那行才是总数）。

## 7. 验证要求（"有界"必须可实测，不接受"看起来有界"）

1. **解耦曲线（核心证据）**：同一组参数下，日志从 10 条增长到 10,000 条，记录每次的 `logBytes` 与 `viewBytes`。
   验收：`logBytes` 单调上涨；**进入有界区后**（即日志已超过预算时）`viewBytes` 恒定 ≤ 预算、**方差为 0**。
   ⚠️ 限定条件（实测补充）：日志尚未超过预算时，视图必然等于日志、会随条数变化。所以验证必须让首行就进入有界区
   （用小预算或大条目），真机曲线里前几轮属于未越界区，属正常现象。
2. **不丢细节**：对被 elided 的每个 range，用 `retrieve({recordId})` / `recall(hint)` 能取回原文；取回的字节与写入时一致。
3. **头尾保真**：视图中**被保留下来的**头/尾条目必须逐字节等于原文、顺序一致。
   ⚠️ 口径补充（实现后修订）：条数**可能少于** `keepHead`/`keepTail` 的请求值——
   因为 §9.4 待办 1 已落地为「为压缩要点预留 `DIGEST_MIN_SHARE`(25%) 预算」，
   预算不够时尾部会被让出一部分给要点。断言的是"保留下来的那部分逐字节一致"，不是"必须有 8 条"。
4. **退化预算**：`budgetChars` 极小（如 200）时仍产出可用视图（不抛错、指针完整），只缩头尾。
5. **回归**：`spikes/verify-all` 仍 211/0；`chat-send` 在真实 Electron 里跑通一轮对话。
6. **观测**：metrics 里能看到 `viewBytes` 在长对话中保持恒定。
7. **指针对模型可用（§10.1 新增）**：mock 模型发起 `recall` → 宿主执行 → 结果回给模型 → 模型据结果再 `retrieve` → 终答，
   全链路逐字节可比对；最大轮数/总预算生效；`audit` 留痕且不含密钥；provider 不支持 tools 时优雅降级。
   验收：`node packages/app-shell/scripts/verify-tool-calls.mjs` 全 PASS。
8. **历史持久化（§10.3 新增）**：真 Electron 重启（同一 userData）后会话历史仍在，且与 `fast-memory.jsonl`
   逐字节一致；记忆服务不可用时对话仍能发。验收：`node packages/app-shell/scripts/verify-history-persist.mjs` 全 PASS。

## 8. 风险与未决

| 风险/未决 | 说明 | 倾向 |
| :--- | :--- | :--- |
| 指针被模型忽略 | 模型可能不主动 `recall` | 已缓解，未根除：§10.1 把 `recall/retrieve` 作为**工具**暴露给模型（工具描述写明"何时必须调用"），并在指针文本里点名这两个工具（"如本会话提供这两个工具，可直接调用"）。但"模型仍选择不调用"是模型行为，无法由宿主保证（更激进的 `tool_choice:'required'` 会强迫每次都要调用，代价是延迟与成本，暂不做） |
| 压缩质量 | CCR 是规则型、零 LLM，要点可能粗糙 | 先接受；要点质量是可迭代项，**有界性**才是本 ADR 的硬指标 |
| KV Cache | 尾部逐字保留 + 头部冻结，理论上不破坏前缀 | 需在 Spike 3（in-history）拿到 key 后一并实测命中率。补充：工具轮会把 tool 结果追加在尾部之后，前缀（头 + 指针 + 原尾部）仍然稳定 |
| 预算单位 | 现在用字符近似 token | 先字符，后续按模型 tokenizer 校正。补：工具结果预算也用字符（单条 4000 / 总 12000） |
| `chatHistories` 仍是内存 | 重启即丢，与"日志是唯一事实来源"有差距 | **已修**，见 §10.3（改为从 `fast-memory.jsonl` 重建；重建窗口有界，更早的历史靠指针 retrieve） |
| 工具结果可能"答非所问" | 记忆服务的 `retrieve` 是分级回退（exact→nearby→fuzzy），不存在的 seq 会返回**另一条**相近记录 | 已在工具结果里显式告警（"⚠ 这不是精确命中"），并把 `hitLevel` 写进审计；后续可考虑给 `retrieve` 加 `exactOnly` 开关 |

## 9. 落地记录（实测补充与后续待办）

### 9.1 预算默认值 = 4000 字符（理由）

1. 与写入侧 CCR 的单条预算同量级（`ccr-compressor.DEFAULT_BUDGET = 4000`），两侧串联不放大：单条先压到 4000，整段视图再限 4000；
2. 4000 字符按常见 BPE 折算约 1.5k–2.7k token，而 `chat-send` 的 `maxTokens=1024`，合计留在常见 8k 窗口内并给输出留余量；
3. 明显大于 `keepHead(1) + keepTail(8)` 的近期原文，保证"指针 + 要点"与近期原文能同时进同一视图。

**诚实标注**：本机无 tokenizer 词表，第 2 条是折算估计而非实测 token 数；§8 已声明"先字符，后续按 tokenizer 校正"。

### 9.2 单位口径（实测踩到的坑）

`viewBytes / logBytes / budgetChars` **统一按字符计**，不按 UTF-8 字节。否则中文按 3 字节算时，
`viewBytes ≤ budgetChars` 会被无声缩水到 1/3，硬指标就不再自洽。验证脚本同时输出两种口径便于换算。

### 9.3 已实测结论（真 Electron + 真记忆服务）

- 解耦：`budgetChars=4000` 下，日志 10 → 10,000 条，`logBytes` 5,120 → 5,120,000（1000×），`viewBytes` 恒为 4000。
- 不丢细节：`retrieve({recordId})` 56/56 逐字节一致；`retrieve({seq})` 3/3；`recall(hint)` → 卡片 → `retrieve` 5/5。
  （§10.2 把 `recordIds` 改为有界采样后，同一条断言的输入集从 56 变为 8：8/8 逐字节一致 —— 断言本身没放松，见 §10.2）
- 真实 24 轮对话：注入体积 730 → 3678 → 第 6 轮起恒 4000；`settingsSave({contextBudgetChars:600})` 后立刻降为 600 且指针完整。
  （§10.1 之后指针多了一句"如本会话提供这两个工具，可直接调用"，同一测试复测为 730 → 3678 → 第 9 轮起恒 4000，
  序列 `730,1467,2204,2941,3678,3256,3529,3806,4000,4000,…`——有界性不变，只是"进入有界区"的轮次右移）
- 值班者路径复用同一渲染器：200 条历史下 prompt 仅 7 条（1 系统 + 头 + 指针 + 尾）。
- 顺带修掉一个真实 bug：原 `id: m-${Date.now()}` 同毫秒重复，撞上 memory-os `records.id` 的 `UNIQUE + INSERT OR REPLACE`，
  会让 SQLite 投影覆盖前一条（JSONL 两条都在，但 `retrieve` 只能回到后者）。现 recordId 带单调后缀，且日志 `seq` 与记忆服务分配的 `seq` 对齐。

## 10. 待办 2/3/4 落地记录（本次实现）

### 10.1 待办 2：让指针对**模型**可用（`recall` / `retrieve` 作为工具）

**为什么之前不成立**：指针文本里写了 `retrieve(recordId=…)` / `recall(…)`，但 `chat-send` 调
`provider.chat({ model, messages, maxTokens })` 时**没传 `tools`** —— 模型看不到这两个函数，
"不丢细节"只对宿主（我们自己的 retrieval 层）成立。

**结构（三段，各司其职）**

| 层 | 文件 | 内容 |
| :--- | :--- | :--- |
| 协议 | `packages/providers/src/tools.ts` | `chatWithTools(provider, req, execute, opts)`：多轮循环、上限、收敛、降级；`providerSupportsTools()` + `PROTOCOL_TOOL_SUPPORT`（openai-compatible ✅ / anthropic ✅ / ollama ❌） |
| 契约与执行 | `packages/app-shell/src/memory-client.ts` | `memoryToolSpecs(labels)`（工具 schema + 何时用/入参/返回）、`runMemoryTool(client, call, {maxChars})`（走真记忆服务，**绝不抛错**） |
| 接线 | `packages/app-shell/src/electron-main.ts` `runChatLoop()` | 视图 + 工具 + 限额 + audit + metrics；`warmy:chat-send`、群值班者、`orchestrateGroupMessage` 三个注入点共用同一个入口 |

协议映射本来就在（openai 的 `tool_calls`/`tool` 消息、anthropic 的 `tool_use`/`tool_result`），本次补齐的是
**循环**与**能力判定**，并顺手修掉一个真 bug：anthropic 上一轮并行工具调用会产生**连续多条 `tool_result`**，
原先每条都单独成一条 user 消息 → API 直接 400（`messages: roles must alternate`）；现在合并成一条 user 消息。

**上限（三层，都在"有界"这一侧）**

- `contextToolMaxRounds`（默认 3，**0 = 不暴露工具**）：模型请求数上界 = `maxRounds + 1`
  （轮数/预算用尽时用 `tool_choice:'none'` **强制收敛**成文本答案，而不是把半截 tool_calls 交给调用方）；
- `contextToolResultChars`（默认 4000）：单条工具结果上限，超了写"被截断 + 原长度"；
- `contextToolTotalChars`（默认 12000）：一轮内工具结果**总量**上限，超了如实报 `stopReason='budget'`。

**降级链（任一环不满足 → 退回"现状"的普通单轮对话，不报错）**

1. 记忆服务不可用（`MemoryClient.isReady=false`，含启动失败/子进程退出）→ 不暴露工具；
2. `contextToolMaxRounds = 0` → 不暴露工具；
3. 协议不支持（Ollama）→ 循环内部降级为普通对话；
4. **首次**带 tools 的请求直接报错（中转/模型不吃 tools，如 HTTP 400）→ 撤回工具重试一次。

**审计（全程留痕，不落密钥）**：`chat.tools.decide` / `chat.tools.enabled` / `chat.tools.unavailable` /

- "不支持 tools"的判定是"协议表 + 首次失败重试"的启发式，不是对各厂 /models 的能力查询。

### 10.2 待办 3：`ElidedRange.recordIds` 有界采样

**问题**：`rangesOf()` 把段内**全部** recordId 堆进数组，指针文本里再做 `includes` 去重 —— 渲染的内存与文本代价
随日志条数线性放大（n=10000 时 1.9ms 尚可，n≈1e6 会很可观），而且这些 id 本来就是**冗余线索**。

**修法（接口不变）**：每段只保留 **8** 个 id（`MAX_RANGE_RECORD_IDS`，段首 4 + 段尾 4，段尾用定长环形缓冲）。
段首/段尾都取，是因为"最近的被省略条目"往往是模型最想要的。`ElidedRange.recordIds: string[]` 形状不变，
`fromSeq/toSeq/count` 依旧精确。指针文本里不再写"…+N"（那会暗示"还有 N 个 id"），只列实际给出的几个；
总数由 `[已省略 N 条，seq x..y，共 M 字]` 那行承担。

**诚实说明代价口径**：`rangesOf` 仍要扫描被省略区间（要算段边界与条数），所以**时间仍是 O(日志)**；
被消掉的是 O(日志) 的**内存**（id 数组）与指针膨胀。要把时间也做成 O(视图)，需要日志侧维护段索引/条数前缀和，
不在本次范围（下一次可做：`chatLogs` 按 key 维护"同段计数"增量结构）。

**实测**：`MAX_RANGE_RECORD_IDS=8`；1e4 条与 1e5 条日志列出的 id 总数都是 **8**（与日志长度解耦）；
1e5 条渲染 **65ms**、`viewBytes=4000`；段首/段尾 id 同时命中；`sum(toSeq-fromSeq+1) == sum(count)`（覆盖性不依赖采样）。

**验证脚本改动（诚实标注）**：`verify-context-renderer.mjs` 里**原有硬指标一条没放松**——
只是"每个 elided range 的 recordId 都能 retrieve 且逐字节一致"这条断言的输入集变小了
（`checked 56 → 8`，因为现在每段只列 8 个 id；断言本身仍是"列出的全部都要精确取回"，`idChecks === idExact`）。
另外**新增**了 5 条不变量断言（每段 ≤ 8 / 总数与日志长度解耦 / 覆盖性靠 seq 范围 / 段首段尾都命中 / 1e5 条仍可渲染）。

### 10.3 待办 4：`chatHistories` 迁到 `fast-memory.jsonl`

**之前**：`chatHistories` 是进程内数组，`chat-send` / 群消息各自往里 push，重启即丢（与不变量 #5 有差距）。

**现在（三件事）**

1. **唯一写入点**：`appendChatLog(key, entry)` 既追加 `chatLogs`（只追加日志），又派生 `chatHistories` 镜像。
   任何调用点都不再自己 push（历史 bug 的根因是"两处各自 push"）。`orchestrator.ts` 在拿到 `logOf` 时
   也不写 `history`（去掉第二份真相），状态卡片改为直接读日志。
2. **启动重建**：记忆服务就绪后 `restoreChatLogsFromMemory('boot')` 调 `memory.tail(400)`，
   按 seq 升序灌回 `chatLogs`（`kind='message'`），`chatLogSeq` 取 `max(seq)` —— 与 `nextChatSeq(memSeq)` 同一条序列，
   所以指针里的 `retrieve(seq=…)` 重启后依然精确命中。重建上限：**400 条 / 400k 字符**（常量在 `electron-main.ts`）。
3. **角色还原**：记忆服务的 SQLite 投影只有 `seq/id/session_id/kind/ts/body`（`tail()` 读投影，读不到 JSONL 上的额外字段），
   所以"这条是用户还是助手"只能从 **recordId 前缀**还原（`a-` = assistant，其余 = 用户消息）。
   这条约定写在 `memory-client.ts` 的 `CHAT_RECORD_PREFIX` / `chatRoleOfRecordId()`，属于**日志契约**的一部分。

**降级路径（必须有，且实测过）**：记忆服务不可用 → 跳过重建（`historyRestore = {done:true, ok:false, reason}`）、
不暴露工具、对话照常发送（进程内日志仍只追加）。`ensureMemoryReady()` 会在冷却 15s 后尝试重启记忆服务，
成功后自动补一次重建 —— 记忆服务"晚起"不会永久禁用工具。

**观测面**：IPC `warmy:chat-log`（回 `count/entries[{seq,role,chars,sha16,recordId}]/stats.restore`，**不回正文**）、
`warmy:chat-log-restore`（手动重建）、metrics 的 `viewBytes/logBytes`、audit 的 `chat.history.restore`。

**实测（`node packages/app-shell/scripts/verify-history-persist.mjs`，全 PASS）**

- 第 1 轮（真 Electron）：2 轮对话 → 4 条日志（seq 1..4），与 `fast-memory.jsonl` 的 4 条**逐条 sha256 相同**。
- 杀进程 → **同一 userData** 再起一次：`restore{entries:4, sessions:1, maxSeq:4}`，
  重建后的 `entries`（seq/角色/sha16/recordId）与重启前**全等**，且每条 sha16 等于 JSONL 正文的 sha256。
- 重启后继续对话：注入给 mock 模型的 prompt **逐字节包含重启前的全部 4 条 body**（4/4 匹配），
  注入体积 101 字符 ≤ 预算 1200；新增日志 `seq=5,6`（严格大于重启前 maxSeq），同样落在 JSONL 且 sha16 一致。
- 记忆服务坏掉（故意 exit 1 的子进程）：`chatSend` 仍 `ok:true` 且有回复、请求体无 tools、
  `restore.done=true/ok=false(memory-start-failed)`、进程内日志仍有 2 条、手动 `chatLogRestore()` 也如实失败不抛错。

**顺带修掉的两个"两份真相"（本次）**

1. **助手回复写记忆时被 `slice(0,4000)`**：日志里是全量、记忆里只有前 4000 字符 →
   `retrieve(recordId)` 对超长回复取不回尾巴（"不丢细节"名不副实）。现在两边同一份正文。
   实测：6009 字符的回复在日志与 `fast-memory.jsonl` 里逐字节一致（sha16 相同）。
2. **写不进记忆时仍给日志挂 `recordId`**：降级路径（记忆服务不可用）下会留下**死 id**，模型白跑一轮工具。
   现在只有 append 真的成功才挂 `recordId`（`seq` 与 `recall` 两种线索不受影响）。
   实测：坏记忆服务下日志条目的 `recordId` 全为 `null`。
   另：append 时同时把 `role` 写进 JSONL（投影查不到，先以前缀为准），为将来"读 JSONL 的 IPC"留字段。

**已知限制（下一步）**：重建窗口有界（`tail(400)`）——超出窗口的**旧会话**在重启后不会回到本地镜像
（内容不会丢：指针里的 seq/recordId 仍能 `retrieve`，但不能"接着那个会话聊"）。
根治要在 memory-os 加一个"按 sessionId 分页读 JSONL"的 IPC（本次**不能改 memory-os**，故未做）。
