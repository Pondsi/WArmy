## 2.2 R1：ID 位数 +3 能解决什么、不能解决什么

**能解决**：碰撞概率。9 位十进制 ≈ 10⁹，按生日悖论，约 4 万个设备时碰撞概率就很可观，10 万设备时几乎必然碰撞。加到 12 位 ≈ 10¹²，碰撞拐点推到约 120 万设备。

**不能解决**：
1. **唯一性不等于身份**。现在的 ID 是 HMAC 签名 + 格式校验，它只能证明"没被篡改"，不能证明"这个 ID 就是那台设备"。两个设备可以生成同一个 ID 而双方都"合法"。
2. 一旦引入 R2 的密钥对，**身份就应该是公钥指纹**，而不是这个短 ID。短 ID 只适合做**人读别名**（用户看到的编号）。

**建议**（成本几乎为 0，但别把它当安全边界）：
- 把短 ID 定位为**显示名/短码**，身份一律用**公钥指纹**（如 Ed25519 公钥的 base32 指纹，附校验位）；
- 短 ID 位数提到 12 位**可以接受**，同时加 **1 位校验位**（防手输错、防相近 ID 混淆）与**命名空间/实例前缀**（避免同一台机器上多个实例/多套安装撞车）；
- 真正要防重放/仿冒，靠 §2.3 的握手，不靠 ID。

## 2.3 R2/R3：握手与密钥体系（6 处修正）

你给的 `秘钥.txt` 结论是对的：**别自己从零实现密码学协议，用成熟的（TLS 1.3 / Noise）**。你的"非对称认证 + 临时对称密钥"正是 TLS 1.3 / Noise 的设计。但有 6 点要改：

1. **临时密钥的粒度是"每个连接"，不是"每条消息"**。"每次都重新生成"如果理解成每条消息都重握手，会带来巨大的延迟与 CPU 开销（而我们刚发现主进程空闲就吃 213% CPU，再加这个会雪上加霜）。正确做法：**每连接一次 ECDHE 握手**；长连接用 **KeyUpdate** 定期刷新（TLS 1.3 机制，即后向安全）。
2. **必须是 ECDHE（临时椭圆曲线 DH），不能用 RSA 密钥传输**。只有 ECDHE 才有前向保密；RSA 密钥交换已被 TLS 1.3 废弃。否则"即使私钥将来泄露也解不开过去的通信"这个承诺不成立。
3. **别手搓**。候选：`js-libp2p` 的 Noise（推荐，与你 R7 的 DHT 同栈）、Node 内置 `tls`（1.3）、或 `libsodium`。手写在 JS 里做对常数时间比较、随机数、nonce 管理几乎不可能不出错。
4. **身份签名密钥与密钥协商密钥分开**：推荐 **Ed25519 做身份/签名**（长期）+ **X25519 做 ECDH**（中期、可轮换）。一套密钥同时干两件事会放大泄露影响面。
5. **私钥必须进 OS 级保护**：项目已有 `safeStorage`；私钥不得明文落盘，能不可导出更好。**这条要做成硬约束**，否则前面所有加密都被一个文件泄露击穿。
6. **首次握手的信任锚你还没定**。这是最关键的一处空白：
   - 无 CA 的去中心化环境里，**"双方互相认证"必须有一方是权威**。你的架构里权威自然就是**项目主**。
   - 建议：项目主对外发布"群组身份公钥"，成员加入时由**项目主签发一张成员证书**（成员的签名公钥 + 权限 + 有效期 + 签名）。否则任何人都能自称成员。
   - 还需要：**吊销列表**（项目主签名的 revocation list，成员重连时同步）、**密钥轮换**、**重放防护**（nonce + 单调计数 + 时间戳容差）。
   - 单纯 TOFU（首次信任）在这种"会有异地陌生人加入"的场景**不够**。

## 2.4 R4：这不是"去中心化"

需求自己就写了"项目主下线项目就不能使用" —— **项目主就是单点故障**。这在拓扑上是 **星型（host-client）**，在信任上是 **自托管主权节点**。

**为什么必须把措辞改准确**：措辞会污染后续决策。如果团队相信这是"去中心化"，就会自然地认为"不应该有单点"、"任何节点都能读相同数据"，从而在数据模型上做出错误选择（例如上 CRDT/多主同步），而这些恰恰与本设计的目标相反。

**建议表述**：*"自托管主权节点 + 星型协作拓扑：每个项目由项目主机托管，数据主权在项目主，成员是经授权的客户端；项目主离线则协作面离线。"*

**必须明确"离线时本地还能做什么"**（否则用户体验就是"软件坏了"）：
- 本地 AI 对话、本地历史、本地仓库、本地看板 —— 这些应当继续可用；
- 界面上要明确显示"协作面离线，本地功能正常"，而不是一片灰。

## 2.5 R7：DHT 的边界与冲突

1. **DHT 解决"找到 IP"，不解决"连得上"**。家用宽带大量在 **CGNAT** 后面，既没有公网 IP 也无法接受入站连接。**DHT 查到对方 IP 之后仍然连不上** —— 这是 R7 与 R8 之间的关键缺口。
2. **公网 DHT 会暴露元数据**。参考文件建议"用群组密钥加密记录"是对的，但即使加密，**记录的存在与更新时机仍可被观察**（能推断"某处有活跃节点在发布"）。
3. **需要 bootstrap 节点**：DHT 不是无中生有，新节点要有引导入口。这与"无服务器"叙事有张力，建议明说"引导阶段依赖公共 bootstrap，之后自组织"。
4. **与 ADR 000 不变量 #4（零原生模块）可能冲突**：js-libp2p 的部分传输/加密实现用原生模块。**必须把组网放在独立子进程**（这也符合 ADR 已有的"记忆服务用捆绑 Node 子进程"模式）。顺带一句：**绝不能放在 Electron 主进程**——我刚写的卡顿报告说明主进程已经很脆弱，网络 IO + 密码学放进去会直接放大卡顿。

## 2.6 R8/R9：公网 IP 是最脆弱的一环，断链提示会抖动

**R8 的产品风险**：把"项目主有公网 IP"作为**前置条件**，等于把这产品限定给少数能拿到公网 IP 的人。这是整个方案里**最大的可用性风险**，比加密选型重要得多。

**建议至少提供一条降级路径**（按成本排序）：
1. **NAT 穿透**：UPnP / NAT-PMP / PCP 自动映射端口（对家庭路由器常有效，成本低）；
2. **打洞**：STUN + 双方同时打洞（对锥形 NAT 有效）；
3. **中继兜底**：TURN / 类似 DERP 的中继（必通，但不是"无服务器"，且占带宽）；
4. 明确文档化"什么网络环境下不可用"。

libp2p 的 `identify` + `autonat` 可以直接告诉你**本机是否可被外部拨入**，比自制"检测按钮"更可靠——建议"检测"直接复用 autonat 的结果。

**R9 的抖动问题**：网络抖动是常态，如果"一断就关组网"，用户会看到开关**反复自动开关**，比不关更让人困惑。建议：
- **迟滞判定**：连续 N 次心跳失败且持续 M 秒（例如 3 次 / 30 秒）才判定断链；
- **先提示后关闭**：断链时先出横幅 + 自动重试（指数退避），**只有重试若干轮仍失败才自动关组网**；
- **横幅合并**：R9（断链）与 R10（组网关但存在异地成员）本质上会同时发生，**不要弹两条**，用一条带状态的横幅；
- 横幅可手动关闭这一条要保持"关闭后不再重复弹同一原因，但状态变化要再弹"。

## 2.7 R13：SSH 隧道——与你的参考文件矛盾，且安全面极大

**矛盾**：`秘钥.txt` 第七节明确写"**不用 SSH 聊天**"，并推荐 QUIC / libp2p 取代。而 R13 要把 SSH 用在**仓库操作**上。这两者未必不能共存（传输层用 libp2p、仓库操作用 SSH 是常见组合），但**必须说清分工**，否则会出现两套并行的连接体系、两套密钥、两套审计。

**更大的问题是安全面**。R13 的表述是"项目主的仓库映射到每一个异地成员那里，异地成员对仓库进行直接操作"。如果这是**带 shell 的 SSH 访问**，等于：

- 任何一个成员都能在项目主机器上执行命令 → 可读走机器上的任何文件（包括私钥、其他项目）；
- 可直接删改仓库（含历史）→ 单点数据毁灭；
- 权限无法按目录细分（除非用很细的 forced-command + 受限 shell）。

**必须先决定的边界**：
- 是 **git-only**（强制命令，只允许 `git-upload-pack` / `git-receive-pack`，**无交互 shell**），还是给完整 shell？**强烈建议前者**；
- 每个成员**独立密钥**（可单独吊销），而不是共享一个；
- 仓库路径**白名单**，禁止 `..` 与符号链接逃逸；
- **全量审计**（谁在什么时候推/拉了哪个分支/哪个对象）；
- 明文写清：**仓库克隆 = 全部源码对每个成员完全透明**，机密性在"成员操作仓库"这个需求下**不可能成立**（除非上加密仓库，那是另一个大工程）。

## 2.10 建议的落地顺序（先能跑，再谈安全）

1. **先定三件事**：R4 措辞与定位、R13 是否 SSH、R8 是否接受"公网 IP 前置"（或给出 NAT 穿透优先级）。
2. **身份层**：Ed25519 身份密钥 + 指纹作为身份 + 私钥进 safeStorage（R2 的基础，也是 R7 的前提）。
3. **握手层**：在现有 `sync-protocol` 上接 Noise/TLS 1.3，**把裸 TCP 换成鉴权通道**（同时修掉"无鉴权"这个现存问题）。
4. **发现层**：DHT 发布加密记录 + `autonat` 式可拨入检测（R7/R8）。
5. **UI 层**：R8/R9/R10/R11/R12 的状态与横幅（注意 §2.6 的迟滞与合并；灰色要保持可读，沿用我们已立的对比度 ≥3.0 规则）。
6. **仓库层**：R13（若确定要走，先做 git-only forced-command 的最小可用版本，不要一上来给 shell）。
7. **补齐 A1–A9** 里你认可的部分。

| **D2 R8 公网 IP** | 不把公网 IP 当前置条件。做**连接阶梯**：公网直连 → 路由器自动映射（UPnP/NAT-PMP/PCP）→ 打洞（STUN）→ 中继兜底 → 全失败则保留**同 WiFi 局域网模式**并明确告知。**优先支持 IPv6**。"检测"复用 `autonat` 式探测。 |
| **D3 R13 SSH** | **只跑 git，无 shell**，安全优先；SSH 仅用于仓库。逐成员独立密钥、路径白名单、全量审计。 |
| **D4 A1 离线消息** | **排队补投**（成员上线后能收到离线期间的消息），并要求在安全、健壮、完善上做到位。<br>补充事实：**所有聊天记录本就全量存于本地**，所以"哪些消息发生在某成员离线期间"用游标记录即可，磁盘成本很低。<br>**每个成员也在自己机器上保存全量聊天记录。** |
| **D5 A2 备份** | **群聊不做快照**（成员各自全量即天然冗余）；**项目做快照**；且快照与既有「AI 执行任务时的检查点回退」**融合**。支持**一键导出整个群资产的备份**。<br>**仓库 = 该项目的全部资产**（全量聊天记录 + 成员信息 + 群配置 + 代码），不是纯代码仓库。<br>**硬规则：群的密钥等凭据不得写入仓库 —— 密钥是用户资产，不是该群的资产。** |

## 附一.1 上下线与心跳机制（本次新增的明确要求）

- **创建者下线** → 所有成员无法在群内活动（直到创建者回来）；
- **创建者上线** → **主动广播**告知成员（**不让成员定期轮询创建者**）；
- **成员上线** → **成员主动**通过 DHT 找到创建者并建立通道（**不由创建者轮询所有离线成员**）；
- **创建者定期检查在线成员** → 发现有人下线 → **告知其他成员**。

# 附二：对这些决定的评审（含必须补的项）

## C1（最关键）心跳方向必须服从连通性

"创建者定期检查所有在线成员"在 **NAT/CGNAT 下可能无法实现** —— 创建者往往**拨不进**成员（成员没有可入站地址）。若把"创建者主动巡检"当作唯一在线判据，在大量真实网络里会得到"全部离线"的假象。

**建议**：以**成员发起的持久连接自身的存活**作为在线判据（连接断了即离线），创建者只在**确实可拨入**（公网/已打洞）时才主动探测。成员侧保持轻量保活即可。这样既绕开 NAT 方向问题，也更省电——而"成员主动找创建者"本来就是你们已经定的方向，两者天然一致。

## C2 多副本 ≠ 多写入者

成员各自全量存储是对的，但它引入了**多个可写副本**的风险：同一条消息若两边都写，会出现"同一 seq 两条内容"。

**建议**：明确 **只有创建者能写正式历史**（单一写入者，呼应 ADR 000 不变量 #6）。成员本地输入先落为**本地待发**，经创建者确认后才转为正式日志；成员的历史副本是**只读**的。这样"全量副本"带来的只有好处（冗余与离线读取），不会引入分叉。

## C3 "广播上线"需要先知道收件人

创建者上线要广播，前提是：(a) 拿到成员名册（✅ 仓库里有成员信息）；(b) 逐个用 DHT 解析出当前地址；(c) 连得上。**对不可达的成员，广播必然失败**。

**建议**：明确这条退化路径 —— 对连不上的成员，退化为"该成员上线时反向发现创建者"，并在状态里区分"已通知"与"待其上线"。否则"广播"会被误以为一定能到达所有人。

## C4 "群聊不做快照"有一个隐含前提

成员各自全量 ⇒ 好处是天然冗余；但**灾难恢复需要一条"从任一成员重建"的路径**。若恢复只依赖创建者机器，那"不做快照"实际等于"没有恢复手段"。

**建议**：补上"从成员导出全量 → 重建项目"的能力（至少允许成员导出，再由用户手动合并/重建）。

## C5 检查点与快照融合，但要保留两套保留策略

融合方向是对的（同一套机制、同一套存储代码），但两者语义不同：

| | 检查点（checkpoint） | 快照（backup snapshot） |
| :--- | :--- | :--- |
| 粒度 | 细（每轮对话 + 文件状态） | 粗（整体） |
| 频率 | 高 | 低 |
| 生命周期 | 短（滚动淘汰，默认上限 50） | 长（保留 N 份长期） |
| 目的 | **回退某次任务** | **灾难恢复** |

**建议**：共用实现，但分**两个命名空间 + 两套保留策略**，否则高频检查点会挤掉/误删长期快照。

## C6 密钥不入仓库 ⇒ 必须补"身份恢复"路径（新增必需项）

既然密钥是**用户资产**、产品不代管，那么"密钥丢失 = 身份丢失"是用户自己承担的风险。但产品必须给出能力：

- 密钥**导出/导入**（或助记词形式）；
- **换机器迁移**流程（新机器导入密钥后，成员/联系人如何重新确认它的身份）；
- 明确的**引导与提醒**（因为不能替他保管，就更要把"请自行备份"讲清楚）。

## C7 仓库含全量聊天记录的两个后果（必须写进硬规则）

1. **体积随时间增长**：与"日志只追加"存在张力。需要归档/裁剪策略（例如把久远历史折叠为归档包，但**不得改写既有日志**——只能新增归档文件）。
2. **该仓库永远不能公开**：一公开就等于把**全量聊天记录 + 成员信息 + 群配置**一并泄露。建议把它写死为产品规则：项目仓库默认私有，且界面上不得提供"发布到公开仓库"。

## C8 新成员能读「加入之前」的历史吗？（必须现在定）

这条会决定群密钥体系，而且**前向保密与"新成员读全部历史"存在根本冲突**：

- 若要求**新成员能读全部历史** → 必须把历史密钥交给新成员（Signal 的 Megolm 会话密钥就是这么做的），代价是**部分牺牲前向保密**（拿到历史密钥的人能解密那段历史）；
- 若**只能读加入之后** → 密钥体系更干净（每次入群生成新一段会话密钥），前向保密完整，但新成员看不到过去。

**建议**：选**后者**（只能读加入之后的），并允许创建者**手动**把某段历史进行"定向分享"（明确的一次性动作，而不是默认全给）。理由：默认全给等于让"任何一次入群"都成为历史泄露的入口。

## 附三.1 C2 落地为「提案式协作」（PR 模型）

"本体唯一" + "成员可改本地副本" + "创建者 AI 审核"三者合起来，形态就是 GitHub 式 PR：

```
成员在自己副本上提交
  → push 到创建者仓库的【提案分支】（不是主分支）
    → 创建者的 AI 审核
      → 通过则并入主分支（本体变更）
        → 成员拉取更新（默认自动，可关闭；也可选择不下载仓库）
```

### 由此产生的三个必须定的点

1. **提案分支的权限**：成员**只能 push 到提案分支，不能 push 主分支**，否则"本体唯一写入者"被破坏。实现上用服务端限制（分支白名单 / 仅开放 `git-receive-pack` 到受限命名空间 / 拒绝非快进）。
2. ⚠️ **审核不得在被审核内容上执行代码（高危）**：成员推来的内容可能包含构建脚本、git hook、依赖安装指令。若创建者的 AI（或人）在创建者机器上"跑一下看看"，那就是**任意代码执行** —— 可读走私钥、可毁掉本体。**硬性要求：审核默认只读内容；确需执行时必须放在隔离环境（容器/沙箱/另一台机器），且不挂载本体仓库、不挂载身份私钥。**
3. **"不下载仓库"的成员，聊天记录从哪来**：仓库里含全量聊天记录，但成员可以选择不下载仓库 —— 二者需要澄清。**结论：聊天记录有两个载体** —— ① **每个成员本地的全量日志**（D4 已定，独立于仓库）② **本体（创建者仓库）里的一份**。不下载仓库的成员靠 ① 仍能聊天，只是看不到代码。

### 对上一轮我自己的表述做一处更正

我此前写"成员本地副本应只读"**不准确**。准确说法是：**成员本地副本可写**（成员要在上面改并本地提交），**但推送进本体必须经审核**；"只读"只适用于**本体那一侧**。

## 附三.2 C3 落地为「事件驱动 + 双向宣告」

- **上线** → ① 更新自己的 DHT 记录（宣告"我在线 + 当前地址"）② 对已知联系人/群成员尝试连线；
- **收到他人宣告** → 若对方在本群名册内 → 建立联系；
- **宣告失败即放弃，不做无限重试**：因为"每个节点上线都宣告"，发现是**事件驱动**的，两侧任一上线都会触发，所以**不存在遗漏**。

这比"创建者定期巡检"更好：省电、无需创建者拨入、且天然应对 IP 变化（IP 变了 = 重新宣告）。

## 附三.3 C6 的回答：更换身份凭证难不难？

**不难，但有一个前提必须先写进需求：只有「旧私钥还在手里」时才能平滑更换。** 分两条路径：

| 场景 | 其他人能否自动认出你 | 做法 |
| :--- | :--- | :--- |
| **主动轮换**（旧私钥尚在） | **能，可自动** | 用**旧私钥签名一条迁移声明**（旧公钥 → 新公钥 + 时间戳 + 原因），随 DHT 记录与群内记录传播；联系人/群用旧公钥验签后接受新公钥。同时用旧私钥签发"旧密钥作废"的**吊销声明** |
| **旧私钥已丢失** | **不能自证**，需要外部信任锚 | ① **群内**：由**创建者重签成员证书**即可恢复；② **点对点联系人**：只能**人工核对新指纹**（out-of-band 确认），无法自动 |

**两个必须明说给用户的固有代价**：

- 旧私钥一旦丢失，**无法吊销旧密钥** —— 拿到它的人理论上仍可冒充你。这是任何无服务器体系的固有代价，必须写进引导文案而不是藏起来；
- 换证后**历史消息仍可验证**，前提是**保留旧公钥**。所以设计上是「**保公钥、丢私钥**」，而不是把旧密钥整对删掉。

**落地要点**：需要一个"身份声明"的载体（放 DHT 记录 + 群内记录），以及联系人侧的**信任更新 UI**（"某某更换了身份凭证：指纹 A → 指纹 B，是否接受？"）。

## 附三.4 ⚠️ C7 的一个致命细节：git 历史会泄露

方向对，但**发布方式必须改**：

- ❌ **不能**把本体仓库 `push` 到公开仓库 —— 那会带上**全部历史**，包括曾经提交过的聊天记录、成员信息、甚至密钥。**哪怕现在已把它们从公开目录移走，历史里仍然有。**
- ✅ **正确做法**：把**公开目录导出为一个全新历史**（orphan branch 或新建仓库，只含该目录当前内容），再推送到公开位置。
- 并加**自动门禁**：导出前扫描公开目录，禁止出现聊天日志、成员名册、邮箱、密钥、本机绝对路径等模式；扫描不通过就拒绝发布。

## 附三.5 磁盘占用（对应"硬盘很贵"）

- 每成员一份整库副本 × 成员数，会随项目增长膨胀。措施：**浅克隆 / 按需拉取 / 不下载仓库**三档（用户已定，需在 UI 明确）；历史做**归档 + 压缩**，且**归档只新增文件、不得改写既有日志**。
- 检查点：滚动淘汰（保留最近 N 个），并对**内容相同的文件块去重**（否则每轮检查点都全量拷贝）。
- 快照：少量长期保留 + **增量**，而不是每次全量。

## 附四.1 本**取代**上一轮的以下结论（请以本轮为准）

| 上一轮记录（附三.1） | 本轮改为 |

## 附四.2 聊天记录的产生方式（本轮澄清）

- 成员的聊天记录是**随聊天出现在其界面上自然生成并记录在本地**的，**不是从仓库下载的**；
- 成员**可以清理**本地聊天记录以节约空间，**清理之后的聊天仍会继续生成并记录在本地**；
- 因此：**"不下载仓库"的成员照样能看到聊天记录**（靠本地界面记录）。

---

## 附四.3 由此必须补的四项

### ① 并发控制必须落到「锁 / 租约」，不能只靠口头指挥

"成员直接操作本体"意味着**多个成员会同时写同一个仓库**。这里有个容易被忽略的陷阱：

> **git 只能保护"已提交"的内容。** 两个成员同时改**同一个文件的工作区内容**时，git **看不到冲突**，后写者会静默覆盖先写者 —— 这不是可以靠"事后 merge"救回来的，因为丢失的那次改动从来没进过对象库。

所以值班者不能只是"指挥"，需要**可执行的仲裁机制**：给成员分配**任务 / 目录 / 文件级租约**（谁在什么范围内、什么时间窗内可以写），并在租约外拒绝写入。

### ② ⚠️ 高危：成员能写本体 ⇒ 必须禁止危险路径，否则"只跑 git"≠"无代码执行"

上一轮定的"SSH 只跑 git、无 shell"给了很强的安全感，但**通过 git 本身仍然可以执行代码**：

- 推送 `.git/hooks/*`（例如 `post-receive`）→ 在创建者机器上执行任意命令；
- 改 `.git/config`（例如 `core.hooksPath`）→ 指向任意脚本；
- 类似的还有 `.gitattributes` 触发的 filter/diff 驱动等。

**因此必须**：禁止/忽略 `hooks` 与 `config` 的写入、限制可推送的 ref、在服务端预接收钩子里做路径与内容校验。**否则"只跑 git 无 shell"这条防线是漏的。**

### ③ 审核环节消失了 —— 需要明确"还要不要审核"

- 上一轮定的是"创建者 AI **审核后**才并入本体"；
- 本轮是"成员**直接操作**本体"。

**二者冲突，必须三选一**：
- (a) 不审核，靠"租约 + 可回退（检查点/快照）"兜底；
- (b) 值班者兼审核闸门；
- (c) 保留创建者 AI 审核（回到上一轮）。

建议：无论选哪个，**都至少保留"可回退" + 危险路径限制**，因为成员已经有能力直接动本体。

### ④ 聊天记录的**权威副本只剩"本体"**，这会让 C4 的恢复能力变弱

成员本地是"界面自然产生 + 可清理"的缓存，所以：

- **C4（从成员副本恢复创建者记录）只在"该成员仍保留着那段记录"时才可行**；若成员都已清理过，就无法恢复；
- **建议**：**本体（创建者仓库）必须永不清理全量聊天记录**，成员本地才是可清理的缓存。否则"本体丢失 → 从成员恢复"这条路径会变成"看运气"。

---

## 附四.4 私钥的两个安全要点（本轮新增）

### ① 私钥放在设置界面 ⇒ 要把"物理暴露"说清楚

你定的是"私钥始终在程序的设置界面"。这与"高强度难破解"存在张力，必须明说：

> **算法再强，也挡不住别人直接复制存在你机器上的私钥。** 任何能看到你设置界面的人（或任何能读你磁盘的程序）都能拿走你的身份。

建议：默认**不显示明文**；导出走**二次确认**，并优先导出为**加密文件或助记词**；导出动作记入本地审计。

### ② 换证的主要动机是「泄漏」而非「丢失」⇒ 吊销是刚需，且必须防"被吊销者反声明"

你把重点放在"私钥被泄露所以要更换"，这比"丢失"更严格 —— 因为**攻击者手里也有旧私钥**，于是会出现劫持竞态：

- 你签发"旧密钥作废、新密钥生效"的声明；
- 攻击者用**同一把旧私钥**签一条更晚的声明，说"作废那条是假的，我现在又换了新密钥" → 联系人无法区分。

**对策：给身份密钥引入单调递增的代次（generation）。** 接收方**只接受代次更高的声明**，忽略代次相等或更低的。这样被吊销的旧密钥**无法反向声明**。

---

## 附四.5 一条实现要求：游标必须与日志分离

成员可以清理本地聊天记录，但仍在持续收新消息 ⇒ **`last_seen_seq` 这类同步游标必须与日志分开持久化**。
否则"清理日志"会连游标一起清掉 → 补投要么**重复**（重复收历史）要么**漏投**（把已清理段落当成已读）。

# 附五：最终决策（第四轮确认，设计冻结）

| 项 | 最终结论 |
| :--- | :--- |
| 并发控制 | 采纳**锁 / 租约**（任务 / 目录 / 文件级），值班者据租约仲裁；不靠口头指挥 |
| 本体安全 | 采纳：**禁止 / 忽略 `.git/hooks`、`.git/config` 等危险路径的写入**，限制可推 ref，服务端预接收钩子做路径校验 |
| **审核环节** | **不设审核闸门**，靠「**租约 + 可回退**（检查点 / 快照）」兜底 |
| 聊天记录 | **创建者（本体）不得清理全量聊天记录**；成员本地可清理（仅缓存） |
| 私钥保险 | 采纳：默认不显示明文、导出二次确认、优先加密文件/助记词、导出记审计 |
| 换证防劫持 | 采纳：**单调代次（generation）**，接收方只接受更高代次声明 |

## 附五.1 ⚠️「抢先换证」——失窃者无法自证，这是**天然不可解**的

你指出的这一点是对的，而且比我上一轮的描述更尖锐：

> **如果盗窃者先一步完成更换，失窃者就无法证明自己。**

### 为什么单调代次**救不了**这种情况（上一轮我讲得不完整，这里更正）

单调代次能防的是"旧密钥**反向**声明"（即攻击者在你之后发一条**更低或相等**代次的声明）。但**一旦攻击者抢先发了更高代次**：

- 联系人收到的是"用旧密钥正确签名 + 代次更高"的声明 → **完全合法**，只能接受；
- 你随后发的声明代次**更低** → 被规则**拒绝**；
- 结果：**代次机制反而把抢占结果锁死了。**

所以：**代次是"防回滚"的，不是"防抢占"的。单靠密码学，这件事无解** —— 因为无服务器体系里没有比私钥更高的权威，也没有"客服"可以介入。

### 能做的只有四层，全部是"减小窗口 / 减小影响 / 让它可见 / 兜底恢复"

**第一层：减少密钥被偷的可能（最有效）**

- **私钥必须加密存储**：用用户口令（或 OS 钥匙串 / 生物识别）解锁。**光偷到一个文件不足以换证** —— 这是投入产出比最高的一条；
- **绝不在设置界面明文显示私钥**（你已采纳）；
- 有条件时上**多设备确认**：换证需两台可信设备共同确认，单机被偷无法单独完成。

**第二层：让抢占"看得见"（把静默变响）**

- 任何换证都向**所有联系人与群**发出**醒目且不可忽略**的通知，附**旧指纹 → 新指纹**，并写明"若非本人操作请立即通过其他渠道联系"；
- 换证时间线记入本地审计与群记录，事后可重建；
- 这份通知必须在**多个渠道**同时可见（应用内 + 该联系人/该群的记录里），而不是一闪而过的 toast。

**第三层：把影响面切小（这一层最实际）**

- **不同用途用不同密钥**：身份签名密钥 / SSH 仓库访问密钥 / 传输密钥**分开**。攻击者拿到"身份"**不等于**拿到你的仓库读写权，而 SSH 密钥可以**由创建者单独吊销**；
- 创建者可以把"被盗用身份的那个成员"**移出群、重新签发成员资格**。

**第四层：兜底恢复 —— 这里星型拓扑反而成了安全资产**

| 场景 | 能否恢复 | 依靠什么 |
| :--- | :--- | :--- |
| **群内** | **能** | **创建者重签成员证书** —— 因为创建者认识你本人，也掌握群的名册。**这是你选的星型拓扑带来的真实好处**（纯 P2P 没有这个角色） |
| **点对点联系人** | **不能自动** | 只能**人工**通知对方"那个新指纹不是我"，靠 out-of-band 渠道 |

**结论**：这件事必须在**首次引导里明说**，而不是藏起来 —— 「身份凭证一旦泄露且被对方抢先更换，你**无法自动自证**；群内可由创建者恢复，点对点只能靠人工确认」。同时引导用户**开启私钥口令保护**，这是唯一真正有效的预防。

## 附五.2 设计冻结 → 落地顺序

至此 ADR 003 的需求与关键取舍已全部确认。落地按下面顺序（每步都能独立验证）：

1. **身份层**（最先，因为它是后续三件事的共同前提）
   - Ed25519 身份密钥对；**公钥指纹**作为身份（短 ID 降级为别名）；
   - **单调代次 generation**；私钥加密存储（口令/OS 钥匙串）+ `safeStorage`；
   - 首启引导：生成身份 → **备份凭证**（其他硬盘 / 打印 / 安全位置）+ **强制提醒口令保护**；
   - 换证流程（主动轮换）+ 换证声明的签名与传播格式。
2. **握手层**：在既有 `sync-protocol` 上接 Noise / TLS 1.3，把**裸 TCP 换成鉴权通道**（顺带修掉"无鉴权"这个现存问题）。
3. **发现层**：DHT 发布**加密**记录（公钥 ID → 地址）+ 双向宣告式上线 + `autonat` 式可拨入检测 + 连接阶梯（直连 / 映射 / 打洞 / 中继 / 局域网）。
4. **本体与协作层**：SSH（仅 git）+ 租约仲裁 + 危险路径禁令 + 提案/直接写入的具体形态 + 检查点/快照融合。
5. **UI 层**：组网开关与检测、断链横幅（迟滞 + 合并）、成员三态（在线 / 离线 / 组网关闭）、停用实例灰+删除线、**换证与恢复的引导与通知**。

# 附六：身份变更的联系人可见性（第五轮新增需求）

## 需求原文要点

- 群聊、项目、联系人**都由真实的人掌握**，所以**身份变更时这三处都要出现明显的横幅提示**，且**确保不被随意关闭**；
- 横幅要**附上他之前的旧的邮箱、手机号等联系方式**；
- **加入群 / 项目 / 联系人时，对方一定可以看到你的联系方式，不可隐藏**（但**可以不写**）；
- 目的：让熟人能**快速联系到本人**，确认不是盗用。

## 设计含义（由此产生的四条硬要求）

1. **身份 = 凭证 + 名片。** 身份里必须携带**联系资料**（邮箱 / 手机号 / 可选其它），与公钥指纹一起构成"身份名片"；**加入动作即交换名片**。
2. **"不可隐藏但可以不写"** ⇒ 字段可选，但界面**必须展示占位**（例如「未填写」），不能让对方以为"他隐藏了联系方式"——否则这条防线的意义就没了。
3. **"不被随意关闭" 需要定义关闭语义。** 建议：横幅**可折叠但保留常驻标记**，或**关闭需二次确认并记入审计**；且**下次启动/下次进入该会话时重新出现**，直到用户明确确认"已联系本人核实"。
4. ⚠️ **换证声明必须携带「旧名片的快照」** —— 否则换证之后旧邮箱/手机号就丢了，横幅**无法展示旧联系方式**，熟人也就无法对照。这是本需求带出的关键实现约束。

## 与「抢先换证」的关系

本需求正是 §附五.1 第二层（把静默抢占变为**可见**事件）的具体落地：横幅 + 旧联系方式 + 不可轻易关闭 = 给熟人一个**可执行的核实动作**。
注意：它**不能阻止**抢占（抢占本身不可解），但能让熟人**在损害扩大前发现**——这也是这个体系里唯一现实的防线。

# 附七：换证与联系方式的冻结机制（第六轮澄清，**更正附六**）

## 附七.1 更正：换证声明**不携带**联系方式

上一轮（附六）我定的"换证声明必须携带旧名片快照"—— **撤销**。正确设计是：

- 联系方式在**加入群 / 加入项目 / 添加联系人**时就交换，并**存在对方本机**；
- 发生换证时，横幅展示的"旧联系方式" = **接收方本机历史留存的那一份**，**不是**从声明里读的；
- 因此**声明里不放联系方式**（声明只含：旧公钥 → 新公钥 + 代次 + 时间戳 + 签名）。

### 为什么这个设计更好（关键，值得写进实现注释）

> **换证声明是"可能被攻击者控制的数据"** —— 密钥被偷后，声明是攻击者生成的。
> 如果横幅的"旧联系方式"来自声明，攻击者可以直接伪造一个"看起来正常的旧联系方式"。
> 而本机历史留存是**在对方被攻陷之前就存下的**，属于**攻击者无法篡改的信息**。

所以"从本机历史读旧联系方式"不是实现细节，而是这条防线的**信任根基**。

## 附七.2 新增机制：换证后 7 天联系信息冻结

| 规则 | 内容 |
| :--- | :--- |
| 对**换证者本人** | 换证后 **7 天内不得添加或修改**联系方式 |
| 对**接收方（本机）** | 收到换证通知后，**7 天内不得把该账号的联系方式更新为新的**，继续用本机历史留存值 |
| 起算点 | **从接收方收到通知的时刻起算**（**不得**使用声明里的时间戳 —— 那是可伪造的） |
| 例外 | **首次加入不受限**（否则新人根本填不了联系方式） |
| 判定位置 | 冻结状态由**每个接收方本地各自判定**，**不依赖任何人广播的"冻结中"标志**（那同样可伪造） |

**动机**：盗窃者可能在新设备上登录后换证，此时他提交的联系方式**可能是空的，也可能是错误的**（甚至是他自己的联系方式）。所以本机不能"跟着更新"，必须**保留之前存的那份**，熟人才能照着打过去核实。

## 附七.3 我补的四条（否则这个机制会被绕过）

1. ⚠️ **7 天到期后必须"人工确认"，不能自动采用新值。** 否则攻击者只要**等满 7 天就赢了** —— 冷却期只推迟了污染，没有形成门槛。界面上应把新值长期标为"待确认"，替换需用户手动确认。
2. ⚠️ **冻结必须绑定「人」而不是「指纹」。** 攻击者可以**换一个新指纹重新加入**（新指纹 = 新账号 → 没有历史联系方式，也没有冻结）。因此群/项目需要记录**身份变更链**（旧指纹 → 新指纹 → …），冻结与"历史联系方式"都绑定在**这条链**上，而不是单个指纹。
3. **横幅必须「旧 / 新并列」。** 只显示旧的看不出变化；只显示新的最危险（那正是攻击者想让你看的）。两者并列 + 标注差异 + 提示"请自行核实"。
4. **本机没有历史留存时必须如实说明。** 若你后来才入群、从未与该身份交换过名片，横幅要显示"**本机无历史联系方式**"，而不是留空 —— 否则用户会误以为"他故意隐藏了"（与"不可隐藏但可以不写"的原则冲突）。
