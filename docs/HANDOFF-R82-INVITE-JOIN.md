# 交接：#108/#112 邀请、加入审批、成员权限

## 是什么

- 项目/群聊右键「查看」弹窗新增：
  - 邀请链接（`warmy://join?...`）与本地二维码；
  - 最近 30 天加入申请，逐条「批准 / 拒绝」。
- 批准会调用 `groupStore.addMember` 真正写成员表；申请带 Ed25519 指纹时落 `zhiWen` 锚点。
- 新增底层 `yao-qing-anchor.ts`：Ed25519 签名邀请、SHA-256 指纹、过期/会话绑定/重放/角色越权真值表、审批幂等。

## 有什么用

- 创建者能把人拉进项目/群，并留下“谁批准的”记录；
- 加入申请不会只被删掉却不进成员表；
- 指纹锚点让后续成员证书/身份校验有依据；
- 角色真值表防止 viewer/member 越权发 admin/owner 邀请。

## 入口

- 第二列项目/群聊右键 →「查看」；
- 「邀请」区显示二维码与链接，可复制；
- 「加入申请」区逐条批准/拒绝。

## 数据与权限

- 邀请令牌由既有 `inviteCreate` 生成；当前 UI 二维码使用这个令牌；
- 加入申请结构：`{id, ming, kind, target, targetType, ts, expireAt, zhiWen?}`；
- 批准写 `groups.json` 成员表，并同步路由；拒绝只移除申请；
- `yao-qing-anchor.ts` 的签名邀请 token 已可独立生成/验证，但尚未替换 UI 的 `inviteCreate` 令牌。

## 方案与取舍

- 方案 A：只展示邀请，不做审批。  
  - 优点：简单；缺点：创建者仍要绕到别处加人。
- 方案 B（已采用 UI+审批）：二维码/链接 + 逐条审批 + 写成员表。  
  - 优点：闭环；缺点：签名邀请还没绑定真实身份私钥。
- 方案 C：签名邀请 token 全链路（生成→扫码→验证→证书）。  
  - 优点：防篡改/防冒充；缺点：身份层不导出私钥，需要受控签名接口与双端协议改造。

## 例子

- 创建者打开群「查看」→ 让对方扫码 → 对方提交申请 → 创建者点「批准」→ 成员表多一人；
- 成员点「批准」：如果 UI 没拦住，后端仍有角色/成员校验（申请只能由创建者处理）。

## 最坏情况

- 不校验邀请签名时，链接可被转发给任意人；批准前必须人工核对；
- 批准写成员表失败时申请不会被删除（当前实现先写成员再 splice），不会出现“申请没了、人也没进”；
- 指纹缺失时成员仍可加入，但没有证书锚点。

## 验收

- `verify-r82-invite` 20/0：签名/过期/换会话/重放/角色真值表；
- `verify-r82-r103` 真机：邀请令牌可创建、查看弹窗有二维码/审批入口、批准写成员表（静态+IPC）。
- 最终 fast 25 门禁 ×3 PASSED。

## 未完成 / 边界

- 签名邀请未绑定身份私钥（需要身份层提供受控签名接口）；
- 管理员角色 UI 只做到“创建者/成员”，admin 细粒度操作未全接；
- 真实扫码跨设备加入需要第二台设备/网络实测。
