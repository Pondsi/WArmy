## 一、P0：凭证与恢复（本轮新增）

### G1. 全新设备只输助记词无法恢复

- **是什么**：用户在新电脑/新系统上安装 WArmy，只有 24 词，没有旧设备的任何文件。
- **有什么用**：这是“换机/重装/旧机丢失”的唯一承诺；没有它，助记词只能在同一台机器上重新登录。
- **现状（实测）**：
  - `AuthService.recoverBegin()` 在 `vault.json` 不存在时直接返回 `no-account`（`auth-service.ts:489-491`）。
  - 旧 vault 存在时同一助记词可以恢复（`ok:true`）；错误助记词返回 `bad-mnemonic`。
  - UI 有“使用助记词登录”，但在新设备上必然失败。
- **为什么技术上可行**：助记词熵 = 种子；种子 → 51 位凭证 → 同一 Ed25519 私钥/指纹。
  新设备其实不需要旧 vault 的随机 salt 来**派生身份**；它只需要新建一个本地 vault 来保存新设备上的 PIN/自动登录。
- **方案**：
  - **A. 新增“新设备恢复”分支（推荐）**：
    1. 没有 vault 时也接受 24 词；
    2. `mnemonicToEntropy` → `credentialFromSeed` → `identityStore.restoreFromCredential`；
    3. 生成**新的**随机 salt + 主密钥，写新 vault（种子/助记词加密）；
    4. 让用户设 PIN 或自动登录；
    5. 显示指纹前缀，要求用户与旧设备/联系人卡片**带外核对**后再继续。
    - 优点：符合“无服务器、离线、只看助记词”；改动集中在 AuthService/首启 UI。
    - 缺点：无法恢复已换证（rotation）后的新密钥；输错但碰巧是合法 BIP-39 的短语会得到另一个身份；
      联系人/群/聊天仍为空。
    - 最坏：用户把一个“合法但错误”的助记词恢复成新身份，以为找回了旧账号；或攻击者拿到助记词后
      在自己设备上恢复并冒充。必须靠指纹核对 + 旧设备/联系人告警降低风险。
  - **B. 只允许“加密身份备份 + 口令”恢复**（已有 `importBackup` 协议）：
    - 优点：能恢复身份代次、退役公钥、名片历史；备份是口令加密文件。
    - 缺点：用户要保存两份东西；仍不含联系人/群/聊天；当前 UI 在助记词账号下被隐藏；
      且与助记词 vault 未同步（G5）。
    - 最坏：用户只保存了助记词、没保存备份 ⇒ 仍然恢复不了；备份口令弱 ⇒ 私钥泄露。
  - **C. 服务器账号恢复**：
    - 优点：体验最好，可同步联系人/历史。
    - 缺点：违背本地优先/无服务器；服务器成为根信任；要处理隐私、合规、被封禁。
    - 最坏：服务器被攻破 = 批量账号接管；服务器停运 = 所有人无法恢复。
- **需要你拍板**：是否做 A（推荐，先把“只输助记词”打通）？A 的指纹核对是否接受为强制步骤？
  B 是否作为“完整状态备份”的长期方案？C 是否明确不做？

### G2. 联系人、群、聊天记录、知识库不随身份恢复

- **是什么**：助记词只恢复密钥身份；本地数据仍在旧设备。
- **有什么用**：用户换机后最想恢复的其实是“我和谁聊过、群里有什么、知识库有什么”。
- **现状**：`groups.json`、`identity/peer-contacts.json`、`chat-logs/*.jsonl`、`knowledge/`、
  `settings.json`、`secure/keys.enc.json` 都是本机文件；没有任何导出/导入或同步入口（整份复制 profile 除外）。
- **方案**：
  - **A. 加密便携备份（推荐先做“可选导出”）**：联系人群组聊天知识库设置打包成口令加密文件；
    新设备恢复身份后可选导入；支持只选“联系人+群结构”或“连聊天记录”。
    - 优点：离线、端到端、不依赖服务器；用户自己掌握。
    - 缺点：文件可能很大；口令弱则全泄露；两台设备都改过时合并冲突；旧备份会过期。
    - 最坏：备份被偷 + 弱口令 ⇒ 全部聊天/联系人泄露；合并错误 ⇒ 覆盖新消息。
  - **B. 自建服务器/中继同步**：E2E 加密后多设备同步。
    - 优点：体验好、可多设备。
    - 缺点：服务器元数据、存储、冲突、密钥分发；不再是“无服务器”。
    - 最坏：服务器被攻破/停运；同步冲突导致消息丢失。
  - **C. 不迁移**：新设备重新加联系人/入群，旧记录留在旧设备。
    - 优点：最简单、最本地优先。
    - 缺点：换机体验差；用户容易以为“恢复了账号就什么都有”。
    - 最坏：用户漏掉关键联系人/群消息，以为对方没联系自己。
- **建议**：近期明确告知“只恢复身份，不恢复数据”；中期做 A 的可选加密备份；B 仅在你明确选择服务器时做。

### G3. 离线消息不排队、不自动重发

- **是什么**：对方不在线时，消息不会在服务器或本机持久队列里等对方上线。
- **有什么用**：这是“我发了他应该能收到”的基本预期。
- **现状**：
  - `chatNetSend` 只发给地址簿里当前 peer；没有 peer ⇒ `no-peers`；全部失败 ⇒ 会话只读（`hui-hua-chuan-shu.ts`）。
  - 没有持久化 outbox/自动重试/送达回执；界面只如实显示“未送达”。
  - FWArmy 中继有 30 秒内存队列，但客户端完整接入未完成（U3/G9）。
- **方案**：
  - **A. 本机持久化 outbox + 重试/回执（推荐先做）**：
    - 优点：无服务器；对方上线/地址更新后自动补发；可显示“已发送/已送达/已读”。
    - 缺点：发送方要保留消息与目标；地址变化/重装后仍可能失败；要防重复/乱序。
    - 最坏：outbox 无限增长；反复重试；没有回执却显示“已发送” ⇒ 虚假安心。
  - **B. 中继离线队列（TTL 可调）+ 客户端接入**：
    - 优点：收件人短暂离线也能收；服务器不存明文。
    - 缺点：服务器元数据；TTL/配额；仍需 E2E 与验签；客户端 UI 未做。
    - 最坏：服务器丢包/过期；用户以为送达。
  - **C. 保持现状，明确“未送达，请重发”**：
    - 优点：最诚实、零新风险。
    - 缺点：体验差；关键消息可能永远不到。
    - 最坏：用户以为发了，其实对方没收到。
- **建议**：A 先做（本地可验证），B 作为可选加速器；不要在没有回执时显示“已送达”。

### G4. 旧设备不会因为新设备恢复而失效

- **是什么**：同一助记词 = 同一私钥；旧设备仍然能登录、签名、读本地记录。
- **有什么用**：旧机丢失/送修/转卖时，用户希望“新设备恢复后旧设备失效”。
- **现状**：没有设备列表、远程下线、远程擦除；新设备改 PIN 不影响旧设备。
  代码里有换证/作废声明/7 天冻结/成员证书吊销，但没有完整 UI/传播；且换证会被助记词登录覆盖（G5）。
- **方案**：
  - **A. 保持“同私钥多设备”**：简单、恢复可用；缺点是无法注销旧设备；最坏是旧机被拿走即身份被拿走。
  - **B. 恢复时自动换证 + 作废旧密钥**：
    - 优点：对已更新声明的对端，旧密钥失效；符合“新设备接管”。
    - 缺点：指纹变化，所有联系人要重新核对；旧设备仍持有旧私钥和全部数据，
      对未更新声明的对端仍可冒充；当前会与助记词 vault 冲突。
    - 最坏：换证声明没传播到所有人 ⇒ 有人仍信旧设备；或联系人把新密钥当攻击者。
  - **C. 每设备独立密钥 + 账户主密钥签设备证书 + 设备列表/吊销**：
    - 优点：真正的多设备与远程注销；单设备丢失可单独吊销。
    - 缺点：协议/UI/同步工作量大；需要账户状态与吊销传播；实现错误会锁死用户。
    - 最坏：设备证书/吊销状态不同步 ⇒ 合法设备被拒或被盗设备仍可用。
- **建议**：先做 G1 后在恢复完成页明确“旧设备仍然有效，请手动退出/删除其配置”；
  B 作为中期；C 只在要做真正多设备时上。

### G5. 换证/备份导入与助记词 vault 不同步（已实测）

- **是什么**：身份层换证会生成新密钥；但 `auth/vault.json` 里仍保存旧种子/旧主密钥。
  下次用助记词或 PIN 登录时，`applyIdentity()` 发现“身份指纹 ≠ 助记词派生指纹”，
  会调用 `restoreFromCredential()` 把身份改回旧密钥。
- **有什么用**：如果以后开放“换证/切换身份”，这是数据一致性的底线；否则用户以为换了钥匙，实际下次登录又被换回去。
- **实测**：
  ```
  register fp0=XN5TE-... gen=1
  rotate    fp1=JK61K-... gen=2
  login after rotate: fpNow=XN5TE-... gen=1
  rotation was undone: true
  ```
- **方案**：
  - **A. 助记词账号下直接禁用换证/凭证轮换/身份导入（推荐立即做）**：UI 与 IPC 都拒绝，并说明原因；
    - 优点：零风险，避免静默回退；缺点：暂时没有换证能力。
  - **B. 原子同步**：换证时同时更新 vault（新密钥/新种子/新助记词或新包裹），并让旧助记词失效；
    - 优点：换证可用；缺点：用户必须重新抄新助记词，旧助记词不再是恢复凭证；改动大。
  - **C. 从助记词 + 代次确定性派生新密钥（BIP32 类）**：助记词能恢复所有代次；
    - 优点：最优雅；缺点：要改密钥派生与协议，旧身份迁移复杂。
  - **最坏**：A 不做而 UI 又开放 ⇒ 用户换证后被静默换回旧身份，联系人看到两个指纹，安全承诺失效。
- **建议**：立即 A；要做换证再上 B/C。

### G6. 入站消息不校验 session/from（可被已授权联系人跨会话注入）

- **是什么**：入站 `chuanShu` 帧只按 msgId 去重，然后直接写 `z.sessionId`；
  没有检查该 session 是否属于这个 peer，也没有比较 `z.from` 与握手得到的 `xiaoXi.peerFingerprint`。
- **有什么用**：防止“我知道你是联系人，但你不能把消息塞进我和别人的私聊/群”。
- **现状**：`electron-main.ts:8198-8208`；`z.from` 未使用；日志只记握手 peer（审计有），但会话归属未校验。
- **方案**：
  - **A. 严格绑定（推荐）**：只接受“握手指纹 = 该 session 的已知 peer/成员”的帧；
    忽略或拒绝 `z.from` 与握手指纹不一致的帧；拒绝时落审计，不写聊天日志。
    - 优点：改动小、立刻堵住；缺点：要维护 session→peer/成员映射（已有 groups/peer contacts）。
  - **B. 每会话通道密钥/MAC**：在握手后派生 per-session 密钥，帧带 MAC；
    - 优点：协议层更强；缺点：协议升级、兼容成本。
  - **C. 不改，依赖地址簿**：只允许已知 peer；缺点：已知 peer 仍可跨会话注入。
  - **最坏**：A 不做 ⇒ 一个已知联系人可以把“转账/删文件/错误指令”伪装成另一个会话里的对方消息；
    用户看到的是那个会话的名字/头像。
- **建议**：A 立即做，并补负向门禁（已知 peer 向未知 session 发帧必须被拒）。

### G7. “按名字添加联系人”没有指纹

- **是什么**：`createContactWithCard(ming)` 只往本地 `state.chats` / 联系人列表加一条名字，
  没有交换公钥/指纹，也没有建立可验证的 peer。
- **有什么用**：用户容易以为“加了联系人就能安全聊天”；实际上这条记录不能证明对方是谁。
- **方案**：
  - **A. 移除/改名为“本地草稿”**：明确不是安全联系人；真正加人走邀请链接/二维码/签名邀请。
  - **B. 加名字时必须绑定指纹**：输入/扫描指纹后才落库；缺点：多一步，名字本身无法验证。
  - **C. 保持现状**：最简单；最坏是未来有人把“名字”当信任依据，导致冒充。
- **建议**：A（推荐）或 B；不要把名字当身份。

### G8. 模型供应商 API Key 不随账号迁移

- **是什么**：Provider Key 存在 `secure/keys.enc.json`，用 OS safeStorage 包裹；不在助记词/vault 里。
- **有什么用**：用户换机后要重新填 Key；供应商只认 Key/它自己的账号。
- **方案**：
  - **A. 保持现状（推荐默认）**：最安全，Key 不进入任何备份；新设备重填。
  - **B. 纳入加密便携备份**：用户口令加密后可迁移；缺点：备份泄露即 Key 泄露。
  - **C. OAuth/设备码**：供应商侧授权，不落长期 Key；缺点：每家实现不同。
  - **最坏**：B 的备份被偷 ⇒ 模型费用被盗刷；A 的用户体验是重填。
- **建议**：A 默认；B 只作为“高级可选”，并在导出时逐项确认。

### G9. 中继客户端完整接入未完成

- **是什么**：FWArmy 服务端协议、E2E 信封、30 秒队列已有；客户端 UI/回执/去重/多服务器故障转移未完整接入。
- **有什么用**：双 CGNAT/无公网时仍能通信。
- **现状**：见 `docs/SERVER-RELAY.md` §5：客户端接入 UI、msgId/ts 去重、前向保密、群密钥分发未完成；
  客户端中继代码存在但未成为默认路径。
- **方案**：
  - **A. 先做局域网/公网直连**：改动小；双 CGNAT 不行。
  - **B. 完整接入中继**：公网可用；要补回执/重试/去重/多服务器。
  - **C. 用邮件/微信/文件异步通道**：无服务器；体验差、非实时。
  - **最坏**：只做半截中继 ⇒ 用户以为在线，消息丢；或服务器替换公钥做 MITM（需指纹核对）。
- **建议**：B 在 G1/G3 之后做；默认仍不要求服务器。

- 现状：邀请 token 支持 viewer，但成员表只有 creator/admin/member/external_member；UI 只给成员/管理员。
- 方案：A 不做；B 加 viewer（可看不可写/不可派活）；C member + kbPerms 模拟。
- 最坏：B 定义不清 ⇒ viewer 能发消息/改文件。**需要你定义只读边界。**

### U7. 签名名片 UI 入口

- 现状：主进程有 `identityMyCard` / `identityPeerCard`，界面没有“导出/导入签名名片”；离线签名邀请缺入口。
- 方案：A 二维码名片（容量/分片）；B 文件/粘贴 JSON（最稳）；C 局域网自动交换（离线不可用）。
- 最坏：没有入口 ⇒ 两个从没在线互连的人只能用不绑定人的通用链接。**需要你选 A/B/C。**

### U8. 真实微信 / 话筒 / 4K 物理屏验收

- 微信：真实扫码/收发/风控需要你的账号与手机；风险是平台风控/封号。
- 话筒：真实麦克风阵列/蓝牙耳机的增益、回声、断连需要物理设备。
- 4K/带鱼屏：盒模型已验证；没有物理屏，无法验系统缩放 150%/200% 的观感。
- **需要你提供测试账号/设备，或明确“不在本轮范围”。**

### U9. 工具执行的 OS 级隔离

- 现状（R93 已做）：文件工具统一路径判定；`run_shell` 静态扫描绝对/相对/环境变量/`cd`/编码命令。
- 残余：高度混淆、变量拼接、运行时生成路径、下载脚本再执行仍可能绕过字符串扫描。
- 方案：A 保持现状；B 容器执行；C 低权限账户/Job Object/sandbox-exec/seccomp。
- 最坏：A 下精心构造的命令能访问其他会话；B/C 配置错误导致正常命令跑不起来。**需要你选 A/B/C。**
