# 交接：#106 会话消息传输 / 发件箱 / 只读

## 是什么

新增 `packages/app-shell/src/hui-hua-chuan-shu.ts`：

- 会话消息帧：`{v:1, msgId, sessionId, from, ts, payload}`；
- AES-256-GCM 加密/解密（AAD 含 sessionId，防跨会话重放）；
- 发送侧同一 `msgId` 只发一次；接收侧按 msgId 去重；
- 每会话最多 5 个并发、单次 8 秒超时；
- 每个会话记住最近成功 ≤5 个 transport；失败第一次标记、第二次剔除，成功清失败；
- 全部失败 → 会话进入 **readonly**，后续发送直接拒绝并回调广播，不假装送达。

主进程新增 `warmy:chatNetSend`：从地址簿取 SecureMesh 对端，真实 `sendToHost`；入站 `group` 通道去重后写会话日志并广播。没有 peer 时返回 `{ok:true, sent:false, reason:'no-peers'}`。

## 有什么用

- 群聊消息可真正发到地址簿里的其它节点，而不是只在本机内存里；
- 重复点击/重试不会让对方收到两条；
- 网络全挂时界面能进入“只读”，不会让用户以为发出去了；
- 加密帧避免明文在局域网上裸奔。

## 入口

- 目前在内置群聊的发送路径自动调用 `chatNetSend`（`deliver()` 的 `kind === 'internal'`）；
- 没有单独的“网络发送”按钮，避免出现第二套发送路径。

## 数据与权限

- 对端列表来自 `PeerRegistry`（SecureMesh 地址簿）；只向已知/已握手对端发送；
- 入站消息来自 SecureMesh 的 `onInbound`，`peerFingerprint` 来自握手，不采信消息体自称；
- 不落盘明文消息到网络目录；会话日志仍走既有 `chatLogs/JSONL`。

## 方案与取舍

- 方案 A：只做 `HuiHuaLuYou` 纯逻辑（已有）。  
  - 优点：不碰网络；缺点：永远不真正送达。
- 方案 B（已采用底层）：加密帧 + 发件箱 + SecureMesh 发送/入站。  
  - 优点：真实局域网可用、有去重/超时/只读；缺点：还没有覆盖所有会话类型与多服务器扇出。
- 方案 C：完整 P2P/中继 + 外部联系人 + 多服务器扇出 + 双机实测。  
  - 优点：完整；缺点：需要第二台设备/公网环境与端到端验收。

## 例子

- 地址簿有一台对端：群聊发送 → SecureMesh 握手 → 对端 `onInbound` 去重 → 写会话日志；
- 地址簿为空：`chatNetSend` 返回 `no-peers`，本机照常跑本地编排，不显示“已送达”；
- 所有对端都超时：第 2 次失败后剔除，最终会话 readonly，后续发送直接拒绝。

## 最坏情况

- 没有第二台设备实测时，NAT/防火墙/名册可能让发送失败；代码会如实报错，不会假绿；
- 只接内置群聊，外部联系人/多服务器扇出仍可能只走本机；
- 入站消息以 `role:'them'` 写入，发送者身份目前只记审计指纹，没有在气泡上显示名字。

## 验收

- `verify-r82-chuan-shu` 16/0：加密/篡改、发送/接收去重、5 并发、超时、失败剔除、成功清失败、≤5 淘汰、全失败只读；
- `verify-r82-r103` 真机：无 peer 时 `no-peers`，不假装送达；
- 最终 fast 25 门禁 ×3 PASSED。

## 未完成 / 边界

- 真实双机/公网 E2E 需要第二台设备；
- 入站消息还未显示发送者显示名（只有审计指纹）。
