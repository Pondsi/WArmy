# 第一部分：需求与流程（它该怎么工作）

## 1. 一句话定位

**记忆系统 = 一份只追加的本机日志（唯一事实来源）+ 一层可以随时丢掉重建的检索投影 + 一个"有界视图"渲染器。**
它保证三件事：**不丢**（历史永远在日志里）、**有界**（喂给模型的上下文永远不超过预算）、**可解引用**（被挤出去的内容还能被取回来）。

## 2. 产品层面的硬要求（不变量）

| # | 要求 | 为什么 |
|---|---|---|
| 1 | **只追加**：日志写入后不修改（唯一例外是用户显式回退到检查点） | "我说过的话"不能被悄悄改写；崩溃不丢已写内容 |
| 2 | **整条请求有界**（第 44 轮后半改口径）：预算 = **所有发给模型的内容**，不是只夹历史视图 | 旧口径下"预算设 2 万"实际发的是"2 万 + 一整套系统提示 + 工具规格" ⇒ 承诺没兑现 |
| 2b | **原文进日志**：写入侧不许折叠丢内容（有界发生在**投影**与**视图**，不在写入） | 真缺陷：`beforeLog` 先折叠 ⇒ 超长中段永久消失，`retrieve` 拿回半截还"命中成功" |
| 3 | **绝不给空视图** | 真事故：预算缩太小把 6 条历史全省略、只剩一根指针 ⇒ 模型说"这是咱们对话的第一条消息"，用户以为它失忆 |
| 4 | **指针必须完整可执行** | 被省略的内容要靠指针取回；半截指针等于取不回。**假 id 比没 id 更坏**（归档锚点曾经写 `seq:N` 这种不存在的 recordId） |
| 5 | **JSONL 是唯一事实来源**，SQLite 只是投影 | 投影坏了可重建；投影与日志冲突时**以日志为准**（所以 `retrieve` 优先读 JSONL 原文） |
| 6 | **写入者唯一**（`duty` / `router` / `memory-service` / `executor`） | 多路写 = 双源 = 同一句话显示两遍 |
| 7 | **权限先于相关性** | 检索先在作用域内过滤（这个会话/这个项目），再谈排序 |
| 8 | **CCR 只压投影/镜像/工具结果**，不压日志原文 | 见 #2b；工具结果是运行噪声，用户说过的话不是 |
| 9 | **宁可如实说"不可用"，也不编造**：服务没起来、向量模型缺失、投影缺行，一律如实上报并降级 | 假成功比失败更糟；"预算足够但被算成 0"也是一种假失败 |
| 10 | **主进程与渲染进程零原生 `.node` 依赖** | 记忆服务的原生依赖（better-sqlite3）只活在独立子进程里 |
| 11 | **token 不许猜**：口径唯一，校准精确到 `供应商 / 模型 / 密度桶`；无回读用平均法，一次都没有用先验 | 同一个模型挂不同供应商分词可能不同；中文与代码的"真实/估算"比值差一大截，共用一个数会超窗或假装装不下 |

## 3. 一次对话里，记忆发生了什么（流程）

```mermaid
sequenceDiagram
    participant U as 用户
    participant M as 主进程
    participant C as CCR 压缩器
    participant J as JSONL（唯一事实来源）
    participant D as SQLite 投影
    participant R as 有界视图渲染器
    participant L as 模型

    U->>M: 发一条消息
    M->>J: append({id:'m-…', role:'user', ti: 完整原文})  ← 唯一写入点（写入侧不再折叠）
    J-->>M: 分配 seq（单调递增）
    M->>D: 同步投影（records/双 FTS/向量，只放 16K 索引预览）
    M->>M: 分段计价（固定开销+工具规格+本轮+图片）→ 整条预算减出「视图额度」
    M->>R: renderChatView(日志镜像, 视图额度)
    R-->>M: 有界视图（头1条 + 要点 + 尾8条 + 指针）
    M->>L: system(道/规矩/印象/门禁/身份/能力清单/知识库/归档摘要) + 视图
    L-->>M: 回复（可能先调 recall/retrieve 解引用；宿主也可前置召回）
    L-->>M: retrieve(seq=…) / recall("…") → **JSONL 原文**回灌（不是预览）
    L-->>M: 端点回传真实 prompt_tokens ⇒ 更新「供应商/模型/密度桶」的校准系数 + 记一条观测
    M->>J: append({id:'a-…', role:'assistant', ti: 全文，不截断})
    M-->>U: 展示（含思考过程；思考不进模型上下文）
```

**要点**：
- 日志写入在**发模型之前**（这样即使模型调用失败，用户那句话也已经落盘）。
- 工具结果**不进记忆**（只回模型，且有 4000/12000 字符限额）—— 记忆是"对话事实"，不是"运行噪声"。
- 助手回复**全文入库、不截断**（历史 bug 曾 `slice(0,4000)`，导致 retrieve 取不回尾巴）。
- 思考过程、系统小字、"本轮模型"这些**只给界面看**，永不进模型上下文。

## 4. 上下文不够用的时候怎么"记得住"

预算不够时，渲染器**不丢内容，只丢"逐字原文"**：把中间那段换成一段压缩要点 + **三种冗余线索的可执行指针**：

```
[省略 37 条 user/assistant，seq 11..48，共 8,412 字]
如需原文，可调用 retrieve(seq=11) / retrieve(recordId="m-1759…") / recall("<语义线索>") 取回原文。
```

- **seq 范围** → `retrieve({seq})` 精确命中（覆盖整段）
- **recordId 采样**（段首 4 + 段尾 4，最多 8 个）→ `retrieve({recordId})` 直取某条
- **语义线索** → `recall("…")` 语义/关键词召回

三种线索**故意冗余**：任何一条坏了，另外两条还能把内容取回来。

## 5. 归档与知识（长期记忆）

- 归档一个会话时，**不只是存一份摘要**，还要：抽取**实体/事件**进知识库、抽取**使用者偏好**（对"我"的长期认知）、生成**结构化摘要**（要点/决策/待办/风险）。
- 清理有明确上限（见 §13），不无限膨胀。

## 6. 优先级：谁的话最算数

`agents.md`（最高信念，用户可编辑）> 身份/模型/时间等 system 段 > **项目记忆**（项目规矩/目标，在值班者系统提示里）> 有界视图（对话历史）。

## 8. 写入路径（第 44 轮后半改口径：**原文进日志，折叠只发生在投影与镜像**）

```
用户消息：
  memory.append({id:'m-<ts>-<n>', sessionId, kind:'message', role:'user', ti: 完整原文})
  → 服务端 ++seq 落 JSONL（唯一事实来源，一字不丢）
  → 同步投影：records.ti / fts_uni / fts_tri 只放 **前 16000 字符的索引预览**（SUO_YIN_ZUI_DA_ZI）
  → 进程内镜像放 CCR 折叠预览（electron-main：beforeLog 只用于度量与镜像，不再决定落盘内容）
助手回复：同形状，role:'assistant'，**正文不截断**
工具结果：不进记忆（只回模型；受 4000 字/条、12000 字/轮限额 —— 这才是 CCR 该压的东西）
```

- **为什么不折叠了**：旧做法"CCR 压缩先于入日志"让超长的中段**永久消失**，`retrieve` 拿回来的就是半截，
  而且"命中成功"（第 44 轮后半用户 #7 点名的缺陷）。现在三层各司其职：
  **日志 = 不丢**、**投影 = 找得到（预览够索引）`、视图 = 装得下**。
- **`retrieve` 一律优先读 JSONL 原文**（`retrieveExact`：先 seq/id 命中 JSONL 索引，
  拿不到才退回投影，`via` 如实标 `sqlite:*-预览`）⇒ 不会"命中成功、内容半截"。
- **JSONL 索引增量维护**（用户 #8 的一半）：以前每次 `append` 把缓存置 null ⇒ 下一次 `retrieve`
  全文件重扫（6000 轮 × 2M 字符的日志上就是分钟级卡顿，还卡在用户等回复的路上）。
  现在 append 直接把新行的字节区间推进缓存；只有文件被外人改过（长度对不上）才重建。
- **角色还原契约**：SQLite 投影的 `tail()` **读不到** JSONL 里的额外字段，所以角色**只靠 recordId 前缀还原**（`a-…` = assistant，`m-…` = user；`memory-client.ts:510-522`）。重建历史时按前缀判定，不依赖投影。
- **seq 分配**：服务端 `meta.last_seq` 持久化计数（`index.ts:288,446`）；主进程用返回的 seq 对齐（`xiaYiLiaoTianXuLie(memSeq)`），服务不可用时退化为本地 +1。
- **去重**：同 `role + content` 且间隔 < 3 秒 ⇒ 跳过（同一句话有两条写入路径）；比的是**镜像里那份预览**（镜像存折叠预览），role 先归一成 `user`/`assistant`；recordId 带单调后缀，防同毫秒撞 UNIQUE id。
- **写入者白名单**：`duty | router | memory-service | executor`；**executor 写 `kind:'message'` 会被拒**（`index.ts:411-414`）—— 记忆里只有对话事实。
- **写入失败不挂 recordId**：宁可没有指针，也不要"指向不存在的记录"的假指针。**归档锚点同理**：
  以前 `session.summary` 的 anchors 写的是 `recordId: 'seq:N'` —— 一个**不存在的 id**，模型照抄只会取回空；现在用日志里真实的 `recordId`。

### 9.1 预算怎么算（第 44 轮后半改口径：**预算 = 所有发给模型的内容**）

```
第 1 步  窗口与 token 预算（youPeizhiSuanShangXiaWenYuSuan）
  百分比   = settings.contextBudgetPercent（默认 60%，夹 10..100；上限可到 100%）
             并不低于 minPercent = ceil(2048 / 模型窗口 × 100)，也**不低于实测固定开销折算的下限**
  tokens  = max(2048, round(百分比 × 模型窗口))，再被"给输出留位"压到 窗口 − 输出上限
  字符天花板 20,000,000（旧的 20 万上限会把滑杆 62%–100% 压成同一个点）
第 2 步  token → 字符：**按本轮真实文字的构成折算**（见 9.2），不再乘那个万能 1.6
第 3 步  分段计价（yuSuan-jiage.jiageQingQiu）
  固定开销 = 把 shenFenTou 各段按【标签】切开逐段量（道/规矩/印象/门禁/身份/人设/能力清单/知识库/归档摘要/最近5条原文…）
  工具规格 = 与发送侧同一个入口 zuJingGongJuGuiGe 的结果（两份逻辑迟早漂移，抽出来了）
  本轮输入 = 只算**另外 push** 的内部续派指令（用户那句话本身在视图里，算两遍就是双重计费）
  图片     = 视觉 token（⚠️ 尚未接入计价，属于用户 #5 的待办）
第 4 步  分配（fenPeiYuSuan）
  视图额度 = max(预算×(1−5%), 固定+工具+本轮+图片+视图最小512)  ← 下限：不许"假装装不下"
             再被 窗口×(1−5%) 封顶                        ← 上限：抬也不许越窗
  视图 chars = tokenDaoZiFu(视图额度, 本轮样本, 该模型该桶系数)   ← 渲染层仍以字符工作
  审计 chat.budget.allocated：每段多大、生效预算、走了哪级降级，当场可查
```

**两条边界都有真机红过，别退回单条**：只讲"预算 = 全部内容"而不抬下限 ⇒ 32K 窗口模型上视图被算成 0（看起来有界，实际让模型失忆）；只抬下限而不被窗口封顶 ⇒ 偷偷超发。窗口真装不下固定开销时如实报 `chuangKouBuGou`，界面显示「固定开销 ≈N tokens 已超过该模型窗口」（`ctx.budget.overWindow`），并走阶梯到**停止发送**。

### 9.2 token 不再靠猜（第 44 轮后半 · 用户 #9，`packages/app-shell/src/token-jiliang.ts`）

修之前同一份内容有**三套互不相干的系数**在数（预算侧 `×1.6`、看板兜底 `÷3`、记忆服务里那套是 bge 的 WordPiece）。现在：

| 环节 | 做法 |
|---|---|
| 发送前 | 分脚本**紧上界**估算（CJK 0.78 / 拉丁 0.30 / 数字 0.45 / 空白 0.35 / ASCII 标点 0.60 / 其它 1.30）× **该模型该桶的校准比值** × 安全垫（1.15 + 桶内残余散布，封顶 +0.35） |
| 系数存哪 | `userData/token-calibration.json`，键 = **`供应商 / 模型 / 密度桶`** 三段（换供应商、换模型、换文字形状都不许混用）；**首次用到时才读盘**（顶层读会撞 const 的暂时性死区 ⇒ 表永远空却装作已校准） |
| 发送后 | 只认端点**原生**用量（`source==='native'`；OpenAI 兼容流式必须显式 `stream_options.include_usage` 才有）⇒ 用**同一条请求的上界**做分母更新 EMA（步长 0.3、限幅 [0.25, 2.5]）。**分母不许用"已放行的量"**，否则系数自我复合、换一次文字形状就追不上（真机 24 轮里 7 轮超窗） |
| 一次回读都没有 | 用**先验** `YAN_XIAN`（0.90–0.95，按桶；`wuCha=0` ⇒ 不凭空加厚垫子）—— 仍比旧的"万能 1.6"准 |
| 部分模型有回读 | `@avg/桶` 平均法条目：取该桶内样本 ≥3 的模型均值，误差取"最坏相对平均的超出比例" ⇒ 借平均值时安全垫自动覆盖最坏情况 |
| 归档时 | 每次回读都追加 `userData/token-observations.jsonl`；生成会话摘要时 `zhongSuanXiaoZhun()` 按全量观测**离线重算**整张表（在线 EMA + 离线重算两条腿），重算失败只记审计、不许把摘要判成失败 |

## 10. 记忆服务本体（memory-os）

- **进程**：主进程 `fork(userData/memory-runtime/ipc.js)`，用**捆绑 Node**（`nodePath`），env 传 `WARMY_MEMORY_DIR`；
  启动超时 10 秒；**stdout/stderr 必须有人读**（不然管道写满 64KB 会把子进程卡死在写操作上，启动必超时）——读进**有界 12 行**缓冲，退出时写进启动日志，便于看崩溃原因。
- **协议**：`{id, op, …}` → `{id, …}`（child_process IPC）；方法：`append / tail / recall / recall_sync / retrieve / rebuild / vector_status / hydrate / stats / embed / shutdown`。单次调用 8 秒超时。
- **索引三通道**（RRF 融合，k=60）：
  | 通道 | 分词 | 擅长 |
  |---|---|---|
  | `fts_uni` | CJK 字符间插空格 → 单字索引（`unicode61`） | 1–2 字的短查询 |
  | `fts_tri` | trigram（≥3 字符才可查） | ASCII 标识符/错误码/路径、≥3 字 CJK 子串 |
  | `vector` | bge-small-zh-v1.5（ONNX int8, 512 维，纯 WASM） | 语义相近但用词不同 |
  - 向量**可选**：没有模型文件就跳过这一腿并**如实报因**；余弦下限 0.5（实测分界：真实语义查询 top1≈0.68、乱码≈0.447）；query 的 `[UNK]` 占比 > 0.5 也跳过（此时稠密向量不可信）。
- **权限先于相关性**：作用域先物化成 `TEMP` 表 `scope_filter_<fnv1a>`，三个通道都 `JOIN` 它。
- **fail-closed**：服务未就绪/不可用 ⇒ 工具返回**可读的说明文本**、绝不抛错；模型因此知道自己"取不到"，而不是被喂空数据。投影缺行时回读 JSONL 原文（`971-995`）。

### 13.5 知识库：结构、类型、怎么用（第 52 轮定稿）

**一个库 = 三份 JSON**（同一目录，按信任级分开存）：`knowledge-session.json` / `knowledge-internal.json` / `knowledge-private.json`。

**里面放两种东西**（都是结构化事实，不是对话流水）：

| 类型 | 字段 | 用途 |
|---|---|---|
| 实体 `Shiti` | id / kind / ming / attrs / eventIds / anchors / updatedAt | "东西是什么"。`kind` 七类：person 人、org 组织、material 资料、place 地点、concept 概念、tool 工具、project 项目 |
| 事件 `ZhishiShijian` | id / biaoTi / tool / method / result / expected / entityIds / anchors / ts | "发生过什么"：标题 + 用了什么工具 + 怎么做 + 结果 + 期望，挂在实体上 |
| 证据锚点 `anchors` | recordId + seq | 指回 `fast-memory.jsonl` 的**原文**（知识库只存事实，原文永远可以 retrieve 回来） |

**三层的语义**（唯一口径在 `zhi-shi-fen-ceng.ts` 的头注释）：

- **私密库 private** —— 不可公开的：用户本人的健康/财务法律/家庭身份/性向/宗教政治/生育/身份账户，以及**对人对事的评价**（"某人不可靠"这类）。
- **内部库 internal** —— 工作与业务：项目、报价、交付、供应商、打包部署，以及游戏娱乐等"非隐私但也非个人形象"的内容。
- **会话库 session** —— 可以对外公开的：与业务无关、非敏感、非个人特性的内容。牛马互通信封与外部渠道能看到的就是这一层。

**读的作用域**（`kbLayersFor`）：单聊/本牛马实例按 `privateKb` 开关决定能不能看私密层；项目群 = 内部 + 会话；外部群聊 = 只会话；联系人/未知会话 = 只会话。
**写的作用域**（`kbWriteLayers`）：与读分开判（能读不等于能写），实例可写三层、项目写内部+会话、外部群只写会话。

**第 52 轮加的两道机制**：

1. **写入口按内容升层**：模型/用户传来的 `layer` 只是"想放哪"，内容的敏感度决定"必须放哪" —— 两者取更严的那个
   （`kbWritable(sessionId, 想写的层, 内容)`）。判成私密却写不进私密层 ⇒ 直接拒，并如实说明"这条内容比本会话能写的层更敏感"。
   审计 `kb.layer-raised` / `kb-layer-denied`。（口径：判漏 = 泄露，升过头 = 群聊写不进任何工作话题 —— 所以业务判据只认硬标志。）
2. **内部库 → 会话库的脱敏概要**（新功能）：归档写完内部库后，从这批内容里**派生**一份可对外的概要写进会话库。
   概要**不是改写原文**，而是从 12 条**能力白名单**里挑条目（"我们可以做网页小游戏的开发与验收"这个级别）；
   挑不出就**整条抑制**。写之前必过确定性检查器四道关：白名单（逐条 + 剥离固定句式后不许残留一个字）、
   禁现形态（数字/金额/日期/路径/联系方式/存在性说法"做过·何时·怎么做"/专名指向）、哨兵 canary、长度 ≤240 字。
   过 ⇒ `kb.tumin-written`，不过 ⇒ `kb.tumin-suppressed` 并**不写**。
   为什么不靠"让模型改写一遍再打码"：摘要本身就是泄露面（成员推断、风格反推属性、被抹数字可重建），业界结论是降密要用
   **上下文之外的确定性检查器**（FlowSeal / IFC 的 no-read-up），只做 paraphrase 必然漏。

**归档后整理**（`zhi-shi-zheng-li.ts`）：同标题且内容实质相同 ⇒ 判重复，留最新；同标题不同内容 ⇒ 判前后矛盾，留新说法；
标题 >60 字或结果 >500 字 ⇒ 截断。只在真有改动时记 `kb.tidy`（含逐条理由）。空库、唯一条目库一律不动。

**模型怎么用**（注入里的触发器，第 40 轮起）：提到某人/某项目/某工具而上下文里没有来历、要对"以前定过的事"下结论、
需要结构化属性、或用户明确问"我们以前是不是说过" ⇒ 先 `knowledge_query`；命中就引用并写明来自知识库，
**没命中就如实说"知识库里没有这条"**，绝不拿猜测当事实；值得沉淀再 `knowledge_add`。

### 13.6 知识库的双时间（第 53 轮项 5）
每条知识带两个时刻：**记录时间**（这条信息什么时候被说出来 —— 写一次不再改，是"你什么时候告诉我的"那条轴）
与**发生时间**（事情本身发生在什么时候，**只有原文写了才填**，相对日期以说话时刻为锚）。
查询某个时间点时**两轴同时查**、命中轴标注出来并参与排序（调研：时间条件做成事后过滤会把 temporal 召回从 50% 打到 37.5%）；
发生时间缺失时明写"未记录：**不许拿记录时间顶替**"。旧说法被新说法**取代不删除**（打 shiXiaoTs），
派生的对外概要带血缘 yinZi ⇒ 源被取代则重算，重算不过一起退场。判据在纯模块 shi-jian-shuang.ts，门禁 verify-r53-shijian。

### 13.7 知识库可靠性三件套（第 53 轮项 4，纯模块 zhi-shi-ke-kao.ts）
1. **实体归一三层裁决**：同 kind 才比；person·org·project 是保护类型 ⇒ 只有归一后完全同名才自动合并，只是"很像"一律新建 + 交复核
   （kb.entity-review 留痕）。相似度 = bigram 重合系数 × √长度相近度（认得"简称⊂全称"，又不把 张三/张三丰 并成一个）。
2. **证据闸（evidence-before-belief）**：写**事件**前要么带锚点、要么是宿主派生来源、要么与**本轮用户原话**连续重合 ≥10 字，否则拒写
   （kb.evidence-denied）并给可执行补救。证据只比用户原话 —— 拿模型自己的输出当依据等于让猜测自我印证。
3. **陈旧降权不删除**：按**发生时间**算半衰期 90 天、下限 0.35；检索结果挂〔陈旧 N 天〕，含糊措辞挂〔待核〕。
   **命中轴相同**时陈旧度参与排序（三年前的旧事不许压过最近说法）；时间命中仍是第一关键字。
4. **写时去重与取代**：同层 + 同标题（忽略空白/大小写）+ 有共同实体 ⇒ 同内容 NOOP 不重复写（`kb.write-noop`）、
   异内容旧说法取代不删除（`kb.superseded-on-write`）、新说法带 `quDaiIds`（与 `yinZi` 的"我由谁派生"分开）。
   判据是确定性的（不调模型裁决），代价是只认"同标题"的冲突，跨标题的同义说法交给归档整理。
阈值与名单只住这一份（主进程再抄一份就是下一个不一致的源头）。门禁 verify-r53-zhishi（44 条 + 15 个变异全抓）。
## 14. 崩溃恢复（第 44 轮后半：**按会话分页**）

- 冷启动重建：库空而 JSONL 有 ⇒ 全量重建投影；恢复内存镜像走 `tailPerSession(每会话 120 条, 最近 60 个会话)`。
- **为什么不再用全局 `tail(400)`**（用户 #6）：按 seq 倒序取 400 条 ⇒ 一个高频会话能把整窗占满，
  **其它会话重启后直接失忆**（界面上消息还在，镜像里没有 ⇒ 模型看不到，用户也不知道要手动让它回忆）。
- 额度分配：单会话 ≤20 万字符、全局 ≤120 万字符，并且"还剩几个会话就分几份"、每会话至少保住 2 万字符；
  服务端不支持该 op 时**如实退回**全局 tail 并把 `fangShi` 写进 `chat.history.restore` 审计（不许静默降级）。
- 更早的历史**不常驻内存**，只能靠指针 `retrieve` 取（取回的是 JSONL 原文，不是预览）。
- 记忆服务崩了/起不来：**对话照常可用**（只是模型暂时没有解引用能力），并且启动日志里能查到子进程最后 12 行输出。

## 15. 相邻机制（同属"别忘事"的一族）

- **CCR 压缩**：现在只管三处 —— 工具结果（`tool_result`）、进程内镜像/视图侧、以及"这条有多大"的度量；
  **不再折叠日志原文**（见 §8）。规则型、零 LLM。
- **read-back 回读**：写后回读校验，不匹配**不许说"已保存"**。
- **资产治理**：会话产生的文件/附件按 project/session 检索（`zhuCeLiaoTianZiChan`）。
- **检查点回退**：全量快照 + 可 rollback 回写日志 —— 与"只追加"**存在张力**，属**显式例外**（用户主动回退才发生）。回退前备份 `fast-memory.jsonl.bak-<ts>`，回退后追加 `kind:'rollback'` 标记（含回退点 id / 时间 / 备份路径），全程持 `JsonlSuo`。
