### 动态块（按条件追加）

| 块 | 何时注入 | 预算处理 |
|---|---|---|
| **最近 5 条 user 原文** | 有用户消息时 | 预算不足时先压成“每条 120 字 + retrieve 指针” |
| **更早对话的归档摘要** | `autoSummary` 开启且有归档 | 份额随本轮预算自适应；装不下的归档条数如实写出并给 retrieve 指针 |
| **上一轮任务黑板摘要** | 同一会话、6 小时内、最近一个任务号 | 只对真实用户轮注入；续派轮不重复 |
| **当前时间戳** | 每轮 | epoch + UTC ISO + 用户 IANA 时区 |
| **图片附件** | 用户附了图 | 计入预算；最多 8 张、单张 6MB；预算不够先降分辨率（最长边 1024）再减张数 |

| **工具结果** | 模型调用工具后 | 单条上限 4000 字符、总量 12000 字符；超出给段首提示 + `offset` 分页 |

## 2. 预算怎么算（不是“拍脑袋”）

1. **窗口**：优先用模型真实 `contextWindow`；拿不到时从模型名解析 `128K/32k/1M`，再拿不到按 **128K**。
2. **预算比例**：设置里的“上下文预算”默认 **60%**（10%–100%）。预算 = 窗口 × 比例。
3. **先留输出**：**至少 2048 token**（窗口 4% 更大时取 4%），并受模型登记的官方输出上限约束；避免“输入塞满、模型说不出话”。
4. **再留安全垫**：窗口的 **2%**，防止 tokenizer 估算误差；分配时还有 5% 执行余量，空间实在不够时可让到 2%（只让一次，输出预留永不归零）。
5. **减固定开销**：产品门禁+道+术+要求+短记忆+印象+工具+教条+束缚+认知+身份+动态块，全部计入这条请求的预算（不是预算之外）。
6. **剩下的才是聊天视图额度**：`contextBudgetChars()` 把剩余 token 按**这段会话的真实文本**折算成字符（不再用万能 1.6），最小 4000 字符。
7. 如果用户把滑杆调得比“固定开销 + 视图下限”还低，**生效预算会抬到这个实测下限**；但绝不超过窗口。窗口连固定开销都装不下时，按降级链走到“停止发送”。

### 例子：128K 模型、60%

- 窗口 128,000 token；预算 76,800 token。
- 输出留位 ~2,048，安全垫 2,560 → 可用约 72,000 token。
- 固定层合计假设 8,000 token（道/术/要求/短记忆/工具等）→ 视图约 64,000 token，折算成中文字符大约 9–10 万字（按校准比值）。
- 结果：最近 5 条 user 原文、最近 10 条消息、很长的归档摘要、图片都能进；不会压任何提示词层。

## 3. 上下文“有余”时怎么处理？

**原则：不为了填满而堆料。** 固定层不会因为窗口大就重复注入；知识库/长期记忆也不会自动全塞。

有余时：

1. **最近 5 条 user 原文**原样保留（每条最多 500 字）。
2. **聊天视图**保留最近 10 条（头 2 + 尾 8）原文；中间更早的内容生成**较长**的摘要（摘要至少占视图预算的固定份额）。
3. **归档摘要**按预算拿到更大的份额：最近的逐条保留，更早的合并去重；不会因为“还有空间”就把 6000 轮全部展开。
4. **图片**不降分辨率、不减张数（上限内）。
5. **固定提示词层**原样全量注入，不压缩。

**例子**：新会话问“把这份 3000 字需求整理成计划”。窗口 128K、预算 60%：
- 注入：产品门禁 + 道 + 术 + 要求（若填了）+ 短记忆（若有）+ 印象 + 工具清单 + 认知 + 身份/时间 + 最近 5 条 user + 全部附件图片。
- 没有归档摘要/黑板（新会话），视图有大量余量 → 最近消息原样、摘要份额充足。
- 模型看到的是完整的规则与最近上下文，不会因为“窗口大”而收到重复的知识库内容。

## 4. 上下文“不够”时怎么处理？

降级顺序是**用户点名的顺序**（`yuSuan-jiage.ts` 的 `JIANG_JI`），不许随便挑一个压：

1. **最近 5 条 user 原文** → 压成每条 120 字 + `retrieve(seq=…)` / `recall("…")` 可执行指针。
2. **本轮用户消息本身** → 若它自己就吃光视图，也摘要（原文仍在日志/记忆库，可取回）。
3. **图片** → 先降分辨率（最长边 1024），再减张数（最多 8 张），并如实告诉用户哪几张没喂。
4. **收缩聊天视图** → 先缩尾、再缩头、最后才动指针；**永远至少给最后一条真实消息**，不允许只剩指针（真事故：模型说“这是第一条消息”）。
5. **压缩固定提示词层**（分层递进，先半极限 72%，再真极限 45%，段内至少 600 字）：
   - 第 1 层：软门禁/工具/**印象**
   - 第 2 层：身份/**认知**/**束缚**/**教条**
   - 第 3 层：**短记忆 → 要求 → 术**
   - **道与产品门禁永不动**；真装不下就停止发送并如实报原因，绝不偷偷超发。
6. **让出自己留的垫子**（只让一次）：安全垫 2%、输出预留退到地板，但**输出预留永远不归零**；让完仍不够才停止发送。
7. **停止发送**：给用户看“窗口装不下固定开销/道 + 必填层”，建议换更大窗口模型或删减提示词。

**例子 A：128K 模型、预算被调到 10%**
- 预算 12,800 token；固定层 8,000 + 本轮 3,000 → 视图只剩很少。
- 最近 5 条 user 被压成 120 字/条 + 指针；本轮若很长也被摘要；图片降分辨率；视图缩到最近 1–2 条。
- 道/产品门禁原样，术/要求/短记忆按层压；不会静默丢用户写的规则。
- 审计里能看到 `chat.fixed-compressed`（哪层、压到多少）与 `chat.view-budget`（视图额度）。

**例子 B：6000 轮长会话，窗口 128K**
- 最近 5 条 user 原文保留；最近 10 条消息保留；更早内容走归档摘要。
- 归档摘要按份额保留“最近 N 次归档”，更早的合并去重；没进摘要的条数如实写“未覆盖第 x–y 次归档”，并给 `retrieve` 指针。
- 模型需要细节时调用 `recall/retrieve`，而不是靠上下文里“记得”。

**例子 C：窗口只有 32K，但道 + 产品门禁 + 工具规格就超过窗口**
- 先把可压缩层压到真极限；把安全垫让到地板；仍装不下 → **停止发送**，并在界面/审计里说明“窗口装不下固定开销”，建议换模型或删减。
- 绝不把道截断、绝不偷偷超窗。

## 5. 短记忆与要求（第 92 轮新增）

- **要求**：第四列卡片，用户亲写；每会话一份、互相隔离；默认空；上限 2000 字；保存超限直接拒绝。
  - 注入位置：术之后、短记忆之前。
  - 模型只能读：产品硬门禁 E + 文件工具/`run_shell` 写入拦截；归档提示明确“不要输出对要求的修改建议”。
- **短记忆**：原「规范」；第四列不再显示、添加列表也没有；用户无法读写。
  - 只由**归档时从本会话有权读的知识库**按使用频率补入（`useCount>0` 且不在短记忆中的条目，次数降序最多 10 条）；每会话上限 2000 字，超出**按使用频率从低到高**丢（同频再比最后使用时间/先后），旧内容已进知识库，可 recall 取回。
  - 频率放 `guifan/<sid>.freq.json` 侧车，正文不写频率标记。
  - 注入位置：要求之后、印象之前；压缩时最先于要求、术被压。

## 6. 一句话总结

- **有余**：固定层全量、最近原文与图片全留、归档摘要变长；不堆知识库。
- **不够**：先摘要最近 5 条 → 本轮 → 图片降级 → 缩视图 → 分层压提示词（短记忆→要求→术→教条/束缚/认知→印象/工具/软门禁）→ 让垫子 → 停止发送；道与产品门禁永不动。
