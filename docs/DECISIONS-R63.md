## 1. `write_file` 整篇覆盖既有文件：要不要收紧？

### 1.1 它现在的实际行为（先纠正一个容易误解的点）

模型写文件时默认「整篇覆盖」，`append:true` 才是追加。宿主**已经有一道防护**（`fuGaiDiuGao`，在所有轮生效）：

- 只针对**本任务账本里写过**、且旧文件 ≥200 字的路径；
- 如果这次没带 `append`/`overwrite`，而且新内容**比旧内容短**，或与旧内容**重合率 <15%**（像是接在后面的下一段），宿主**不执行**，并在工具结果里告诉模型：续写带 `append:true`、局部改用 `edit_file`、确实整篇替换带 `overwrite:true`。

所以现在不是「完全没有防护」，而是还剩两个口子：

1. **模型可以自己带 `overwrite:true`**：宿主不核对用户原话，模型自己声明「我要重写」就能绕过；
2. 账本对不上（压缩/重启/路径写法变化）或旧文件 <200 字时，这道闸可能不触发；而且 `overwrite:true` 放行时**没有额外的告知/审计**。

真机 live 出现过一次（不是每次）：小说文件 5609 字 → 1751 字 → 107 字，前文被抹掉，模型没意识到，最后另存了一份「完整版」。这正是要补的口子。

### 1.2 方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 保持现状** | 已有闸；模型可自带 `overwrite:true` 绕过 | 不打断；零改动 | 模型仍可悄悄截断前文；live 偶发红 |
| **B. 现状 + 覆盖留痕** | 每次 `overwrite:true` 覆盖本任务写过的文件，工具结果和审计里写明「此前 N 字 → 本次 M 字」；丢失超过一半时在聊天里提示 | 不打断；用户/门禁看得见 | 文件已经丢了，只是事后知道 |
| **C. 核对用户原话** | `overwrite:true` 只有在用户原话明确说「重写/覆盖/改成/缩成…」时才放行，否则拒绝并说明 | 防模型自授权；不需要用户点卡 | 原话识别可能误判；模型要多一轮 |
| **D. 破坏性覆盖弹卡（建议）** | 保留现有闸；`overwrite:true` 且新内容 **< 旧内容 50%** 或删除 **>1000 字** 时弹一张确认卡；用户同意才写，拒绝则保持原文件；其它覆盖只留痕 | 真正会丢前文的操作由人把关；正常重写不受影响 | 无人值守的定时任务会停下来等卡；需要卡片超时策略 |
| **E. 扩大闸的覆盖面** | 把「跨重启/账本对不上/<200 字」也纳入，并覆盖 `copy_file` 等同类工具 | 减少漏网 | 实现复杂；可能误拦合法操作 |

### 1.3 例子

- 模型写小说，先写 5609 字，下一段只发 107 字却没带 `append`：现有闸会拦住（如果账本命中）；D 还会要求确认，前文保住。
- 用户明确说「把这篇 5000 字报告缩成一句话」：D 直接按用户意图放行，不弹卡；C 也能从原话识别。
- 用户没提重写，模型自己决定「重写一版更短的」：D 弹卡；用户拒绝后模型只能改用 `edit_file` 或追加。
- 定时任务凌晨自动改文件：D 弹卡没人点 ⇒ 任务停在等待，超时后如实报「需要你确认覆盖」；这比静默丢前文安全。

### 1.4 最坏情况

- A：某次长文任务前文被抹掉，用户只能靠备份/重新生成。
- B：用户事后才知道丢了内容，仍要恢复。
- C：用户原话识别误判，合法重写被拒，多花几轮。
- D：无人值守任务被卡住；需要定「等多久、超时算拒绝还是保持原文件」。
- E：误拦合法操作，或实现引入新的路径匹配 bug。

### 1.5 建议

**D（现状 + 破坏性覆盖弹卡 + 始终留痕）**：保留已有的短/不重合拦截；只在「丢一半以上或删超过 1000 字」时让人确认；其它覆盖写清楚「此前 N 字 → 本次 M 字」并记审计。无人值守时默认**不覆盖**，超时后在会话里如实报告。

**你可以怎么回**：`1 = A / B / C / D / E`（可加一句：无人值守时「默认不覆盖」还是「默认放行」）。

## 2. P0-6 脱敏体系：还剩五个边界

### 2.0 它是什么（一句话）

内部知识库 → 会话可见的概要，不能直接抄原文；只能从「能力白名单」里挑短语，再由宿主做五道确定性检查，并且同一件事至少有两个独立来源（k=2）才允许出现。目的是：让牛马记得「你会做什么」，但说不出「你给谁做过什么」。

### 2.1 模型新增白名单短语，要不要人工确认？

现状：模型可以通过 `capability_propose` 提案；宿主校验（≤14 字、无数字/标点/对象名、1–6 个关键词、总数 ≤32）后直接落盘；**没有人工确认界面**。

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 保持自动（现状）** | 零打扰；模型能适应新领域 | 白名单可能被逐步放宽；用户看不见 |
| **B. 每条都弹卡确认** | 人完全掌控 | 频繁打断；用户容易无脑点同意 |
| **C. 先进待审区，人工批准后才生效** | 不打断当前任务；有把关 | 新能力要等审批；多一套 UI |
| **D. 自动生效 + 审计可见 + 一键撤销 + 定期复核（建议）** | 不打断；至少可追溯、可撤销 | 发现问题前可能已经输出过一次 |

**例子**：模型提案「住院记录」。A/D 会直接可用；如果两个来源都提到住院，概要可能出现「近期住院」。B/C 会先问你。

**最坏**：A 下模型把白名单堆到很宽，某个敏感能力组合被写进会话库，而你完全没看见。D 至少会在审计里留痕、可撤销，但泄漏可能发生在复核之前；如果你要「宁可少说也不冒险」，应选 C。

**建议**：日常用 **D**；如果你把隐私看得比顺滑更重要，选 **C**。

**你可以怎么回**：`2.1 = A / B / C / D`。

### 2.2 历史会话库要不要一次性重扫？

- **是什么**：升级前写进会话库的旧条目，没有经过现在的检查器。
- **选项**：A 不扫（现状）；B 先 dry-run 出报告，再替换不合格条目（建议）；C 直接全量替换。
- **优点**：B 能先看到会影响多少条、哪些类型，再决定；**缺点**：要跑一段时间，可能大量旧概要被清空。
- **最坏**：不扫 ⇒ 旧泄漏一直留着；直接全量替换 ⇒ 历史概要大面积消失，牛马「忘事」。

**建议**：**B（先 dry-run 报告，再执行）**。

**你可以怎么回**：`2.2 = A / B / C`。

### 2.3 canary 红队要不要进 live 档？

- **是什么**：故意植入一个假值（例如「用户有一艘叫××的船」），走完整归档链路，检查它有没有出现在会话库/群聊可见层。
- **现状**：fast 档已有可执行探针；live 档没跑。
- **选项**：A 不加；B 加一条 canary 到 live（建议）；C 每次发版人工跑。
- **优点**：B 能抓端到端泄漏（真实模型、真实归档）；**缺点**：live 多几十秒到几分钟。
- **最坏**：不加 ⇒ 只在单元层证明「检查器能挡」，证明不了「整条链路真的没漏」。

**建议**：**B**。

**你可以怎么回**：`2.3 = A / B / C`。

### 2.4 受众分档（群内可见 / 可导出对外）

- **是什么**：会话库再分两层：群内可见的概要可以稍具体；可导出/对外的概要更泛化。
- **优点**：对外分享时更安全；**缺点**：要改层语义、归档管线、UI，改动面大。
- **最坏**：不做 ⇒ 一份概要同时给群友和外部导出用，边界靠自觉；做错 ⇒ 两层内容不一致，牛马「两套记忆」。

**建议**：**暂缓**，等有真实「导出给外部」需求再做。

**你可以怎么回**：`2.4 = 现在做 / 暂缓`。

### 2.5 概要 TTL（多久不用就退场）

- **是什么**：概要有有效期，久不更新自动消失。
- **优点**：减少陈旧敏感信息；**缺点**：用户会觉得「牛马忘了」。
- **最坏**：TTL 太短 ⇒ 刚建立的理解消失；没有 TTL ⇒ 三年前的敏感概要还在。

**建议**：**暂缓**；如果做，只对敏感能力设 180 天，且退场前在审计里留一条。

**你可以怎么回**：`2.5 = 暂缓 / 180 天 / 其它天数`。
