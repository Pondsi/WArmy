## 二、本轮新增的开放问题

### R100-2. 项目（群聊）停止的真实 E2E

- **是什么**：单聊停止已真机验证；项目停止本轮加了
  `isStopped` + `qunZhiXingZhe`（停止时逐个中止正在跑的执行者），但**没有用真实项目 + 多执行者跑过**。
- **为什么没做**：需要一个已创建的项目、至少两个执行者、以及一个会跑较久的任务；本轮没有构造。
- **需要你/可选方案**：
  - A（当前）：`warmy:tingZhiDuiHua` 对项目 id 置停止标志，编排器 `isStopped` 不再派新执行者，
    `qunZhiXingZhe` 里登记的执行者逐个 abort + 世代 +1。
  - B：加一个 mock 编排器门禁（假执行者 sleep 10s），不依赖真实项目，验证“停止后不再派/在跑的被执行者被 abort”。
  - C：你创建一个真实项目，我远程/按你的步骤跑一次。
- **例子**：项目里让值班者派 2 个执行者各写 5 段长文；第 1 个执行者开始后点停止；
  预期：第 2 个不再起跑，第 1 个在 1–2 秒内停，界面出现“已停止”，之后不再有新执行者。
- **最坏情况**：A 可能漏掉“执行者已起跑但还没登记到 `qunZhiXingZhe`”的极窄竞态；
  B 需要写假编排器；C 需要你花时间。
- **默认**：A + B（下一轮补 mock 门禁）。

### R100-3. 停止后上游仍在生成/计费

- **是什么**：`AbortController` 只停止我们这边的 HTTP 消费；供应商可能已经生成完并在计费。
- **为什么没做**：主流 OpenAI-compatible 端点没有统一的“取消这次生成”API；只能做到“本地立刻停 +
  晚到结果丢弃 + 不再发下一次请求”。
- **可选方案**：
  - A（当前）：abort + 世代 + 丢弃晚到结果；界面/日志都不再消费。
  - B：给支持取消的供应商（如部分 Anthropic/OpenAI 新接口）接专用 cancel；其余回退 A。
  - C：不处理（已有 A 的本地效果）。
- **例子**：点停止后，供应商后台可能仍把这次 completion 跑完并计费；我们不会再显示、不会再拿它做下一步。
- **最坏情况**：A 下用户仍可能被扣一次已发出的 token；B 维护多套协议；C 没有额外收益。
- **默认**：A；如果你看到具体供应商有 cancel 接口，告诉我型号，我们加 B。

### R100-4. 旧停止消息的 stopped 标记

- **现状**：新停止消息写 `chat-meta.stopped`，重启后 ±5 秒认领；旧数据没有这个字段，
  只对“（已停止…）”占位文案做开头兜底。
- **问题**：如果旧停止消息带的是**真实半截正文**（不是占位文案），重启后可能被当成正常回复。
- **可选方案**：
  - A（当前）：占位文案兜底；新数据全部有 stopped。
  - B：写一次性迁移：按“消息时间 + 操作台账/占位文案”推断旧 stopped，写入 chat-meta。
  - C：不迁移，旧会话保持现状。
- **最坏情况**：A/C 旧停止气泡可能少一个“已停止”标记，但正文/思考仍在；B 可能误标正常回复。
- **默认**：A；如果你有重要的旧停止会话，我们可以按那个会话做定向迁移。

### R100-5. 旧操作台账的 `xd1` 覆盖

- **是什么**：旧版行动 id 是 `xd1/xd2…`，重启后计数器从 1 开始，可能覆盖旧条目；
  本轮已改成 `xd-<时间戳>-<序号>`，**新数据不会再覆盖**。
- **问题**：旧 `chat-meta` 里已经被覆盖的条目无法还原（历史动作可能少几条/错位）。
- **可选方案**：
  - A（当前）：不迁移，旧数据保持现状；新数据正确。
  - B：一次性清空旧操作台账（会丢历史动作）。
  - C：按消息 ts 重新分配旧 id（无法恢复被覆盖的内容）。
- **最坏情况**：A 旧会话的“执行过程”可能少几条；B 丢更多；C 工作量大且不保证。
- **默认**：A。
