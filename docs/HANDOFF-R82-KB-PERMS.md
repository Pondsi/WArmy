# 交接：#103 知识库权限 / 用户切换 / 归档规范

## 是什么

第四列「知识库」卡现在有三组勾选：**可读 / 可写 / 可归档**，每组分会话库、内部库、私密库三层。勾选按会话保存到 `settings.kbPerms[sessionId]`。

同时提供「查看身份」下拉：在项目/群聊里选择某个成员，只展示该成员能看到的**公开会话层**，隐藏内部/私密层，也不给写入入口。

归档时自动把整理结果里“像规矩”的短句追加到本会话 `guifan/<sid>.md` 的「归档归纳」段。

## 有什么用

- 解决“群成员能写内部库 / 项目成员能看私密库”的越权风险；
- 让用户按会话决定知识库读写归档范围，而不是只能接受一套固定矩阵；
- 归档时把会话规范沉淀下来，下一轮注入即可约束牛马；
- 查看身份让创建者能核对“别人看到的公开层是什么”，不必切账号。

## 入口

- 第二列选中联系人/群聊/项目 → 第四列「知识库」卡 → 三组勾选；
- 同一张卡上方「查看身份」下拉；
- 归档由既有自动/手动归档触发，无需新入口。

## 数据与权限

- 存储：`settings.kbPerms = { [sessionId]: { read: string[], write: string[], archive: string[] } }`。
- 后端先算内置硬作用域：
  - 群聊/联系人：只有会话库；
  - 项目：会话 + 内部（内部写只给创建者）；
  - 我的牛马：会话 + 内部 + 私密（私密读还要实例的 `privateKb`）。
- 用户勾选只能在这个硬作用域内取交集；**前端勾选不是授权层**。
- 归档默认：我的牛马写内部库；共享会话写会话库。用户可在第四列取消。

## 方案与取舍

- 方案 A：只在前端显示勾选、后端仍走固定矩阵。  
  - 优点：改动小；缺点：界面像能配、实际不生效，最坏让用户误以为权限已收回。
- 方案 B（已采用）：前后端同一份 `kbPerms`，后端取交集。  
  - 优点：配置真实生效且不能越权；缺点：多一层设置与刷新。
- 方案 C：把权限做成角色表（owner/admin/member/viewer）。  
  - 优点：更接近团队产品；缺点：需要完整的成员角色/审批/证书链，属于 #108 的后续。

## 例子

- 群聊成员把“可写”勾到内部库：后端仍只保留会话库，界面下一次渲染会显示内部库未勾选；
- 项目创建者给项目勾“可归档：会话”，自动归档只写会话库；
- 项目成员点「查看身份」选另一个成员：只看到会话层的公开条目，写/归档勾选隐藏。

## 最坏情况

- 若只做前端勾选，私密层可能被越权写入；
- 若默认值写错，群成员可能写内部库；
- 若归档层配置为空，自动归档会跳过该会话（不会丢数据，手动归档仍可用）。
