## 3. 未完成项（逐项：是什么 / 为什么 / 需要你做什么 / 方案 / 最坏情况）

### U1. 企业微信 / 钉钉的**接收**（发送已完成）

- **是什么**：把企微/钉钉里别人发来的消息接进 WArmy，再交给某只牛马处理。
- **现状**：发送已经真实实现并通过 mock 门禁；接收**没有实现**。飞书用消息列表轮询、Telegram 用 `getUpdates`，这两个已经能收；企微/钉钉官方**没有等价的可轮询消息列表接口**。
- **为什么没完成**：需要二选一的外部条件：
  - 企微：企业微信后台配置**公网 HTTPS 回调 URL** + `Token` + `EncodingAESKey`，服务端做 SHA1 验签 + AES 解密；
  - 钉钉：官方 `dingtalk-stream` **Stream 长连接 SDK**（需要企业应用凭据），或事件回调。
  这两者都不是本机代码单独能“假装”的；没有公网回调/SDK 就收不到真实消息。
- **方案**：
  - **A. 企微回调服务器（推荐先做企微）**：在应用内起一个 HTTP 端点（可配置端口），实现 GET 验证 + POST 验签/解密/解析 XML；用户用内网穿透/反向代理把公网 HTTPS 指到本机。优点：不依赖第三方 SDK、协议可控；缺点：用户要维护公网入口/证书；最坏：公网入口配错 → 收不到消息但界面不能显示“已连接”。
  - **B. 钉钉 Stream SDK**：装 `dingtalk-stream`，用 clientId/secret 建长连接。优点：不需要公网 URL；缺点：引入第三方依赖、要企业应用权限；最坏：SDK 断线重连不稳 → 消息延迟（必须显示真实状态）。
  - **C. 暂不做接收，只保留发送 + 如实标注**：当前状态；最诚实、零外部依赖；缺点：只能单向发。
- **需要你做什么**：决定 A/B/C；若选 A，给一个可用的公网 HTTPS 域名/反代方式与企微后台参数；若选 B，确认可以安装 `dingtalk-stream` 并给企业应用凭据。

### U2. 四个 IM 平台的**真实凭据与线上联调**

- **是什么**：让飞书/企微/钉钉/Telegram 真正连上你的应用，而不是回环 mock。
- **为什么没完成**：没有你的应用凭据，也没有你的服务器/机器人；我不能凭空创建。
- **需要你提供（按平台）**：
  - 飞书：`app_id`、`app_secret`、目标群 `chat_id`；应用需开通 `im:message`（发）与 `im:message:readonly`（收）；Lark 国际版要说明用 `open.larksuite.com`。
  - 企微：`corpId`、`corpSecret`、`agentId`、接收人（默认 `@all`）；接收还需要 U1 的回调参数。
  - 钉钉：`clientId/AppKey`、`clientSecret/AppSecret`、`robotCode`、接收人 userId；接收需要 Stream SDK。
  - Telegram：BotFather 的 `botToken`、目标 `chat_id`；如用自建 Bot API 给 `baseURL`。
- **方案**：先用**测试企业/测试群**联调，确认发送形状与权限，再切正式群；凭据只在本机加密存储（已有 cred-vault）。
- **最坏**：拿正式群直接试 → 发错消息/触发风控；或应用权限不足 → 一直 401/403，界面必须如实报错而不是“已连接”。

### U3. 双机跨公网 / 多服务器故障转移

- **是什么**：两台真实设备跨公网互发消息；A 服务器挂了自动切 B；全部失败时会话只读、消息留待发。
- **现状**：本机双实例 E2E 已通过（同一台机器、回环）；地址簿多 peer **扇出**已实现；**公网中继隧道、跨机 NAT 打洞、故障转移/顺序保证**没有做真实验收。
- **为什么没完成**：需要第二台真实设备 + 公网/中继环境；当前只有一台机器。FWArmy 可做中继，但“转发隧道”仍未启用（项目里明确标注）。
- **方案**：
  - **A. 只做局域网 mesh**：现有能力即可，改动小；公网不行。
  - **B. 接 FWArmy 中继**：公网可用；要补中继客户端、回执、重试、顺序；工作量中等。
  - **C. 多服务器扇出 + 故障转移**：最完整；要处理部分成功、去重、乱序、只读广播；工作量最大。
- **需要你做什么**：给第二台设备（Windows 优先）与网络条件；决定先做 B 还是直接 C；若用 FWArmy 中继，给中继监听地址/端口与凭据策略。
- **最坏**：只做发送不做回执 → 用户以为发出去、对端没收到；只做选路不做 outbox → 重启丢待发；多服务器无序扇出 → 重复/乱序。

### U4. 本机 Device Guard 阻止未签名打包 exe（**交付阻断，优先处理**）

- **是什么**：2026-10-25 23:08 起，本机 Windows Code Integrity（Policy ID `0283ac0f-fff1-49ae-ada1-8a933130cad6`）阻止 `release/win-unpacked/WARMY.exe`，提示“已被组织 Device Guard 阻止”。事件日志 `Microsoft-Windows-CodeIntegrity/Operational` Id 3077。
- **为什么没完成**：这是**系统策略**，不是程序逻辑；未签名 exe 被策略拒绝。开发态 `electron.exe`（已签名/被允许）仍能跑，所以功能验收不受影响；打包版在本机打不开。
- **方案**：
  - **A. 代码签名（最正规）**：买 OV/EV 代码签名证书（或企业内 CA），用 `electron-builder` 的 `win.certificateFile/certificatePassword` 签名；需要你提供证书与密码（不要发到聊天里，放本机文件并告诉我路径）。最坏：证书丢失/过期 → 发布链断；EV 还要硬件 token。
  - **B. WDAC 补充策略放行哈希/发布者**：管理员为本 exe 的哈希或发布者加 allowlist；需要管理员权限与组织安全审批。最坏：策略由 IT 统一管理，个人改不了。
  - **C. 在另一台没有该策略的机器上安装/验收**：最快；缺点是本机仍不能跑打包版。
  - **D. 继续用开发态 Electron 验收**：当前状态；缺点不是用户实际安装形态。
- **需要你做什么**：决定 A/B/C/D；若 A，给证书文件路径（我不会打印密码）；若 B，找管理员要策略变更；若 C，给另一台机器。
- **最坏**：一直不处理 → 本机永远打不开打包版，只能开发态验收；发布出去的安装包在同类企业策略机器上也会被拦。

### U5. A9 拟态“看屏幕”的范围

- **现状**：只截**本应用自身窗口**，默认关，点一次才截一次，不落盘；不截桌面、不自动、不做鼠标键盘动作。
- **没完成的部分**：真正的“看整个桌面/其它应用 + 受控动作”。
- **方案**：
  - **A. 保持现状（推荐）**：隐私最好、零误操作；缺点：桌宠看不到别的窗口。
  - **B. 整屏截取 + 隐私开关 + 遮罩确认**：体验完整；需要屏幕采集权限、敏感窗口排除、预览确认、失败回退；最坏：误采密码/私聊窗口并进入模型上下文。
  - **C. B + 受控动作（点击/快捷键）**：最强；风险最高（误点、外挂判定、权限），需要动作白名单与二次确认。
- **需要你做什么**：选 A/B/C；若 B/C，明确“哪些窗口永不采集”“是否需要每次确认”“允许哪些动作”。

### U6. 只读角色 viewer 的完整落地

- **现状**：邀请模块支持 `viewer`，但群成员表类型只有 `creator/admin/member`；UI 邀请只给“成员/管理员”。所以 viewer 目前不会真正进入成员表。
- **为什么没完成**：`group-store` 与契约 `QunJuese` 没有 viewer；加它要同时改契约、存储、权限判断、UI 与门禁，属于一个完整小迭代。
- **方案**：
  - **A. 暂不做 viewer**：成员/管理员已满足当前协作；最省事。
  - **B. 加 viewer（只读）**：可看不可写/不可派活；要定义“只读”到哪一层（聊天可发？文件可读？）。
  - **C. 用 member + 会话级知识库权限模拟**：不新增角色，靠 `kbPerms` 限制写；语义不如 viewer 清楚。
- **需要你做什么**：选 A/B/C；若 B，定义 viewer 能做什么（举例：能看聊天与知识库、不能发消息/不能改文件/不能派任务）。

### U7. 签名名片的 UI 入口

- **现状**：主进程已有 `identityMyCard`（导出签名名片）与 `identityPeerCard`（接收验签），但**界面还没有“导出/导入签名名片”入口**；群弹窗的签名邀请依赖“在线联系人已有公钥名片”，没有公钥时只能拒绝签发。
- **为什么没完成**：产品入口/交互没定；导出成二维码、文件还是粘贴 JSON？是否需要“扫一扫导入”？
- **方案**：
  - **A. 二维码名片**：导出 QR（含签名名片 JSON），对方扫码导入；离线可用、仪式感好；缺点 QR 容量有限（名片 JSON 可能较长，需要压缩/分片）。
  - **B. 文件/粘贴 JSON**：最稳、无容量问题；缺点不直观。
  - **C. 局域网自动交换**：在线时自动互发签名名片；最顺滑；缺点离线不可用，且要防自动信任（仍需用户确认）。
- **需要你做什么**：选 A/B/C（可组合 A+B）；若 A，确认二维码容量策略（超长时分片/仅含指纹+公钥，联系方式另传）。
- **最坏**：没有入口 → 两个从没在线互连的人无法用签名邀请，只能走通用链接（通用链接不绑定人）。

### U8. 真实微信账号 / 话筒 / 4K 物理屏验收

- **微信**：现有 iLink 扫码通道与协议门禁；真实个人微信扫码、收发、风控需要你的账号与手机。风险：平台风控/封号；不能承诺“接上就一定稳定”。
- **话筒**：本机 ASR 已门禁；真实麦克风阵列/蓝牙耳机的增益、回声、断连需要物理设备。
- **4K/带鱼屏**：门禁用真实 Chromium 视口 960/1280/1920/2560/3440/3840 验证盒模型；没有物理 4K/带鱼屏，无法验证系统缩放 150%/200% 下的观感。
- **需要你做什么**：给测试账号/设备，或明确“这些不在本轮验收范围”。
