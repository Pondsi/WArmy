# P0-5 自托管凭证与"看不到密钥也能自动解锁"（第 53 轮项 8 · 等用户拍板，未写代码）

> 用户的原话：**"我们要做看不到密钥也能自动解锁的体验，但我们的项目是没有服务器的，我们使用类似比特币钱包的方式让用户自己管理登录凭证，
> 这样的情况下，如何实现看不到密钥也能自己的解锁，并且在其他设备上若是成功登录了自己的账号，就能解锁之前的文件。"**
>
> 这一份是**方案文档**（不含实现）：先给结论，再给机制、边界、丢失场景真值表、性能、落地三步与需要拍板的 5 个决策点。
> 上一轮的结论仍然成立（见 `docs/HANDOFF-R51.md` §32）："用登录 ID 当密钥"不可行 —— ID 是公开的低熵标识，不能当秘密。
> 本轮这条口径把它推进了一步：**凭证本身就是密钥**（本产品已经是这么做的，见下面第 1 节），于是"钱包式自托管"是唯一不需要服务器的路线。

## 0. 结论先行（两问两答）

**Q1「看不到密钥也能自动解锁」怎么实现？**
⇒ 密钥**从来不需要被看见**：它被**本机可信存储封装（wrap）**，解封由系统自动完成；用户只在封装不可用时（重装系统/换设备/TPM 重置）
才被要求输入恢复凭证。三层：**封装层**（Windows DPAPI / TPM 非导出密钥 / macOS 钥匙串）→ **内存解锁态**（会话内缓存 + 闲置自动锁）
→ **恢复路径**（输入凭证重新派生）。"自动解锁"和"看不到密钥"是同一件事的两面：只要秘密被封装在设备里，就既不用显示、也不用手输。

**Q2「在其它设备上成功登录了自己的账号，就能解锁之前的文件」怎么实现？**
⇒ 在没有服务器的前提下，**"登录"不可能是"服务端验密码"**，只能是**"证明持有同一份自托管秘密"**。可行的只有一条路：
1. **同一份凭证 ⇒ 派生出同一把主密钥**（确定性派生，跨设备、无需网络）；文件用内容密钥 DEK 加密、DEK 由主密钥封装 ⇒
   新设备输入同一凭证就能解开旧 DEK，进而解开旧文件。**这是"换设备恢复钱包"的做法，不需要服务器。**
2. 不想让跨设备依赖"人肉重输凭证" ⇒ **设备之间再封装**：旧设备用新设备的公钥（X25519）把 DEK 重新包一份，
   包好的东西丢进**任意**同步介质（网盘 / Syncthing / U 盘 / 聊天文件）⇒ 新设备用自己的私钥解开。
   **同步介质只搬运密文，永远拿不到解开它的东西**（这正是与 LastPass/MEGA 那类失败的差别）。
3. **反面（必须如实告诉用户的代价）**：想要"输个账号密码，新设备就自动解锁"而**不需要**输入自托管秘密，
   就一定需要**服务端持有一份能解开用户数据的材料** —— 这与"没有服务器"直接冲突，而且历史上这类设计两次出事
   （MEGA 的"密码即密钥"导致改密码要重加密全库、且服务端能接触明文材料；LastPass 2022 事件是服务端持有的可解材料被拿走）。
   **要么放弃"无服务器"，要么放弃"忘了凭证也能自动解锁"，二者不能同时要。**

## 2. 密钥层级（一份秘密，多个用途，域分离）

```
用户自管的凭证（256bit，唯一需要人保管的东西；界面上遮罩显示，永不强制展示）
  └─ HKDF-Expand，域分离标签（各标签互不相同 ⇒ 一个子密钥泄露推不出另一个）
       ├─ IK   身份密钥（已有：Ed25519，互通签名用）
       ├─ MK   主封装密钥 ⇒ 封装每条 DEK
       ├─ BK   备份封装密钥 ⇒ 导出包用（与 MK 分离 ⇒ 导出的备份不会因日常使用被牵连）
       └─ AK   设备绑定密钥 ⇒ 本机 DPAPI/TPM 那层封装用的密钥名空间
每条数据一个 DEK（内容密钥，随机 256bit）：
  文件 / SQLite / 每个知识库层各自一批；DEK 永远以"被 MK 封装后的形态"落盘
设备侧还有：
  WK（工作密钥）= MK 被本机可信存储封装后的 blob ⇒ 开机自动解封 ⇒ "看不到密钥也能自动解锁"
```

**为什么用 HKDF 分层而不是"凭证直接加密数据"**：凭证要参与签名、互通、备份，直接当数据密钥会让任一用途的实现细节
变成对凭证本身的泄露面；HKDF 域分离（label + 上下文）是标准做法（HKDF 的用途绑定就是为这个设计的）。
**为什么不复用 BIP-39 的助记词**：BIP-39 = 熵 + 校验词（PBKDF2-HMAC-SHA512 **2048 轮** + 可选 passphrase），
它的 2048 轮拉伸是为**人类可读词表**服务的（词表本身熵不高的顾虑、以及兼容生态）；我们的凭证已经是 256bit 随机、
由程序生成与粘贴，不需要拉伸成口令族 ⇒ **不引入 BIP-39 的词表依赖与"第 25 词只带校验不带熵"这类坑**，
但**保留同一套自托管语义**：一份秘密 + 确定性派生 + 可导出备份 + 换设备用同一份秘密恢复。
（若将来要给人念/抄，再单独出助记词编码，属可选层。）

## 3. 封装层选型（"自动解锁"靠它）

| 方案 | 自动解锁体验 | 强度 | 关键边界（必须如实知道） |
|---|---|---|---|
| **Windows DPAPI / Electron safeStorage**（现状） | 同一 Windows 账户登录即自动解，用户零输入 | 中 | ① 绑定**用户账户**，不绑机器；② **域环境下 AD 会备份 escrow 密钥 ⇒ 组织管理员理论上能解**；③ 换机/重装或账户密码变更（非 DPAPI 迁移）会解不开 |
| **TPM 非导出密钥（NCrypt/TPM）** | 开机自动；可选附加 PIN | 中高 | 密钥不可导出 ⇒ **不能跨设备恢复**，必须另配导出备份；TPM 重置/PIN 锁死即丢；Windows 更新偶发导致句柄失效 |
| **macOS 钥匙串 / Linux** | macOS 自动；Linux 无统一可信存储（kwallet/secretservice 可能缺失） | 视平台 | Linux 必须回落到"封装文件 + 用户输入"，不能假装有硬件信任根 |
| **只靠用户输入（无封装）** | 每次冷启动都要输入 ⇒ 与"自动解锁"矛盾 | 高（若熵足） | 留作**恢复路径**与 Linux 回落，不作日常主路径 |

**建议的组合**：日常 = DPAPI/safeStorage 封装（零输入）；**可选加强** = TPM 非导出密钥 + 闲置自动锁；
恢复 = 凭证输入；导出 = age 格式（scrypt 派生 + XChaCha20-Poly1305，64KiB 分块）或 DEK 的 recipient 封装。
界面上那把"小眼睛"继续只展示**遮蔽形态**，明文凭证只在用户主动点"导出恢复材料"时出现一次。

## 4. 六种场景真值表（哪种丢什么、怎么救）

| 场景 | 现在会发生什么 | 上方案后会发生什么 | 补救 |
|---|---|---|---|
| 换电脑（有凭证） | 数据在旧机器上，新机器读不到 | 输入同一凭证 ⇒ 派生 MK ⇒ 解开带过来的 DEK 包 ⇒ **旧文件直接可读** | 带密文走任意同步介质 |
| 换电脑（凭证没抄下来） | 身份彻底丢，无找回 | 同上：**彻底丢，不可找回** | 事前：导出 age 备份包 / SLIP-39 分片交给可信的人 |
| 重装系统（同账户，凭证在） | safeStorage blob 可能失效 | 用凭证重新派生并重新封装 | 重新封装时留 `.bak` |
| 重装系统（凭证没抄） | 同上 | 同上 | 同上 |
| 凭证泄露（别人拿到那 51 位） | 对方**立刻**拥有你的身份 + 能解你所有密文 | 同样立刻（自托管的本质） | 事前：DEK 轮换 + 重新封装；**不能靠服务端封号**；界面上已经遮罩、不落明文日志 |
| 同一 Windows 账户被人登录（家里/公司公用机） | 对方 DPAPI 自动解封 ⇒ 直接读明文数据 | 对方能解 WK ⇒ 但可加第二层：启用 TPM + PIN，或锁屏即清内存密钥 | 锁屏自动锁 + 可选 PIN |

**这条必须写在界面上**：自托管 = "我们拿不回你的数据，也没有能替你恢复的后门"。任何"忘记密码也能找回"的设计，
要么引入服务端可解材料（违背无服务器），要么引入受托人分片（SLIP-39/Shamir）。没有第三种。

## 5. 性能（用户上一轮问过"这种加密对性能影响大吗"）

- 对称 AEAD（AES-256-GCM 有 AES-NI；XChaCha20-Poly1305 纯软件）在现代 CPU 上 **>1 GB/s** 量级；
  age 的 64KiB 分块开销是每块一个 nonce/tag（约 +16B/块，密文膨胀 ~0.02%）。
- 唯一贵的是 KDF：**scrypt/Argon2 只在"用户输入凭证 ⇒ 得到 MK"这一步跑一次**（几十 ms 到 ~1s），跑完就把 MK 封存在内存/可信存储里。
  **绝不能每轮对话都重新派生。**
- 数据库整库加密（SQLCipher 一类）实测开销约 **5–15%**（页级 AES + 页缓存），本地几千行的记忆库远在噪声级别以下。
- 结论：**性能不是这件事的瓶颈**，瓶颈在"密钥常驻与解锁策略"（安全性与"零输入"之间的取舍）。

## 6. 落地三步（每步都可逆、可单独验收）

1. **Step 1 · 本机自动解锁（对应 Q1）**：给本地数据加 DEK/MK/WK 三层，WK 用现有 `safeStorage` 封装；
   迁移一次性完成（逐文件"明文 ⇒ 密文"，先留 `.bak`），审计记录迁移条数与失败清单；锁屏/闲置清内存密钥。
   **验收**：同账户重启零输入能解；把密文拷到另一台机器解不开；kill 进程后内存里没有明文 DEK（用转储核对）。
2. **Step 2 · 加密备份包（对应"凭证丢了怎么办"的事前一半）**：导出 age 文件（口令模式 scrypt 派生，或 recipient 模式）
   含知识库 + 提示词层 + 设置；导入时校验层完整性与版本；**导出包本身不含凭证明文**（凭证只用来派生）。
   **验收**：导出 ⇒ 换 profile 导入 ⇒ 归档/召回/注入三侧行为一致。
3. **Step 3 · 跨设备再封装（对应 Q2 路线 1+2）**：新设备生成身份密钥 ⇒ 旧设备把 DEK 用新设备公钥重新包一份（X25519）；
   同步介质只搬密文；"设备清单"可见可撤销。**这一步不做服务端**，也不做"账号密码登录"。
   **验收**：新设备**不需要**重输 51 位也能解开旧文件；撤销某设备后其 DEK 包无法再解（需要轮换 DEK 才真正失效，如实写明）。

## 7. 需要用户拍板的 5 件事（不定就无法开工）

1. **默认强度档位**：只做 DPAPI 自动解锁（零输入、最省事），还是加 TPM 非导出密钥 + 可选 PIN（更强、换机更麻烦）。
2. **"锁屏即锁"要不要**：锁屏清内存密钥 ⇒ 解锁要重新输入凭证/唤醒 ⇒ 与"永远零输入"直接冲突，选哪头。
3. **恢复材料要不要导出**：age 备份包 / 助记词式编码 / SLIP-39 分片，三选一或全不要（全不要 = 凭证丢即永久丢）。
4. **跨设备要不要"同凭证直接解"（Step 3 路线 1）**：最简洁，代价是"同一份秘密在多台机器上以可解形态存在"；
   还是要走"设备间再封装 + 设备清单"（可撤销，代价是要多做一层密钥管理与轮换）。
5. **要不要真的做"账号 + 服务器"那条线**：如果想要"忘掉凭证也能自动解锁"，就必须有服务端参与密钥 ⇒ 明确推翻"项目没有服务器"的前提。
   （现状：**不做**。本文档按"没有服务器"写。）

## 9. 第 54 轮：用户拍板后的定稿（伪 PIN + 绑定 + 60 天期限 + 助记词兜底）

用户的决定（原话要点）：**丢了凭证就永久取不回**（没有后门，除非事先导出）；用**伪 PIN** 登录，绑定
「设备 + 系统账号 + 随机选一个硬件（CPU/显卡/硬盘）的 ID」，任一变更 PIN 即失效；**每次打开都要输 PIN**；
锁屏即锁要覆盖 Windows/macOS/Linux；要**导出助记词**（唯一取回方式，平时用 PIN，PIN 不可用时用助记词）；
跨设备只要凭证正确就能解；**PIN 可设期限**（如 60 天不登录即过期，每天登录自动续期）。

### 9.1 密钥与校验结构（不新造密码学）
```
助记词（唯一恢复材料，离线抄写）
  └─ Argon2id(助记词, 固定盐) ⇒ RK 根密钥（只在恢复/导出时出现）
       ├─ HKDF("warmy/dek")  ⇒ MK ⇒ 封装各 DEK（数据解密）
       └─ HKDF("warmy/auth") ⇒ AK ⇒ 身份签名（Ed25519，互通/设备证书）

伪 PIN（日常）：
  Argon2id(PIN, 每设备随机盐, m=64MiB, t=3, p=1) ⇒ KEK
  PIN 包 = AEAD_KEK( RK密文 | 过期元数据 | 绑定摘要 )      ← 绑定摘要与过期时间都进 AAD
绑定摘要 = H(机器ID ‖ 系统账号SID ‖ 随机选定硬件序列号 ‖ 设备公钥)
```
- **任一绑定项变化 ⇒ AAD 校验失败 ⇒ PIN 包解不开**（不是"程序判断后拒绝"，是密码学上解不开）。
- **60 天期限**：`上次成功解锁时间` 与 `最晚有效时间` 写在 AAD 里，解锁时校验；每天成功解锁就把最晚有效时间往后推 60 天。
  另存一个**只增不减的计数器/最高水位**（同样进 AAD）防止把系统时间往回拨来续命。
- **PIN 强度**：至少 6 位数字（推荐 6–8 位）；错误 5 次后指数退避（30s→1m→5m→15m），并在界面显示剩余次数。
  PIN 短，所以 Argon2id 的内存成本必须真实生效（不能降参）；这台机器上的 PIN 包离线爆破的成本主要来自它。

### 9.2 "锁屏即锁"三平台怎么落
| 系统 | 事件源 | 兜底 |
|---|---|---|
| Windows | Electron `powerMonitor` 的 `lock-screen`（会话锁）/ `suspend` | 定时器 + 空闲检测（`powerMonitor.getSystemIdleTime`）> 5 分钟也锁 |
| macOS | 同上的 `lock-screen` / `suspend` | 同上 + 屏幕保护启动检测 |
| Linux | `org.freedesktop.login1` 的 `LockedHint`（DBus）；没有 logind 时读 XScreenSaver | 空闲检测 + 手动锁定按钮 |

锁定动作 = **清内存里的 RK/MK/KEK 与已解密的 DEK**，并切回 PIN 界面；不结束进程、不丢未保存内容（先落盘再清）。
"每次打开都要 PIN" = 冷启动一定要求 PIN；**锁屏后也要求 PIN**（即使用户没离开系统账户）。

### 9.3 助记词（唯一取回路径）
- 24 词（256 bit 熵）编码，**只在创建时与"主动导出"时显示一次**；禁止截图（界面提示）、不写日志、不落明文文件。
- 输入助记词 ⇒ 重建 RK ⇒ 用当前设备/账号/硬件重新生成绑定摘要与新 PIN 包 ⇒ **旧 PIN 立即作废**。
- 助记词输错不报"哪一位错"（避免把校验信息当 oracle）；连续失败退避同上。
- 助记词丢失 = 数据永久不可解（用户已确认接受）；导出包（age）是第二条退路，不含助记词本身。

### 9.4 跨设备
- 同助记词 ⇒ 同一 RK ⇒ 直接解旧密文（离线、无服务器）。
- 设备改绑：旧设备可把"DEK 包"用新设备公钥再封装一份（`docs/ANQUAN-HUTONG.md` 的设备证书流程）；同步介质只搬密文。
- 设备/账号/硬件任一变化 ⇒ 该设备的 PIN 失效 ⇒ 必须助记词（或旧设备授权）才回来 —— 这正是用户要的"换机就要证明自己"。

### 9.5 必须如实告知的三条边界
1. **硬件 ID 可被伪造**：有代码执行权限的攻击者能改绑定信息；绑定挡的是"同一个系统账户被另一个人用"这类场景，
   真正的秘密是 PIN + Argon2id。要更强就加 TPM 非导出密钥（可选档）。
2. **重装系统/换主板/换硬盘 ⇒ PIN 必失效**（这是设计，不是 bug）；事先导出助记词是唯一解。
3. **没有"忘记 PIN 也能找回"**：任何这种能力都要求服务端或受托人持有一份可解材料，与"无服务器 + 丢了就丢了"冲突。

### 9.6 落地顺序（每步可单独验收）
1. 纯逻辑：`pin-ce-lue.ts`（PIN 包结构、AAD 绑定摘要、60 天期限、退避、时钟回拨检测）+ 真值表门禁（不碰 UI）。
2. 加密落盘：数据层 DEK/MK（先对**新写入**生效，旧文件迁移留 `.bak`）。
3. 解锁界面与锁屏钩子（三平台事件 + 兜底定时器）。
4. 助记词创建/导出/恢复流程（含"导出后确认已抄写"）。
5. 设备证书与跨设备再封装（与互通安全共用一套）。
