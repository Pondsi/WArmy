# 无服务器、无中继的去中心化身份与对等通讯（方案与风险评估）

> 用户口径：**永远没有服务器、没有中继、没有用户以外的控制者**；联系人之间是**对等**传输；
> 项目和群聊里**创建者是主机**，其他人/牛马是副机；需要一个**类似比特币记账网络**的去中心化身份层，
> 让用户用助记词恢复后能在网络上**确认身份**、找回联系人/群聊/项目列表；网络**不记聊天内容**，只记身份与列表；
> 群/项目里创建者必须在线，其他人才能发送；迟上线的人在后台慢慢同步历史；联系人消息带回执、可撤回、失败重试、错位提示。

## 0. 结论先行（三句话）
1. **"身份 + 列表"上公共账本：一半可行。** 身份锚（公钥、设备证书根、恢复指纹、版本号）适合上链；
   **联系人/群/项目列表不适合直接上链**（社交图谱永久公开、无限增长、谁都能写），应改为**签名文档 + 内容寻址（DHT/IPFS 式）**，
   链上只放这份文档的**哈希指针**。
2. **"永远没有服务器"在身份层只能"借用"公共网络**：真正比特币式网络需要矿工与共识，个人产品无法自建；
   可行的两条路是**借用现成公链做锚定**或**用 Kademlia DHT + 自认证记录（不需要共识，但没有"永久"保证）**。
   这两条的取舍见 §6，需要你拍板。
3. **恶意添加与虚假信息不能靠"网络上没人乱写"来防**，只能靠**签名 + 双方确认 + 本地信任策略**：
   任何一条"已确认"的联系人/群/项目都必须**双方签名**；单向写入只能显示为"待确认请求"，不进列表、不参与解密。

## 1. 分层：哪些上网络、哪些永远不上
| 层 | 内容 | 存在哪 | 谁能读 |
|---|---|---|---|
| 身份锚 | 根公钥、设备证书根、恢复公钥指纹、**单调版本号**、列表文档哈希 | 公共账本 / DHT | 所有人（本来就要被查到） |
| 列表文档 | 联系人、群、项目（含成员公钥指纹与角色） | **加密后**放 DHT（按哈希取） | 只有本人（用根密钥派生的存储密钥解密） |
| 聊天内容 | 消息、附件、知识库、私密库 | **本机 + 对端本机** | 只有会话参与者（端到端加密） |
| 回执/在线状态 | `msgId` 确认、心跳 | 端到端加密通道 | 只有对端 |

**为什么列表不直接上链**：链上数据永久、公开、不可删 —— 等于把"谁认识谁、谁在哪个项目、群里有谁"永久公开；
而且每个用户每次加人都要写一笔交易（成本 + 无限增长）。**哈希指针**只暴露"有一份列表更新了"，不暴露内容。

## 2. 身份与恢复（防冒充的核心）
```
助记词（24 词，唯一恢复材料）
  └─ Argon2id ⇒ RK
       ├─ HKDF("warmy/id")   ⇒ 身份签名密钥 IK（Ed25519）
       ├─ HKDF("warmy/dev")  ⇒ 设备授权根（签发/撤销设备证书）
       └─ HKDF("warmy/store")⇒ 列表文档的存储密钥（加密列表）
身份记录（公共账本/DHT）：
  { did = 公钥指纹, ikPub, devRootPub, recoverPub, version, listHash, updatedAt, sig=RK }
```
- **恢复**：助记词 ⇒ RK ⇒ 用 RK 签一条 **version+1** 的新身份记录（新设备证书 + 新的 listHash）⇒ 广播。
  网络只认**版本最大且签名有效**的那条；旧设备记录版本更低，自动失效（防回滚）。
- **防冒充**：任何自称是某人的消息/列表更新，都必须能追到"当前 version 的身份记录"里授权的设备证书；
  证书不在记录里、或被撤销 ⇒ 直接拒收。
- **旧设备怎么办**：恢复后**必须显式撤销旧设备**（新记录里不带它）；旧设备即使本地还有数据，也签不出被网络接受的新消息
  （它拿不到新的会话授权）。但它仍能解开**它本地已有的旧文件** —— 这是"没有后门"的必然代价，只能靠"恢复即轮换"减轻。

## 3. 联系人的"双方确认"（防恶意添加的关键）
- A 想加 B：A 写一条 `request`（A 的 DID + B 的 DID + 时间 + 签名）放进自己的列表文档。
- B 收到后，**B 也在自己的列表文档里写一条指向 A 的确认**（B 签名）。只有**两边都有对方签名**的条目才算"联系人"。
- 因此：任何人都可以往**自己的**列表里写你，但**无法让你这边显示"已确认"**；你的界面只显示"某人请求加你"，
  你可以忽略/拉黑（拉黑也是一条你签名的记录）。
- **虚假信息**：任何事实（"张三是某项目负责人"）都以**签名者**背书；未签名/来源不明的条目不进"已确认"层，
  只进"待核"层（与知识库的〔待核〕同一口径）。
- **垃圾请求**：本地按 DID 维护"未通过请求"的速率上限（例如每 DID 每天 ≤3 条）；超过就静默丢弃并记账。
  没有服务器，所以无法全局封禁 —— 只能"本地不看你"。

## 4. 群聊/项目：创建者为主机（按你的要求）
- **创建者 = 权威排序器**：群消息的发送需要一份**创建者签发的短时授权**（`groupId, memberDID, 有效期, 序号, sig`）。
  创建者离线 ⇒ 授权过期 ⇒ 其他人**只能读历史、不能发送**（与你的要求一致）。
- **历史记录**：每条消息由作者签名，按 (创建者序号, 作者序号) 排序；存储为**追加日志 + Merkle 根**，
  新成员从任意在线成员拉取（**优先非创建者**，减轻创建者带宽），后台限速分块同步，校验 Merkle 根与作者签名。
- **所有权转移**（必须预设，否则创建者永久失联 = 群永久只读）：
  创建者可在任何时候签一条 `transfer(toDID, seq)`；或预先签好"若我 90 天不在线，由成员多数签名接管"的条款。
  没有这条，就只剩"只读存档"——这是"创建者必须在线"的直接代价，需你确认接受。
- **解密权限**：群/项目有一条组密钥（GK），由创建者用每个成员的**设备公钥**封装分发；成员变更 ⇒ 轮换 GK。
  "单机时判断有没有权解密"= 本地有没有被你的设备私钥解开的 GK 包；**不需要任何服务器参与**。

## 5. 联系人消息：状态机 + 回执 + 撤回 + 批重试 + 错位
状态：`草稿 → 发送中(牛马跑动图标) → 已送达(收到回执，图标消失) → 已读(可选)`
```
失败：连续 3 次无回执/明确 NACK ⇒ 失败（左侧显示"发送失败"+ 重发图标），不影响后续消息
撤回：仅"未送达"可撤回（右击菜单）；已送达 ⇒ 撤回项置灰（不可点）
批发送：按消息创建时间排序，每批 2–3 条；批内成功/失败分别处理，失败重试 3 次后判失败；一批结束再发下一批
错位：接收侧比较 创建时间 与 接收时间；若某条创建时间早于已显示的最后一条 ⇒ 左侧显示"超时/错位"图标并提示时间异常
在线状态：联系人上线时主动广播（加密心跳）；列表显示在线/离线；上线后先补发未成功的队列
```
- 这些状态**全部本地持久化**（`outbox` / `inbox` 两张表），重启后继续；回执本身也是一条签名消息（防伪造）。
- 你给的两枚图标已复制进 `renderer/icons/`：`chong-fa.svg`（重发）、`chao-shi.svg`（错位），实施时直接用。
- **没有中继**：离线消息只能"存在发送方本机"，等对端上线再发；对端永久不上线 = 永远发不出去（如实显示"未送达"）。

## 6. 去中心化身份层：三条可选路线（需要你拍板）
| 路线 | 怎么工作 | 优点 | 缺点 / 最坏情况 |
|---|---|---|---|
| **A. 借用公链锚定**（比特币/类似链的 OP_RETURN 或 DID 注册） | 身份记录哈希写到公链；列表文档放 DHT/自托管 | 真正"永久、不可篡改、无运营者"；助记词恢复后能查到最新版本 | 要付交易费、要等出块；**链上只放哈希**，别人仍可能通过交易关联分析你；依赖外部链的规则与费率 |
| **B. Kademlia DHT + 自认证记录**（IPNS 式） | 记录按"公钥哈希"寻址，由持有私钥者签名更新；节点互相转发 | 零费用、无共识、纯 P2P；延迟低 | **不保证永久**：最后一个保存者下线就没了；需要至少一个在线副本；易受 Sybil/日食攻击 |
| **C. 混合**（推荐起步） | DHT 为主 + 可选"把最新记录哈希锚到公链" | 日常零成本，想要"永久"的人自己付一次锚定费 | 实现两套；用户体验分叉（锚定/未锚定） |
**我的建议**：先做 **B（DHT）+ 本地/手动导出兜底**，把 **A 作为可选开关**。理由：我们没有服务器也没有运营团队，
B 是唯一"零成本、纯 P2P"且能马上落地的；A 的"永久"对个人用户不是刚需，但可以作为付费/高级选项。

## 7. 安全威胁与对策（逐条回答"是否安全/恶意添加/虚假信息"）
| 威胁 | 说明 | 对策 |
|---|---|---|
| **冒充** | 别人声称是你的联系人/群主 | 所有记录与消息必须签名；接受方先查"当前版本身份记录"里的设备证书；证书撤销即失效 |
| **恶意添加** | 任意人往你列表里塞条目 | 单向写入只显示"待确认"；**双方签名**才成为联系人；本地速率上限 + 拉黑 |
| **虚假信息** | 伪造"某人是某项目成员" | 只信"被声称者本人签名"的成员记录；创建者的成员变更也要签名；未签名条目进〔待核〕 |
| **重放** | 重发旧消息/旧列表 | 每条带 `seq`（每人单调）与 `ts`；接收方记最大 seq，旧 seq 直接丢；列表用 version 单调 |
| **日食/Sybil（DHT）** | 攻击者包围你的 DHT 邻居，阻断或投毒 | 多路径查询 + 记录自校验（哈希=公钥）+ 固定引导节点列表；**无法彻底防**，如实告知 |
| **元数据** | "谁和谁聊、什么时候聊" | 聊天不走网络存储；列表加密；DHT 查询用哈希，不暴露 DID 明文（可选） |
| **链上隐私** | 交易关联出身份 | 链上只放哈希；每次更新用新地址/一次性密钥（若走公链） |
| **创建者失联** | 群永久只读 | 预设所有权转移条款（§4）；否则接受只读 |
| **本地丢失** | 设备丢/坏 | 助记词 ⇒ 新身份记录 + 重新封装组密钥（从任意在线成员拉历史） |

## 8. 分阶段实施（每步都能独立验收）
1. **v0（现在）**：本机身份、设备内数据、本机知识库分层（已完成）。
2. **v1 手动对等**：二维码/文件交换身份记录与列表文档；双方签名；消息走现有渠道（密文信封）。**不依赖任何网络服务**。
3. **v2 DHT 身份层**：自认证记录 + 列表文档加密上传/拉取；创建者授权令牌；群历史 Merkle 同步。
4. **v3 可选锚定**：把身份记录哈希写到用户选择的公链；恢复时优先查链、回退 DHT。
5. **v4 体验**：在线状态、回执、撤回、批重试、错位提示（§5 的状态机）。

## 9. 需要你拍板的三件事
1. **身份层路线**：B（DHT，零成本、不保证永久）起步 + A 可选？还是直接只做 A？
2. **创建者永久失联**：接受"群变只读"，还是允许"预设转移条款（多数成员签名接管）"？
3. **群消息一致性**：坚持"创建者在线才能发"（强一致、可用性差），还是允许"创建者离线时先本地排队、上线后确认"（可用性好、顺序弱）？

## 10. 第 55 轮补充：创建者离线与"没有公网怎么找到对方"

### 10.1 创建者离线（用户定稿：只读，不排队）
- **创建者离线 ⇒ 群/项目进入只读**：能看已有历史，不能发消息、不能用功能；**不做"本地排队等上线"**（用户明确不要）。
- **创建者永久失联 ⇒ 永久只读**（**暂定**，以后可能改）：不做自动转移、不做多数成员接管（除非将来用户另行拍板）。
  这意味着一个群的生命周期绑在创建者身上；若要长期存在，唯一出路是创建者提前导出/移交（将来可加"预设转移条款"）。
- 实现上：群会话的发送权绑定"创建者在线的短时授权令牌"；令牌过期即只读。UI 必须**明说原因**（"群主不在线，当前只读"），
  而不是让按钮无反应。

### 10.2 两台设备怎么连（无公网、无服务器）
按"能不能直连"分四层，逐层降级、每层都如实告诉用户当前用的是哪条路：
| 场景 | 办法 | 说明 |
|---|---|---|
| 同一局域网 | **mDNS/DNS-SD** 广播身份指纹，发现后直连 | 不需要任何外部设施；手机热点/公司网若禁组播则失败，降级到下一层 |
| 有公网 IP 或锥形 NAT | **STUN 取外网映射 + UDP/TCP 打洞**（项目里已有 NAT-PMP/STUN 代码） | 成功率取决于 NAT 类型；打洞失败**不能**靠"中继"（用户禁止），只能降级 |
| 双方都在对称 NAT 后 | **直连基本不可能**（没有中继时） | 两条合法出路：① 走双方已有的**异步通道**（邮件/微信/文件）交换密文；② 等一方网络变化。**不假装能连** |
| 不知道对方当前 IP | **会合记录（rendezvous record）**：`DID → 当前 endpoint 列表 + 时间 + 签名`，放 DHT/自认证存储 | 每次上线/换网更新；对端按 DID 查记录再打洞。这就是"IP 变了也能找到"的答案 |

**关键点：地址按"身份"找，不按 IP 找。**
- 联系人：A 上线 → 查 B 的 rendezvous 记录（B 的 DID 是固定的）→ 拿到 B 当前 endpoint → 打洞 → 完成配对 → 恢复在线状态与待发队列。
- 群/项目：成员查**创建者**的 rendezvous 记录；创建者不在线 ⇒ 查不到/记录过期 ⇒ 只读（与 §10.1 一致）。历史同步可以查任意在线成员的记录。
- 首次互相发现（连 DHT 都还没有）：**邀请码/二维码里带"引导节点"**（对方或任意共同联系人），或用同一局域网 mDNS；这是"冷启动"唯一能做的。
- 无 DHT 时的极简版：邀请文件里带对方公钥 + 最近一次已知 endpoint，之后每次通信都互相更新地址（gossip 式），可靠性差但零依赖。

**必须如实写进产品的限制**：没有中继、没有公网、又是对称 NAT ⇒ **可能永远连不上**；这时只能走异步通道或换网络。
这不是实现缺陷，是"不要服务器/不要中继"的直接代价。

## 11. 在公网"广播"能不能保证对方收到？

**不能。** 无服务器的公网里没有"广播给某个人"这回事：你能做的是"把一条记录放到对方**会去查**的地方"，然后**等对方来取**。
所以可靠性不来自广播，来自三件事：

1. **会合记录（rendezvous record）**：`DID → 当前 endpoint 列表 + 有效期 + 序号 + 签名`。
   每次上线/换网/换 IP 都更新一条（序号单调递增，旧记录自动作废）；对方按 **DID**（不是 IP）查，拿到的是"你现在在哪"。
   - 存哪：DHT（自认证键 = 公钥哈希）/ 双方共同联系人转发 / 任何可写的公共存储。
   - 多写几处、带 TTL：任何一处还在，就能找到你。
2. **有应答才算送达**：消息带 `msgId`；对方收到后回一条签名的回执。**没有回执 = 没收到**，按你定的"2–3 条一批、3 次失败"重试。
   广播本身不产生回执，所以"广播 + 回执"才是可用的组合。
3. **多路径 + 退避**：同一份会合记录写到 ≥2 个地方；查询按 DHT 多路径 + 已知联系人缓存依次尝试；失败指数退避，不无限刷。

**两个人下线后都换了 IP、再上线怎么找到对方？**
- 各自上线时先更新自己的会合记录（DHT 里那条 `DID → 新 endpoint`）。
- A 找 B：用自己的 DID 查 B 的会合记录（DHT get）→ 得到 B 的新 endpoint → 向该 endpoint 发打洞包 → B 的客户端同时向 A 的 endpoint 发包 → 打通 → 交换在线状态与待发队列。
- 如果 B 的记录过期/没查到：A 向**共同联系人**要 B 的最新记录（gossip 一跳），或等 B 上线后主动来找 A（双方都上线时互相更新，最迟在 TTL 内收敛）。
- 如果双方都在对称 NAT 后：**打洞失败**；没有中继时只能走异步通道（邮件/微信/文件），或等一方网络变化。**如实告知，不假装成功。**

**群聊的"广播"**：向所有成员逐个发送加密消息（或发到群的历史 DAG，成员各自拉取）；成员在线状态由各自会合记录决定，
创建者不在线 ⇒ 只读（§10.1）。没有服务器，就不存在"一条消息保证全员同时收到"——只有"每人各自确认收到"。

## 12. "群消息弱一致"是什么

- **强一致**：任何时刻所有成员看到的群消息顺序与内容完全一样，且发送必须得到多数/权威节点确认（类似数据库事务）。
  在 P2P 里通常要共识（PBFT/Raft），代价是**必须有多数节点在线**、延迟高。
- **弱一致（最终一致）**：允许成员短暂看到不同顺序/暂时缺消息；只要**最终**每个人都能拿到全部消息并收敛到同一顺序即可。
  实现通常是"追加日志 + 因果顺序/序号 + 后台补拉"（我们的方案：作者签名 + 创建者序号 + Merkle 根 + 缺块补拉）。
- 你选的规则（创建者在线才能发、离线只读）其实是**用"可用性"换"顺序确定性"**：发送被创建者串行化，所以顺序不会乱；
  代价是创建者不在就没人能发。它**不是**强一致共识（不需要多数派），而是"单一排序者"。
- 若将来想放宽：可以让成员离线时**本地排队**，创建者上线后统一排序并广播（弱一致/最终一致），代价是"发出去"与"被确认"之间有一段不确定期。
  当前按你的决定：**不排队、只读**。

## 13. 有没有比"比特币式公链"更合适的方案？（第 57 轮调研）

有。把"身份"和"内容"分开选型，比"全部上链"更贴合你的需求（个人用户、无服务器、无中继、要能换机恢复）：

| 方案 | 它解决什么 | 优势 | 代价 / 不适合的地方 |
|---|---|---|---|
| **KERI（Key Event Log）** | 自认证身份（`did:keri`），密钥轮换/恢复记录在**hash 链**里，不依赖账本 | 无币、无手续费、无共识；恢复=新密钥事件；**比"公链存公钥"更轻** | 需要把事件日志复制到别处（DHT/联系人）；生态不如 DID 成熟 |
| **Secure Scuttlebutt（SSB）** | 每人一条**签名 append-only feed**，朋友间 gossip；离线优先 | 天然支持离线/最终一致；身份=公钥；无服务器 | 无全局顺序；发现依赖好友（gossip）；历史膨胀 |
| **Hypercore / Autobase** | 多写入者**因果日志**（multiwriter），排序是最终一致的 | 与我们要的"弱一致群消息"几乎同构；有成熟实现（holepunch） | 需要引导/发现（Hyperswarm DHT）；不是"永久公共记录" |
| **Nostr** | 签名事件 + 中继转发 | 简单、生态大 | **中继就是服务器**（你明确不要），且中继可读元数据 |
| **AT Protocol / Matrix** | PDS/家庭服务器 | 功能全 | 都需要服务器角色，违背前提 |
| **公链锚定（Bitcoin 等）** | 永久、抗审查的"存在性证明" | 真正永久 | 费用、延迟、隐私关联；个人用户不需要"永久" |

**我的建议（组合，而不是单选）**：
1. **身份**：KERI 风格 **Key Event Log**（自认证 id + 轮换/恢复事件 + 单调序号），日志放 DHT 并抄送联系人；
   需要"永久"的人可**可选**把最新事件的哈希锚到公链（一次付费，不是每次）。
2. **列表与群消息**：Hypercore/Autobase 风格的**多写入者签名日志**（我们已落地的 `qun-xiao-xi-rixi.ts` 就是它的最小排序内核：
   每作者 seq + 因果 deps + 确定性排序 + 缺口补拉 + 待排序队列）。
3. **发现**：Hyperswarm 式 DHT（topic = 群的公钥哈希）+ 会合记录（DID→endpoint）+ mDNS 局域网兜底 + 打洞；
   对称 NAT 无中继时如实失败。
4. **不引入**：全局共识、代币、中继、PDS。它们解决的是"陌生人之间无信任协作"，而你的场景是"熟人/小群 + 自携身份"。

**这也是"更好的方案"**：同样满足"无服务器、无中继、可恢复、防冒充、离线最终一致"，但**没有手续费、没有出块延迟、没有把社交图谱永久公开**；
代价是"不保证永久可查"——而"永久"对个人用户并不是刚需，需要时再用可选锚定补。

## 14. 可选服务器（中继/撮合）：接口、样机与威胁模型

- 允许内网/公网组网，也允许**加一个可选服务器**：它只做"撮合 + 转发"，**不存消息**（未送达消息留在发送方本机），
  **看不到明文**；不配服务器时退回局域网/打洞/异步通道。
- 协议、加密信封格式、样机（`fwarmy/server.mjs`）、客户端（`zhong-ji-ke-hu.ts`）与门禁（`verify-r58-zhongji` 16/0）
  见 **`docs/SERVER-RELAY.md`**。
- 结论：只要私钥不出本机、客户端强制验签、公钥经**带外核对**，**恶意服务器也拿不到明文**；它能做的是
  拒服务/丢包/延迟、看元数据、以及"替换公钥"——前两个靠多路径与如实提示，最后一个靠指纹核对（不依赖服务器）。
  重放可被原样重发，需客户端按 msgId+ts 去重（协议已留字段，尚未实现）；前向保密（Double Ratchet）未做。

## 15. 网络选择与多服务器（第 59 轮口径）

- 组网优先级：**局域网 mDNS → 自有公网 IP/网关 → 可选服务器**；局域网与网关可用时**不强制**服务器；两者都没有时**必须**选至少一个服务器。
- 服务器可**同时连多个**，按**会话**多选；同一条消息发给该会话配置的所有网络，**任一送达即送达**，其余逐台记录、重试。
- 添加联系人/加入群聊/项目时选择网络（可多选）；创建群/项目时**不选**，创建后在第四列「网络设置」卡里改。
- 服务器用**凭据**授权（每台服务器可发多个有名字的凭据）；与端到端加密互补：服务器能拒服务/看元数据，但看不到明文。
