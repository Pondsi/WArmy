# A16「道」跨设备同步：为什么、举例、边界

> 状态：道的单一来源已落地（`dao.md` 只在「我的」页维护一份）；跨设备同步尚未实现。

## 1. 先明确「道」是什么

「道」是用户自己的最高规范（做事原则、称呼、禁区、输出风格），不是模型自带的人格，也不是项目规范。它只属于**用户本人**，所以同步的对象是“同一个人在不同设备上的道”，不是“把道发给别人”。

## 2. 为什么需要跨设备

因为用户不只在一台机器上工作：

- 公司 Windows 台式机 + 家里 Mac/笔记本；
- 主力机 + 备用机/测试机；
- 重装系统或换机后，希望新机器上的牛马仍然“懂我”，而不是从出厂稿重新开始。

不同步的后果：在 A 机器上调好的道（例如“先给结论、不要客套、代码必须给完整文件”），到 B 机器上全部失效；用户要在每台机器重复维护，且容易版本分叉。

## 3. 具体场景

### 场景 A：公司 + 家里
- 公司机器上的道：`对外邮件先给结论；代码审查只报问题和证据；不要用 emoji。`
- 家里机器上的道：默认出厂稿，牛马回复风格完全不同。
- 同步后：两台机器读到同一份道；改一处，另一台下次启动/手动同步时更新。

### 场景 B：换机/重装
- 旧机器坏了，只备份了身份助记词与数据目录；新机器恢复身份后，道随加密备份一起恢复，不用重新写。
- 若只备份身份不备份道：身份还是同一个人，但牛马“失忆”，需要重写。

### 场景 C：多台机器同时改
- 公司机器把“不要 emoji”改成“可以用少量 emoji”；家里机器同时把“先给结论”改成“先给风险”。
- 如果直接覆盖：后同步的会丢掉前一个修改。
- 正确做法：按条目/段落做三方合并；冲突时保留两份并让用户选，绝不静默覆盖。

### 场景 D：团队共享？
- **不共享**。道是个人的，不随项目/群同步；项目规范走「规范」层，群共享事实走「项目记忆」，两者都不是道。
- 如果把个人道同步给团队，会把个人偏好强加给所有成员，也会泄露个人工作习惯。

## 4. 方案与取舍

| 方案 | 做法 | 优点 | 缺点/最坏情况 |
|---|---|---|---|
| A 端到端加密同步 | 道文件用用户身份密钥加密后，经可选服务器/局域网同步；只同步密文 | 服务器看不到内容；换网不变锚点 | 冲突合并复杂；私钥丢失=道也解不开（需随身份备份） |
| B 导出/导入 | 手动导出加密包，在另一台导入 | 实现简单、可控 | 每次改动都要手动搬；容易忘记，版本分叉 |
| C 云盘明文 | 放到用户自己的网盘 | 最省事 | 明文离开设备；网盘可读；不推荐 |

建议：先做 **B（导出/导入加密包）** 解决“换机恢复”，再做 **A（端到端同步 + 三方合并）** 解决“多机日常”。不做 C。

## 5. 边界

- 道只在「我的」页有一份；同步不产生“第二份道”。
- 同步的是密文；服务器/中继只看到大小与时间。
- 冲突不静默覆盖：保留本地/远端两份，界面让用户选。
- 道里的敏感内容（客户名、内部地址）同步前提醒用户：它会随道到其他设备。
