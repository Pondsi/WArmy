# 第 93 轮交接 · 短记忆按使用频率更新 / 压缩

> 用户口径：
>  · 归档时只从**本会话有权使用的知识库**里，挑**使用频率最高、且还没进短记忆**的内容补进去；
>  · 短记忆超限/需要压缩时，**丢使用频率最低的**，不再丢最旧的；
>  · 可以在条目上写频率标识，或有更好的方案。

## 1. 更优方案：频率放侧车，不污染正文

短记忆正文每轮都会发给模型；如果把 `[f=7]` 写进正文，会白占 token，也会让模型把标记当内容。
现在用**侧车文件**：

- 正文：`userData/guifan/<sid>.md`（保持干净，只有 `- 条目`）。
- 频率：`userData/guifan/<sid>.freq.json`：
  ```json
  { "v": 1, "items": { "<hash>": { "n": 7, "last": 1793... } } }
  ```
  `hash` = 去空白/标点后的小写文本的 SHA1 前 16 位；`n` = 被模型真正用过的次数；`last` = 最后一次使用时刻。

## 2. 使用频率从哪里来

- 知识条目（`ZhishiShijian`）新增 `useCount` / `lastUsedAt`。
- **只有 `knowledge_query` 真正把条目交给模型时才累加**（`knowledge.noteUse(shiJian)`）；写入、UI 浏览、归档整理都不算。
- 每次查询批量写一次盘，避免每条 fsync。
- 检索结果里的“已取代”条目不计数（`activeEventsIn` 过滤）。

## 3. 归档更新算法

`guiNaDuanJiYi(sid)`（归档落库之后调用）：

1. `layers = kbLayersFor(sid)` —— 群聊只有会话层，项目会话+内部，本机牛马三层；**绝不跨出这些层**。
2. `knowledge.activeEventsIn(layers)`，只保留 `useCount > 0`。
3. 生成候选文本：标题（泛称时用正文）+ 正文；去空白/标点后与现有短记忆条目比对，已在短记忆里的不重复加。
4. 按 `useCount` 降序、`lastUsedAt` 降序排序，最多补 10 条。
5. 追加到 `## 短记忆（归档自动整理；界面不可见）` 段；同时写侧车频率。
6. 若整份超过 2000 字，调用 `yaSuoDuanJiYi`，按频率丢条目。

## 4. 压缩算法

`yaSuoDuanJiYi(sid)`：

- 逐条读频率；老条目没有侧车记录时按 `n=1` 起步（避免升级后第一次压缩把历史全删）。
- 总长 > 2000 时，循环找 **n 最小** 的条目删除；同 n 比 `last`（更久没用先删），再比文件顺序（更早先删）。
- 删掉的条目写进内部知识库（`laiYuan:'prompt:overflow'`），`recall` 仍可取回。
- 没有可删条目（纯散文）时停止，交给注入侧压缩；绝不截半句。
- 审计：`prompt.duanjiyi-compressed`；归档更新审计：`duanjiyi.archive-summary`（带 top 5 频率）。

## 5. 验证

`verify-r93-memory-security`（39/0）：

- `noteUse` 按层累加、记录最后使用时间、`activeEventsIn` 过滤被取代条目。
- 真 Electron：种子知识 A(9 次)/B(1 次)/C(0 次) → 归档只补 A、B，A 在前，C 不进。
- 造超限短记忆（高频 1 条 + 低频 10 条）→ 压缩到 ≤2000，高频保留、低频删除。
- 静态：候选只来自 `kbLayersFor`、要求 `useCount>0`、侧车存在、压缩走 `yaSuoDuanJiYi`。

## 6. 取舍 / 最坏情况

- **频率只代表“被 knowledge_query 命中过”**，不代表“真的对答案有用”。模型查了但忽略也算一次；这是可解释的代理指标，比拍脑袋好，但不能当绝对质量分。
- 旧短记忆条目没有历史频率，按 1 起步；第一次压缩会优先丢它们（比新条目更早）。如果用户希望保留历史，可以手工把 `n` 调高（侧车是普通 JSON）。
- 阈值 2000 与上限一致；压缩后可能只剩高频几条，低频内容进内部知识库可 recall。
