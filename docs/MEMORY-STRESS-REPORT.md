## 0. 一句话结论

**2000 轮真对话、1069.7 万字符的日志下，有界视图始终 ≤ 预算（2000 轮里 0 次越界）、渲染只要 0.21 ms/轮，
"不丢 + 可解引用"这条底线用 `retrieve` 做到了 40/40 命中；但"模型看得见多少事实"完全由
"中段抽样要点（24 条 × 240 字）+ 头 1 条 + 尾 8 条"这套采样器决定，与预算大小几乎无关——
预算从 100 万字符压到 3.1 万字符（−96.9%），10 条抽查的可见性一条没变（都是 5/10）。
长期记忆的真正缺口不在预算，而在"摘要没有回灌上下文"：自动摘要只进归档，模型看不见。**

## 2. 判据：业界通行做法（联网检索所得）

这一节是我设计压测与判定"合格线"的依据，全部来自官方原文（webfetch 抓正文）：

| 来源 | 关键做法 | 对本项目的对照结论 |
|---|---|---|
| Anthropic《Effective context engineering for AI agents》(2025-09-29) | ① **Compaction**：接近窗口上限时把历史交给模型**总结**，用"摘要 + 最近 N 个文件"续跑（Claude Code 保留架构决策/未解 bug/实现细节，丢弃冗余工具输出）；② **Structured note-taking**：把笔记落到上下文之外的持久存储，之后**再拉回上下文**；③ **Sub-agent**：子代理用干净窗口干活，只回 1000–2000 token 的蒸馏；④ 引用 Chroma "context rot"：token 越多，召回越不准；目标是"**最小高信号 token 集合**" | 本项目做对了①②的一半：**有**持久化（JSONL/归档/知识库）与**规则型**压缩，**缺**"摘要自动回灌上下文"——归档摘要没有注入点，知识库要模型自己调 `knowledge_query`（§8 发现②）。另外 compaction 明确是"**用模型**总结"，而本项目的中段要点是"抽样 + 规则压缩"，不含语义蒸馏 |
| MemGPT / Letta（arXiv:2310.08560 摘要 + Letta 官方 Memory 文档） | **virtual context management**：把上下文当"快内存"，用**分层记忆**（主上下文 / 外部存储）之间搬运数据，让模型在有限窗口里"看起来"有大内存；用中断让模型自己决定何时读写记忆。Letta 现状：git 版本化的 MemFS 文件式记忆 + `/remember` 显式记忆 + **dreaming**（后台子代理在**上下文窗口被压缩时**触发，巩固经验再写回记忆） | 本项目的 recall/retrieve/knowledge_query 就是 MemGPT 的"按需换入"那一半，且做得更严（权限先于相关、非 exact 命中强制告警）；**缺**的是"自动搬回"：MemGPT/Letta 在**窗口被压缩时自动**巩固并写回，本项目只能靠模型主动调工具，渲染器**不会**自动把命中事实塞回上下文 |
| LangChain conversation summary memory / Deep Agents | summary memory：用 LLM 把历史滚动摘要，把"摘要 + 最近 K 轮"喂给模型。⚠️ **本机取不到官方原文**：`python.langchain.com` 旧文档站 302 到新版 overview，只抓到 Deep Agents 的 "automatic context compression" 提法 | 该模式的三要素（滚动摘要、摘要+近 N 轮、摘要持久化）本项目只有第 2、3 项，第 1 项被"规则抽样"替代。因此下面的评估会把"滚动摘要"列为**最高优先可改点** |

**由此确定的判据（本报告的合格线）**：
1. **有界性**：视图字符 ≤ 预算，任何日志长度、任何预算下都成立（硬断言）；
2. **不丢**：被省略的内容必须能逐字节取回（`retrieve` 100% 命中）；
3. **可解引用**：指针必须完整可执行（seq 范围 / recordId / 语义线索三线索冗余）；
4. **摘要有效**：进入视图的"要点"应当覆盖历史中的**事实**，而不只是"样本条目的前 240 字"；
5. **诚实**：上下文里没有的，模型必须说"没有"，不许编造。

## 3. 方法（哪些是"真"的，哪些是"复刻"）

| 组件 | 真实性 | 说明 |
|---|---|---|
| 有界视图渲染 `xuanranYoujieShitu()` | **真模块**（`packages/app-shell/dist/context-renderer.js`，直接 import 编译产物） | 产品里唯一的注入入口；`keepHead=1`、`keepTail=8`、`DIGEST_MIN_SHARE=0.25`、`MAX_RANGE_RECORD_IDS=8`、`ENTRY_SAMPLE_MAX=24`、`ENTRY_SAMPLE_CHARS=240`、`CCR_SAMPLE_BUDGET=8000` 全部用默认值 |

| 超限收缩阶梯 `1.0→0.6→0.35→0.2` | **⚠️ 复刻** | 同因（`daiShangXiaWenChongShiYunXing` 也是 electron-main.ts 内部函数） |

**每次（run）1000 轮对话的流程（严格串行，每轮 2 条日志）**：

```
① 生成用户消息：5200 字"长文本工作记录"（24 段真实中文技术叙述轮转）+ 埋点 + 一句提问；
   每 50 轮附加一段 17200 字符的"构建输出"（专门触发写入侧 CCR 截断分支）
② 写入侧 CCR beforeLog()                       ← 真模块
③ memory.append()（JSONL + 三路投影，seq 单调） ← 真模块
④ xuanranYoujieShitu(log, {budget, keepHead:1, keepTail:8})  ← 真渲染器 + 真/复刻预算
⑤ 真调模型：[system(不许编造)] + 视图（头 1 条 + 指针/要点 + 尾 8 条）  ← 用户消息在尾窗里，不重复发
⑥ 助手回复 append 入日志（正文不截断）
⑦ 记录指标 → runN.metrics.jsonl；每 10 轮写进度 → runN.state.json（可断点续跑）
```

**埋点设计（每 run 18 条，见 `docs/MEMORY-STRESS-LEDGER.md` 全表）**：

| 类别 | 轮次 | 位置 | 设计意图 |
|---|---|---|---|
| 开头 F-01…F-06 | 第 1、3、8、12、16、20 轮 | F-01/02/04/06 放在消息**开头**，F-03/05 放在消息**结尾** | 第 1 轮会被 `keepHead=1` 逐字保留；第 3 轮会落进中段采样窗的 240 字内；第 8 轮（放结尾）落在 240 字**之外**；12/16/20 轮落在采样窗之外 |
| 中间 M-01…M-06 | 第 498–501 轮 | 各轮头/尾 | 检验"第 500 轮左右"的事实是否还能被带进上下文 |
| 最近 R-01…R-06 | 第 997–1000 轮 | 各轮头/尾 | 落在 `keepTail=8`（= 最近 4 轮）里，作阳性对照 |

**抽查方式**：两次 1000 轮结束后，各抽 10 条（开头 4 / 中间 3 / 最近 3），把**当时的最终视图** + 一句提问
（"我第 N 轮说过的那条编号 XXX 的事实是什么？如果不在这条信息不在你可见的上下文里，请直接回答「当前上下文里没有这条信息」，不要猜测。"）
发给模型，判分标准 = 回答里是否出现该事实的**唯一答案 token**。抽查**不再改动日志**。
为隔离"预算"与"模型"两个变量，同一份日志各跑两组（2×2 对照）：
`MiMo+大预算(1,006,634 字符)` × `MiMo+小预算(31,458 字符)` × `本机ollama 4b+小预算(31,458 字符)`（共 4 组 40 条）。

**断点续跑**：日志在 `.memory-stress-state/runN/`（真服务落盘），进度在 `runN.state.json`。实测：跑到第 20 轮后杀掉进程，重跑时脚本打印"起始轮次 21，已有日志 40 条 / 100866 字符"并正确接续（冷启动从 JSONL 重建投影）。

## 5. 记忆抽查结果（4 组 × 10 条 = 40 条，全部真调）

判据列说明：
- **正文在视图内** = 该事实的答案 token 确实出现在发给模型的视图文本里（后验用同一份日志重算，见 `--regen` 模式）；

**两条硬结论**：
1. **命中 ⟺ 事实正文在视图内**：4 组共 40 条，正文在视图内的 20 条**全部**答对（含上面那条重跑 3/3 独立复现）；
   正文不在视图内的 20 条**全部**如实回答"当前上下文里没有这条信息"，**0 编造**。
2. **预算大小对"看得见多少事实"没有影响**：预算从 1,006,634 → 31,458 字符（−96.9%），
   视图从 38,742 → 28,714（−25.9%），但 10 条的可见性**一条没变**（都是 5/10）。
   可见性的决定因素是"头 1 条 + 尾 8 条 + 中段 24 条样本"，不是预算。

### 5.6 解引用腿（recall / retrieve）

| 路 | 命中 | 说明 |
|---|---|---|
| `retrieve({recordId})` 精确取回 | **40/40 = 100%** | 全部逐字节取回原文并包含答案 token。**"不丢 + 可解引用"这条底线成立** |
| `recall(token, 5)` 关键词/语义召回（top-5 卡片） | 28/40 = 70%（run1 9/10 ×2、run2 5/10 ×2） | 漏的都是**纯数字类答案 token**（`7782`、`6318`、`3351`…）：这些 4 位数字在我自己的生成文本/"观测值"里也出现过，FTS 打分把它们排进了前 5，真记录被挤出 |

### 7.1 性能（优）

- 云端 2000 次真调用 **0 失败**；均值 6.9 s（run1）/ 11.0 s（run2）；长尾由共享账号排队造成（p99 26–47 s、峰值 101 s）。
  两条 1000 轮对话并行比串行只多花约 1.5 倍墙钟换取 2 倍总量，性价比合理。
- **渲染器几乎没有成本**：0.21 ms/轮、峰值 2 ms，且在 524 万字日志上不变 —— 这条最值钱（O(视图) 而非 O(日志)）。
- 本机 4b 模型反而更快（5.8 s/轮），但只承载 31,458 字符预算；本地推理是"省 token 换质量"的选项，不是替代品。

### 7.2 效率（有明确浪费）

- 视图 38,742 / 日志 5,239,897 = **0.74%**；压缩比 1:135，看起来极佳，但代价是**信息损失不可控**（见 7.4）。
- 预算利用率 **3.8%**：1,006,634 字符的预算只用了 4 万。**预算这个旋钮实际上被"要点采样器"架空了**：
  调它只改变头尾能留多少，不改变事实覆盖。
- prompt token 累计 4,596 万，缓存命中仅 **16.2%**（视图每轮变，前缀命中不稳）。若把视图做成"前缀稳定"
  （要点分块、只在阈值处变更），缓存命中还能明显提高。
- **同一份视图内容，4 组抽查花的 token 完全相同，但小预算组并没有因为预算小就更省** —— 因为视图规模由采样器决定。

### 7.3 完成度（达成既定目标，但有未覆盖项）

| 目标 | 结果 |
|---|---|
| 连续 1000 轮 × 2 次 | ✅ 2000/2000 全部完成，0 失败轮 |
| 对话记录 > 10M 字符 | ✅ **10,696,801 字符**（104.3%），另 25,690,455 字节 |
| 真调 API（不许模拟） | ✅ 2040 次真调用（MiMo + 本机 ollama） |
| 走真实预算 + 真实压缩 | ✅ 渲染器/CCR/记忆服务是**真模块**；预算函数是**复刻**（已在 §3 明确标注） |
| 中途崩溃能续跑 | ✅ 实测从第 21 轮接续成功 |
| 未覆盖 | ⚠️ ① 真 Electron 门禁 `verify-context-renderer.mjs` 未跑（不许启动 Electron）；② 本机 ollama 只承担 40 轮（4%，脚本按 `--ollamaTail` 默认值跑，未放大）；③ 视图从未接近预算上限（峰值 40,026 ≪ 1,006,634），**"预算真的不够用"时的那条路径只在小预算组被部分走到**；④ `recall` 的向量腿未启用（无嵌入模型文件），只跑了 FTS 两腿 |

### 7.4 理解度（合格线之上，但"长期事实"确实会丢）

- **看得见的就答得对**：正文在视图内的 20/20 条答对（含 3 次独立复现），且模型能指明"依据第 3 轮记录的压缩要点，不是逐字原文"——**不把"相似"说成"就是"**，这一点做得比很多实现好。
- **看不见的一定答"不知道"**：20/20 条如实声明"当前上下文里没有这条信息"，0 编造。
  典型回答："我可见的范围只包含记忆点 R1-F-01（第 1 轮，幸运数字 8317）以及第 997 轮起的 R1-R-01 至 R1-R-06；
  第 12 轮的原始记录已被压缩省略，其中未包含 R1-F-04 的内容，所以无法给出它的具体表述，**不做猜测**。"
- **但"长期记忆"名义下的能力是打折的**：第 498–501 轮埋的 6 条事实，20 次抽查（4 组 × 5 条相关）**无一次可见**。
  对用户而言，这等于"两千轮里第 500 轮说过的事，模型再也想不起来"——除非它主动调 `retrieve(recordId=…)`，
  而报告里模型自己指出："**本轮也未提供 retrieve/recall 工具**，无法取回。"
- 唯一"看得见却答错"的形态是 `仅编号可见`（run2 4 条）：模型看见 `R2-M-05` 这个编号就答
  "上下文里有这条信息"，随后发现没有内容再改口。**编号进了上下文、内容没进**，是当前实现最容易误导模型的信息形态。

### 7.5 满意度（从产品视角）

- "有界不炸""日志不丢""可解引用"三条硬需求：**满足**（2000 轮 0 越界 / 40/40 retrieve 命中 / 断点续跑可用）。
- "记得住"这条软需求：**只在对最近 4 轮和最早 1 条成立**。用户最容易感知的"中段失忆"没有被解决。
- 视图构成（头 1 条 + 一期要点 + 尾 8 条）在实战里会让模型反复看到**同一份 6,224 字符的要点**（第 2–6 轮样本），
  这部分内容随时间**完全不更新**——1000 轮对话结束时，模型"看的历史"里仍然只有开头那几轮样本 + 最近 4 轮。

### 7.6 遵守度（优）

- 系统提示里的"不许编造、没有就说没有"被 40/40 条严格执行；20 条未知项**零幻觉**。
- 模型还主动给出可执行的补救建议（`recall("R1-M-05")` / `retrieve(seq=…, recordId=…)`），与视图里指针文本提供的三线索一致
  —— 说明指针格式对模型是**可理解、可执行**的。
- 唯一瑕疵：本机 ollama 4b 的 40 轮里有 6 条把 `<think>…` 思维链原样吐进**正文**（脚本已传 `think:false` 仍未完全抑制），
  这类思维链会以 assistant 正文身份进日志、再进后续上下文。

### 7.7 安全性

- 密钥只在脚本进程内经 `fs` 读取 **`MIMO_KEY_FILE` 环境变量**指向的文件；报告、日志、账本里**没有任何 key 片段**，
  也未写入 `.memory-stress-state/`。
- 写路径全部经真记忆服务（写入者白名单 `duty`；`executor` 写 message 会被拒 —— 本次未触发该分支）。
- 记忆文件的权限隔离未被本次压测覆盖（未跨 session 越权检索）；不过 `recall` 调用带了
  `scope:{sessionId}`，run1/run2 的命中结果**没有互相串号**（见 5.2–5.5 的 recordId 前缀 `m-1-*` / `m-2-*`）。
- 未做：注入攻击/Prompt Injection 压测（把恶意指令埋进历史记录看模型是否执行）——**列为未覆盖**。

## 8. 发现与建议（按优先级）

### 发现①（真 bug，但**我没改**）：极端预算下 `stats.pointers` 谎报"存在可执行指针"

- **证据**：同一份 5,239,897 字符日志，`budgetChars=200` 时视图 = 200 字符，
  其中 system 段被硬裁成 42 字 = `[已省略 2000 条，seq 1..2000，共 5,239,897 字] ret`
  —— `retrieve(seq=1)` 被切断、三条冗余线索只剩半条，**指针实际不可执行**；
  但 `xuanranYoujieShitu().stats.pointers` 返回 **1**。
- **为什么算 bug**：`context-renderer.ts` 自己在另一分支写明规则——"指针被截断 → 不可执行，如实记 0 条"
  （第 479 行 `pointers = 0; // 指针被截断 → 不可执行，如实记 0 条`），而"降配成功"分支（第 465 行
  `pointers = ranges.length`）没有做同样判断，随后被第 3 步/第 4 步的裁剪改写了文本却没有修正计数。
  这会让 `metrics.recordView()` 的观测值与"指针必须完整可执行"的不变量对不上（ADR §5 / 不变量 #4）。
- **建议改法（一行级）**：在第 3 / 第 4 步裁剪之后，若指针消息（role=system 的那条）的文本长度
  与其完整形态不一致（或在 `jieWeiAnQuan`/`yingQianzhi` 真的动了 system 段时）把 `pointers` 置 0，再 `mkStats`。
- **为什么我没改**：`context-renderer.ts` 是被 `packages/app-shell/scripts/verify-context-renderer.mjs` 覆盖的共享纯函数，
  而该门禁包含"真 Electron 跑 24 轮"环节，**在本任务"不许启动 Electron"的约束下我无法运行对应验证**。
  按"未经验证的改动不上"的原则，这里只报告 + 给出改法。

### 发现②（设计缺口，最值得改）：摘要没有回灌上下文，长期记忆全靠模型自己调工具

- **证据链**：
  1. 自动摘要的开关是真的接上了——`renderer/app.js:5450-5460` 每 60 s 检查一次，会话空闲 > 3 min 且距上次 > 10 min 时
     发起 `warmy:huiHuaZhaiYao(auto:true)`（`electron-main.ts:15445`）。
  2. 归档摘要本体（`archive/archives.jsonl`）**只有写入方与 UI 列表方**：全仓 `archiver` 只在
     `electron-main.ts:3644 / 15497 / 15560 / 15596` 出现（构造、写入、给界面列列表），**没有任何注入模型上下文的地方**。
  3. 归档时抽取的知识（实体/事件）**可以**被模型取到，但走的是**模型必须自己主动调**的 `knowledge_query` 工具
     （`electron-main.ts:2484-2497`）——不是自动回灌；而且抽取是**纯规则 regex**（`congGuiDangTiQuZhiShi` / `tiQuJieGouHuaZhaiYao`，零 LLM），
     摘要正文只取**末 30 条、每条截 160 字**。
  4. 于是模型能看到的"历史要点"其实是渲染器里的**抽样**（24 条 × 240 字 + CCR，永远不会覆盖中段 5 百万字），
     与归档摘要**互不相干**。
- **后果（实测）**：中段 6 条事实 20 次抽查全不可见；模型自述"本轮未提供 retrieve/recall 工具，无法取回"。
- **建议**（按性价比排序）：
  1. **把归档/项目记忆注入视图**：`renderChatView()` 的 `recallHint` 之外再给一个"长期要点"槽位，
     优先注入最近 N 次 session 摘要的 bullets（有上限，比如 1200 字，与项目记忆同样的截断告警）；
  2. **把中段要点从"抽样"换成"滚动摘要"**（这是 §2 判据里 Anthropic compaction / LangChain summary memory 的核心）：
     用一次 LLM 调用对"被挤出去的那一段"生成摘要并**持久化**，后续复用（而不是每次重新抽样 24 条）；
     预算不变的前提下，事实覆盖率会显著上升；
  3. **给模型自动解引用**：当渲染器判定"用户提问命中被省略区间"（例如问题里出现记录编号/seq）时，
     自动做一次 `recall`/`retrieve` 把结果前置到视图，而不是等模型想起调工具；
  4. **编号不应单独进上下文**：实测"只有编号、没有内容"会让模型误答"上下文里有这条信息"。
     若必须列编号，应紧跟一句"编号对应的内容不在上下文中，需要 retrieve 才能看到"。

### 发现③（脚本/平台侧，非产品 bug）：MiMo 推理模型的 reasoning 与正文共享 `max_tokens`

- **证据**：pilot 阶段把 `max_tokens` 设为 192 时，40 轮里 **10 轮**返回 HTTP 200 但 `content` 为**空字符串**，
  `completion_tokens` 被 `reasoning_content` 吃满；正式运行把上限提到 512 后 2000 轮 **0 次空正文**。
  另在抽查里出现过一次正文只 19 字就 `stop`（同提示重跑 3 次全对）。
- **为什么不算产品 bug**：产品侧默认 `maxTokens` 上限大得多（示例路径 4096），且对"本轮模型没有返回文字内容"
  有空正文兜底重答（`electron-main.ts:7031-7047`）。**但这是一个真实的踩坑点**：接入新推理模型、
  或把 `maxTokens` 调小时会静默产生"调用成功但没人说话"。
- **建议**：provider 层在 `finish_reason === 'length'` 或"正文为空但 reasoning 非空"时，
  自动以更大 `max_tokens` 重试一次，并在界面上如实标注"本轮只有思考、没有正文"，而不是让空字符串进日志。

### 发现④（小问题）：本机模型的思维链会以正文身份进日志

- 本机 ollama 4b 40 轮里有 6 条把 `<think>…</think>` 连同推理过程写进 `content`（脚本已传 `think:false`），
  这些正文随后成为历史、被后续上下文引用。**建议**：入口处过滤/剥离 `<think>` 段并归到 `reasoning` 通道（只给界面看）。

### 发现⑤（度量口径）：`recall` 的 top-5 + 纯 FTS 打分在"数字型唯一 token"上会漏

- 实测 40 次 `recall` 只有 28 次命中目标记录（70%），漏的全是 4 位数字型 token，
  原因是这些数字在别的记录里也出现（我生成文本里的"观测值"就带随机数字），RRF/FTS 把干扰项排进了前 5。
- **建议**：给 `recall` 结果加"精确 token 命中"的加权（含 `fts_tri` 精确子串的一路单独提权），
  或允许调用方传 `limit` 更大 + 结果里标出"这是编号匹配、不是语义匹配"。

### 发现⑥（测试基建）

- 仓库根已有 6 个 `verify-*.mjs`，但**没有**"记忆/上下文"的独立压测门禁；建议把本脚本的
  `--rounds 100 --stateDir <tmp>` 模式（约 6 分钟）纳为 CI 冒烟：断言 0 越界、视图/日志比 < 2%、
  渲染 < 5 ms/轮、续跑可用。完整 2000 轮（3 小时）留给定期长跑。

## 9. 未做 / 未验证 / 残留风险（如实记录）

   所以"预算逼近上限时的逐级降配"只在 §6 的零 API 复算里被完整验证，**没有在真调对话里走完**。
4. **向量腿未启用**：本机无嵌入模型文件，`recall` 只有 `fts_uni` + `fts_tri` 两腿（向量腿按设计 skip）。

   日志在抽查期间未被修改（抽查不写日志），因此两者应当一致，但严格说这是**重算**而非**原始快照**。
7. **复刻函数的漂移风险**：预算函数是复刻（§3），若 `electron-main.ts` 的算法/常量改动，本报告的预算数字需要跟着重算。

   "SQLite 只是可重建的投影"，需要复核 `recall` 时跑一次 `--regen` 即可从 JSONL 冷启动重建（脚本会重建）。
   不需要时整个目录可删（`docs/MEMORY-STRESS-LEDGER.md` 与本报告是文字版证据，不依赖它）。
