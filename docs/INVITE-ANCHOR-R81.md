# 邀请名片 / 会话锚点设计评估（#108）

## 1. 用户提出的方案

加入群聊/项目/联系人时，给该会话一个**专有 ID（或凭证）**：不显示、不可改，作为锚点；换网络后仍能联系上彼此。

## 2. 结论：方向正确，但“随机专有 ID”不够

只用随机 ID 的问题：

- 中继/服务器可以替换这个 ID，把消息导向自己；
- 对方无法验证“这条消息真的来自这个会话”；
- 换机/重装后 ID 可以复制，无法区分“同一个人换设备”还是“别人拿了 ID”。

因此建议把“专有 ID”升级为**每会话一对 Ed25519 密钥**：

- 创建项目/群/联系人关系时生成 `anchorKey`；
- **公钥指纹 = 会话锚点**（可显示成短安全码，供带外核对）；
- 私钥只在本机系统安全存储，**不显示、不可改**；
- 邀请名片/二维码只带公钥指纹 + 一次性邀请 token + 可选服务商列表；
- 消息、成员证书都用该私钥签名；换网络/换服务器只换传输地址，锚点不变；
- 旧邀请在创建者确认后通过 `supersedes` 失效。

这比随机 ID 好：服务器无法冒充会话，历史消息可离线验签，换网不断关系。

## 3. 备选方案对比

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| 随机 UUID + 服务器映射 | 实现最简单 | 可被替换/伪造；换机无法证明同一性 | 不推荐做安全锚点 |
| 每会话 Ed25519 指纹（推荐） | 可验签、换网不变、离线可验 | 私钥丢失=会话身份丢失，必须随身份备份 | 群/项目/联系人 |
| did:key / VC 标准 | 标准化、可互操作 | 依赖库与解析、体积大 | 以后要跨产品互操作时 |
| Signal 式安全码 + TOFU | 联系人体验好、防中间人 | 群规模大时成员验证成本高 | 联系人优先，群用创建者证书 |

建议落地：联系人用“安全码 + TOFU”，群/项目用“创建者密钥 + 成员证书”，底层同一套 Ed25519；对外都只显示短指纹，不显示原始 ID。

## 4. 最坏情况

- 只做随机 ID、不验签 ⇒ 恶意中继可冒充该会话发消息。
- 做了锚点但不备份私钥 ⇒ 换机/重装后老会话无法继续，只能重新邀请。
- 名片里带长期私钥或可改 ID ⇒ 等于没有锚点，且泄露即被接管。

## 5. 与角色矩阵的关系

- creator：唯一，持有创建者密钥，签发/吊销成员证书；
- admin：可审批加入、移除 member、改设置，但不能改 creator/锚点；
- member：只读+发言，不能改设置/审批/移除；
- 审批流：pending → creator/admin 批准 → 签发成员证书；拒绝不泄漏群内容。
